# Plan: #2053 sync: pullSession paginates card_reviews with no ORDER BY

## What this is

`pullSession` (`lib/sync/cloud.ts:364-392`) walks `card_reviews` in 1000-row `.range()` pages
with no `ORDER BY`. Offset pagination without a stable sort key can skip a row when the
underlying rows move between requests, and `card_reviews` is the one synced table whose rows
are constantly UPDATEd. A skipped row means a card's cloud state never reaches this device,
with no error, no banner and no log line.

The sibling paginator on the append-only table already does this correctly and explains why:
`lib/sync/gradeLog.ts:73-83` orders by `occurred_at` before `.range()`. I confirmed the split
across the repo: of the six paginated reads, only `pullSession` and `pullStreak`
(`lib/sync/streak.ts:38-58`) lack an `.order()`. The three route handlers
(`app/api/export/route.ts:123-129`, `app/api/srs/optimize/route.ts:84-90`,
`app/api/push/send-daily/route.ts:734-739`) all already order, so this change closes the
last two gaps rather than one of many.

I also verified the persistence claim in the issue. `pullAndMerge.ts:604` sets
`lastPullAt: maxCloudUpdatedAt(cloudRows)` from the rows that *were* returned, so a row
dropped mid-scan whose `updated_at` predates that maximum fails rule 3 (`updated_at >
lastPullAt`) on every subsequent pull. The miss does not self-heal.

This is a defensive fix. Nothing proves the drop has happened in production (by design it is
silent), and with the 4-column PK the planner will often pick an index scan and make it a
non-event. The asymmetry is what justifies it: one method call against a silent data-loss mode.

## Approach

**Sort key: the PK tail, `(card_type, subject_key, locale)`.** `user_id` is already pinned by
`.eq()`, so those three columns complete the primary key `(user_id, card_type, subject_key,
locale)` (migration 029, `db/migrations/029_card_reviews_locale.sql:28`). Two properties matter:

1. They are **immutable for a live row**. Every write path upserts on
   `CARD_REVIEWS_CONFLICT_COLS`, so an UPDATE can never change a row's sort position. That is
   precisely the class of concurrent write this bug is about, and ordering on the PK eliminates
   it outright rather than narrowing it.
2. They are a **prefix-compatible match for `card_reviews_pkey`**, so the ordering can be served
   straight from the PK index with no sort node.

Rejected alternatives:

- **Order by `updated_at`.** It is the column every concurrent write changes, so rows would move
  between pages by construction. Strictly worse than no ordering.
- **Order by `subject_key` alone.** Not unique: the same species has rows for several
  `card_type` values and up to four locales, and ties within a sort key are ordered arbitrarily,
  so the boundary between pages would still be non-deterministic.
- **Keyset pagination now.** Immune to inserts as well as updates, but it changes the
  `fetchAllPages` contract (`lib/sync/paginatedFetch.ts:27`) for all five current callers,
  including three route handlers. Much larger review surface for a bug that has never been
  observed. Raised as an open question below rather than silently deferred.
- **A `count: 'exact'` head request compared against rows collected, to make a drop loud.** An
  extra round trip on every visibility pull, and the count is itself taken at a different instant
  from the pages, so it would fire false alarms during entirely normal concurrent writes.

**Routing `pullSession` through `fetchAllPages` is behaviour-preserving.** Today the loop pushes
the `subject_key !== null`-filtered rows into the accumulator but checks the last-page condition
against the raw `data.length`. `fetchAllPages` uses the same `data.length < pageSize` check, so
moving the filter to the returned array produces an identical result. Error handling is also
identical: both return `null` on `error || !data` and both swallow throws into `null`.

**Keep the null-`subject_key` filter.** Since migration 029 put `subject_key` in the PK it cannot
be null any more, so the filter is vestigial, but removing it is an unrelated call and would put
a behaviour change into a fix PR.

**`pullStreak` gets the order, not the comment.** The acceptance criterion allows either. Ordering
is one line, is index-served, and removes the need for a future reader to re-derive the
append-only argument. `streak_days` exposure is low, but consistency across all six paginated
reads is worth more than the saved line.

  received `("card_type", { ascending: true })`, `("subject_key", …)`, `("locale", …)` in that
  order. This is the anti-regression guard the issue asks for: the clause cannot be dropped
  silently later.
- `pullSession applies the ordering on every page request` - two-page fixture (1000 rows then

  called three times *per page* (six in total), since each page rebuilds the chain from
  `client.from(...)`. This is the criterion that actually pins "on every page request".
- `pullSession returns rows collected across both pages` - length 1500.
- `pullSession skips rows with a null subject_key` - pins the filter through the `fetchAllPages`
  refactor.
- `pullSession returns null when a page errors` - pins the fall-back-to-local-only contract.

`lib/sync/streak.test.ts`: extend `makeClientWithSelect` to `select → eq → order → range` (mirror
the chain already used in `lib/sync/gradeLog.test.ts:13-22`) and add

Deliberately **not** run, with reasons:

Also rejected: an integration test against the local `postgres:15` container that inserts >1000
rows, mutates one mid-scan and asserts nothing is lost. It would only fail when the planner
happens to choose a sequential or bitmap heap scan, which is exactly the thing we cannot pin, so
it would be a flaky test that proves nothing deterministic. The value is in the ordering
assertion, not in reproducing the race.

Downstream blast radius is nil: every other test that touches `pullSession` mocks the whole
`@/lib/sync/cloud` module (ten files, checked), and the mock-auth seam's query builder
(`lib/auth/mockAuth.ts:166`) already implements `order()` returning `this`, so e2e mock-auth runs
are unaffected.

## Risks and unknowns

- **Residual insert-shaped window.** `ORDER BY` on immutable PK columns closes the UPDATE-induced
  drift completely, but offset pagination is still not immune to a concurrent INSERT that sorts
  *before* the current offset: it shifts the window by one and can still push a row past the
  boundary. Inserts do occur mid-scan (the first grade of a previously-unwritten card, and the
  first-sign-in `pushSession`). The window after this change is much narrower than today's but it
  is not zero, and the acceptance criteria as written do not close it. See the open question.
- **Unfalsifiable success criterion.** We cannot demonstrate the bug ever fired in production;
  there is no log line for a dropped row. Success here is "no regression and a narrower failure
  mode", not a fixed defect count. Worth saying plainly in the PR body so the review is not
  looking for evidence that cannot exist.
- **Performance.** ~1500 rows, index-served ordering. If the planner does pick a bitmap scan it
  adds a sort over at most 1000 rows per page. Negligible either way, but it is a claim from the
  query shape rather than a measurement.
- **Minor documentation trap.** `lib/sync/cloud.ts:228` and `:332` cite "docs/sync.md F22" and
  "F23", but no `F`-numbered markers exist in `docs/sync.md` (the references are stale). Do not
  extend that numbering when adding the new subsection.

## Open questions for Fraser

**Should the residual insert-drift be closed in this PR, or filed as a follow-up?**

- **Option A (recommended): ship the `ORDER BY` exactly as the issue specifies, and file a
  follow-up issue for keyset pagination.** Two one-line changes plus tests, matches the four
  acceptance criteria and the existing `pullGradeLog` convention, tiny review surface. Leaves the
  narrower insert-shaped window open, tracked rather than forgotten.
- **Option B: add keyset pagination to `fetchAllPages` now** (cursor on the sort tuple instead of
  an offset) and migrate all five callers. Closes both the update and the insert window
  completely. Cost: it changes a shared helper's contract and touches three route handlers
  (`export`, `srs/optimize`, `push/send-daily`) plus the two sync legs, so a small defensive fix
  becomes a cross-cutting refactor of every paginated read in the app, for a failure mode that
  has never been observed in production.

I recommend A: the fix in the issue removes the dominant cause (updates, which are the constant
traffic on this table) and the leftover risk is both smaller and better handled as its own
scoped change than bolted onto a one-line fix.
