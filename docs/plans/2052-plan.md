# Plan: #2052 Undo does not roll back cloud state: the undone grade is resurrected by the next pull

## What this is

The practice-page Undo rolls back local state only. For a signed-in user the graded state has
already left the device on two paths by the time Undo lights up, and neither undo handler reverses
either, so the undone grade survives in Supabase and is merged back on the next pull.

Every claim in the issue was re-checked against the code on this branch (`qa` at `7bbd0ed0`) and
holds:

- `enqueueGrade` is called once, during the visible swap (`components/review/ReviewSession.tsx:2736`),
  arming the 200 ms push debounce (`lib/sync/usePerGradeSync.ts:306`).
- The undo snapshot is armed only after `saveSession` resolves inside the background persistence
  chain (`components/review/ReviewSession.tsx:2895`), i.e. after the push was already armed.
- `appendGradeEntry` dispatches `GRADE_LOG_APPENDED_EVENT` (`lib/gradelog/persistence.ts:272`) and
  `AutoSyncOnChange` turns it straight into a `pushGradeLog` with no debounce
  (`components/sync/AutoSyncOnChange.tsx:95`).
- Neither undo path touches the cloud: `handleUndo` (`components/review/ReviewSession.tsx:2993`) and
  the Cmd/Ctrl+Z handler (`components/review/ReviewSession.tsx:1537`).
- `removeGradeEntry` is local-only and cannot be anything else: migration 018 dropped
  `grade_log_update` / `grade_log_delete` (`db/migrations/018_reset_all_progress_rpc.sql:17`), so the
  client has SELECT + INSERT on `grade_log` only.
- `mergeGradeLog` is a pure union with no tombstones (`lib/sync/gradeLog.ts:116`), written back by
  `saveGradeLog` in `lib/sync/pullAndMerge.ts:557`.

One thing the issue understates, and it changes the option costs: **the client cannot push the
reverted card state either.** `card_reviews_reject_regression_trigger` blocks `last_review` moving
backward and `reps` / `lapses` decreasing (`db/migrations/015_card_reviews_reps_lapses_non_decreasing.sql:40-63`),
which is exactly what an undo produces. So "push the reverted state" is not a small variant of the
current code, it needs a SECURITY DEFINER RPC.

This plan recommends a direction and specifies it fully, but the direction itself is a product call
and is the first open question below. Everything in "Files to change" and "Testing" is for the
recommended option (defer the cloud write until the undo window closes); the other options are
costed in "Approach".

## Approach

**Chosen: hold the last grade on-device until the undo window closes.** The undo window is not a
timer, it is "until the next grade, or until you leave the session" (the snapshot is overwritten by
the next grade at `ReviewSession.tsx:2895` and consumed by undo at 3034). So the commit boundary is
exactly: next grade, page hidden, or session unmount. Holding at those boundaries restores the #257
design premise ("the unsynced grade is rolled back locally before the push runs") that #133's
per-grade debounce and the undebounced grade-log push broke, and it needs no schema change.

The held grade is still written to the persisted pending queue, so durability is nearly unchanged:
a force-kill during the undo window leaves the grade in `poke-memory:pending-grade-queue:v1` and the
mount-seed effect replays it next session. What is genuinely lost is a force-kill window for the
grade-log entry, which is why open question 3 exists.

Rejected:

- **Push the reverted card state after undo.** Blocked by the regression trigger: `reps` decreasing
  and `last_review` moving backward both raise `check_violation`, so `pushSingleCard` returns
  `"rejected"` and the card is evicted (`lib/sync/cloud.ts:334`). This is the divergence the issue
  describes, not a fix for it.
- **DELETE + INSERT the `card_reviews` row to bypass the trigger.** The trigger is `BEFORE UPDATE`
  only, so this would work, and that is precisely why it must not be done: AGENTS.md and docs/sync.md
  both say the trigger is not to be worked around, and a client-side delete-and-reinsert is the #293
  failure shape with extra steps.
- **A rollback RPC plus grade-log tombstones (issue option 2).** Correct in the strongest sense
  (undo works however late it is clicked), but it needs a migration adding a SECURITY DEFINER
  `undo_last_grade`-style function that can legitimately regress `card_reviews`, a tombstone column
  or table for `grade_log`, a merge-side tombstone rule in `mergeGradeLog`, and a real-RPC
  integration test under `lib/sync/integration/` (docs/testing.md: a new RPC needs both a migration
  and a real-RPC test). It also hands the client a sanctioned way to move `card_reviews` backwards,
  which is the one thing the whole trigger family exists to prevent. Costed under open question 1
  rather than dismissed.
- **A fixed delay (push N seconds after the grade).** Only works if Undo also expires after N
  seconds, which is a bigger UX change than cancelling it on page-hide, and it leaves the same bug
  for anyone who clicks Undo at N+1 seconds.
- **Moving the grade-log push out of `AutoSyncOnChange` into `ReviewSession`.** `AutoSyncOnChange` is
  the documented owner of that leg (docs/sync.md path 4) and `components/onboarding/KnownPokemonQuiz.tsx`
  also depends on it, so the hold belongs there, not in the practice component.

Scope kept out, as the issue asks: `streak_days` (`recordReview` at `ReviewSession.tsx:2909`) is not
rolled back, and guest mode is untouched because no cloud write happens at all.

## Risks and unknowns

- **The fix is forward-only.** Grades already undone by existing users are in cloud `grade_log`
  permanently (no DELETE policy) and cannot be identified after the fact, so their sparkline and
  heatmap stay slightly wrong. Worth one sentence in the PR body rather than a data fix.
- **Residual divergence window.** `useOnlineReconnectSync` and `useRetryPush` prefer the persisted
  pending queue, which now contains the held card. They gate on `lastPushFailed`, so they will not
  normally fire during an undo window, but an offline-then-online blip between grade and Undo can
  still transmit the held grade. Narrow and strictly smaller than today's bug; I would document it
  rather than add another guard.
- **`pagehide` flush for `grade_log` is unreliable.** supabase-js does not use `keepalive`, so the
  held grade-log entry can be lost on a hard close. This is the argument for open question 3.
- **`components/onboarding/KnownPokemonQuiz.tsx` also calls `enqueueGrade`** (line 350, in a loop).
  It keeps the immediate path because the hold is opt-in per call, but its grade-log entries route
  through the same `AutoSyncOnChange` handler, so its last entry is held until the page is hidden.
  Harmless, and covered by the catch-up leg if that is included.
- **Test-surface size.** `ReviewSession.test.tsx` is already very large and the mock surface for
  `usePerGradeSync` appears in four test files; expect the mock signature change to ripple.

## Open questions for Fraser

**1. Which direction? (the actual call)**

- **(a) Defer the cloud write until the undo window closes.** No migration, no schema risk, matches
  the original #257 design intent. Cost: the most recent grade is not in the cloud until you grade
  again or leave the page, and a hard kill can lose its `grade_log` row (the card itself survives via
  the persisted queue). Roughly a day of work including tests.
- **(b) Server-side rollback RPC plus grade-log tombstones.** Undo becomes genuinely correct at any
  point, including after a tab switch. Cost: a migration, a SECURITY DEFINER function that is allowed
  to regress `card_reviews`, a tombstone concept in `grade_log` and in `mergeGradeLog`, an
  integration test, and applying the migration to both Supabase projects. Several days, and it
  deliberately weakens the guard that exists because of #293.
- **(c) Accept and disclose.** Leave the behaviour, note in the UI or docs that Undo is local. Nearly
  free, but it leaves a silent data-integrity bug in the FSRS optimiser's input.

**Recommendation: (a).** The user-visible damage is a slightly wrong accuracy chart plus a rare
silently-reverted undo, which does not justify handing the client a sanctioned regression path. If
you want (b) eventually, (a) is not wasted work: it removes most of the cases (b) would have to
handle.

**2. Should Undo be cancelled when the practice page is hidden or left?**

- **(a) Yes.** The invariant becomes "Undo is offered only while the grade is still on this device",
  which is easy to reason about and closes the hide-then-return divergence. Cost: the Undo button
  disappears if you switch tabs and come back, with no explanation.
- **(b) No.** The button stays until the next grade, and a tab switch followed by Undo reproduces the
  original bug in a narrow window.

**Recommendation: (a).** The Undo button is already ephemeral (one grade deep, cleared on reload),
so losing it on a tab switch is consistent with how it already behaves, and (b) keeps a known-wrong
path open on purpose.

**3. Include the grade-log catch-up push in `pullAndMerge`, or file it separately?**

- **(a) Include it here.** About 20 lines inside the existing best-effort grade-log leg. Makes the
  grade-log converge in both directions and covers the `pagehide` flush that supabase-js may drop.
  Also repairs the pre-existing hole where a failed grade-log push is only retried at next sign-in.
- **(b) File a separate issue.** Keeps this PR to one concern; the hole stays open in the meantime
  and is marginally wider than today.

**Recommendation: (a)**, because the deferral is what makes the flush fragile, so shipping the
deferral without the catch-up trades one small data-loss shape for another.
