# Plan: #2051 main has 55 failing tests (localStorage undefined under jsdom)

## What this is

The failure is real, but the issue's premise is not: **`main` is green in CI.** The last push to
`main` (`a95826b3`, 2026-09-10) ran the full `npm test` and passed.

- `.github/workflows/ci.yml:4-5` triggers on `push: branches: [main]`.
- `ci.yml:56-65` forces `code=true` on any non-pull-request event, so the `test` job body always
  runs on a push to `main`.
- `ci.yml:98-106` runs the **full** `npm test` on that path (the `--changed` narrowing is the
  pull-request branch only).
- Run `34469264265` (event `push`, head `a95826b3`): `test` job conclusion `success`.

So the issue's "Why nobody noticed" section is wrong. The suite does run on the default branch. The
reason no CI run showed up when the reporter looked is simply that `main` has had no push since
2026-09-10; everything since is `schedule` / `workflow_run`.

What is actually happening is a **host-Node versus vitest-jsdom interaction that is local to the
machine the suite was run on**, and it silently removes `localStorage` from the test global.

### Mechanism

Vitest's jsdom environment copies jsdom window properties onto the worker's `globalThis` via
`populateGlobal`, then sets `global.window = global`. Which keys get copied is decided by
`getWindowKeys`:

```js
// node_modules/vitest/dist/chunks/index.DC7d2Pf8.js (vitest 4.1.8)
const keysArray = [...additionalKeys, ...KEYS];
return new Set(keysArray.concat(Object.getOwnPropertyNames(win)).filter((k) => {
  if (skipKeys.includes(k)) return false;
  if (k in global) return keysArray.includes(k);   // <-- host global wins
  return true;
}));
```

`KEYS` contains `Storage` (the constructor) but **not** `localStorage` or `sessionStorage`. So:

- On a Node major where `globalThis.localStorage` does **not** exist (Node 24, which `.nvmrc` pins
  and CI uses), `k in global` is false, the key is bridged, and `window.localStorage` is jsdom's.
- On a Node major that **does** define a `localStorage` global, `k in global` is true and
  `keysArray.includes("localStorage")` is false, so the key is dropped. `window.localStorage` then
  resolves to the host global rather than jsdom's, and every consumer reads `undefined`.

This matches the reported 55 failed / 58 passed split exactly. Tests that install their own
in-memory stub via `Object.defineProperty(window, "localStorage", ...)` still pass
(`components/profile/masteredCountCache.test.tsx:44-56`); every test that needs the real jsdom
`Storage` fails, starting with the module-level captures at `masteredCountCache.test.tsx:39` and
`components/qa-seed/apply.test.tsx:51`, plus the direct `window.localStorage.clear()` calls in
`components/pwa/PushOptIn.test.tsx:103` and `components/analytics/FunnelTracker.test.tsx:73`.

### Why the guard did not catch it

`.nvmrc` pins Node 24 and `scripts/check-node-version.mjs` enforces it, but it is wired only as
`preinstall` and `prebuild` (`package.json:9,11`). There is no `pretest`. `npm run pre-pr` is safe
because its `build` step trips the guard, but the loop's verification command
(`npm run lint && npm run typecheck && npm test`) never builds, so it walks straight past it.
`docs/testing.md:65-68` already records "Running under Node 26 produces local-only failures
(#657 / #614)", but only for Playwright.

## Approach

Fix it at the environment-bridge layer, in the setup file, not in the five test files.

```ts
// jsdom's localStorage/sessionStorage reach the test global only through
// vitest's populateGlobal, which skips any jsdom window own-property that the
// host Node already defines and that is absent from vitest's hardcoded KEYS
// list. KEYS has `Storage` but not `localStorage`, so a Node major shipping Web
// Storage globals shadows jsdom's and every consumer reads `undefined` (#2051).
// Bind them explicitly so the jsdom project is host-runtime independent.
const jsdomWindow = (globalThis as unknown as { jsdom?: { window: Window } }).jsdom?.window;
if (jsdomWindow) {
  for (const key of ["localStorage", "sessionStorage"] as const) {
    Object.defineProperty(globalThis, key, {
      value: jsdomWindow[key],
      configurable: true,
      writable: true,
    });
  }
}
```

Three things this depends on, all verified against the installed vitest source:

- `global.jsdom = dom` is set by the jsdom environment's `setup()` before setup files run, so
  `globalThis.jsdom.window` is the real jsdom window.
- `configurable: true` is mandatory. Five test files replace these properties with stubs and then
  `delete` them (`masteredCountCache.test.tsx:46-55`, `qa-seed/apply.test.tsx:124-133`); a
  non-configurable definition would break them.
- Placement inside `vitest.setup.ts` (rather than a separate, earlier `setupFiles` entry) is safe
  because ES imports hoist, and none of the four modules that file imports read `localStorage` at
  module scope (checked: `lib/pokemon/seed.ts`, `lib/pokemon/seed-async.ts` contain no reference).

`tsconfig.json` has no `types` array, so the `jsdom` global is not typed. Cast locally as above
rather than adding `"vitest/jsdom"` to `compilerOptions.types`, which would widen ambient types for
the whole project to fix one line.

### Rejected

- **Rewrite the five test files to stub `localStorage` everywhere.** It would go green and destroy
  coverage. Both files document why the real `Storage` is needed: jsdom's `StorageEvent` constructor
  rejects a non-`Storage` `storageArea` and the write helper swallows the resulting error silently
  (`masteredCountCache.test.tsx:5-8`, `qa-seed/apply.test.tsx:48-50`), so the dispatch assertions
  would pass vacuously.
- **A hard-failing `pretest` guard and nothing else.** It converts a cryptic failure into a legible
  one, which is worth having, but on its own it leaves the automation lane exactly as blocked. That
  lane is what the issue is about. Hence `--warn`, not `exit 1`. See open question 1.
- **Pin or downgrade `vitest` / `jsdom`.** There is nothing to pin back to: `localStorage` has never
  been in vitest's `KEYS` list, and `jsdom` has been at 29.1.1 since before the last green run. The
  variable is the host runtime, not the dependency.
- **A vitest `environmentOptions.jsdom` setting.** No option forces a key into the bridge.

## Risks and unknowns

1. **The premise is inferred, not measured** (see Step 0). This is the one that matters.
2. **Version skew in the evidence.** The `getWindowKeys` source above was read from vitest **4.1.8**
   in the sibling checkout's `node_modules`; `package-lock.json` resolves **4.1.11**. A patch release
   is unlikely to have changed it, but re-read the installed copy before writing the shim.
3. **A throwing host global instead of an undefined one.** Some Node builds expose `localStorage`
   but make access throw without `--localstorage-file`. The reported symptom
   (`Cannot read properties of undefined`) fits shadow-by-undefined, but if the implementer sees an
   `ERR_*` throw instead, it is the same root cause and the same fix, just a different surface.
4. **The shim adds one more way for local and CI to differ.** It papers over a genuine runtime
   mismatch rather than removing it. The `pretest` warning is the compensating control, and the
   `build` step in both `pre-pr` and CI still hard-pins Node 24, so nothing can merge on the strength
   of a Node-26-only green.
5. **`delete window.localStorage` in five test files stays a latent footgun.** It is only safe
   because each test file gets a fresh environment, and `vitest.config.ts` sets no explicit
   `isolate`, so that safety rests on a vitest default. Out of scope here; worth its own issue if
   you want it removed.
6. **A future vitest that adds `localStorage` to `KEYS`** makes the shim redundant. Harmless, but
   the comment should say so, so a later reader knows when it can go.

## Open questions for Fraser

**1. Should `npm test` be runnable on a Node major other than the pinned one?**

- **A. Yes.** Land the shim so the jsdom project is host-runtime independent, plus a non-fatal
  `pretest` warning.
- **B. No.** Treat Node 24 as the only supported test runtime: add a hard-failing `pretest` guard and
  fix whatever runs the loop to use Node 24.

Recommendation: **A.** B is the more principled answer (one runtime, no divergence), but it does not
unblock anything by itself. It turns a cryptic failure into a legible one and still requires a
runtime fix outside this repository. A does both, and costs six lines in a file that already carries
two jsdom shims. The trade-off is that a green local suite could then mask a real Node-26 problem
elsewhere (the esbuild-wasm/Turbopack build break; TS 7 in #1921 is a separate one), which is why the
warning stays and why the build gate keeps its hard pin.
