# Plan: #2058 qa keeps falling behind main: two push-to-main paths have no backmerge, and the drift issue names the wrong cause

## What this is

`qa-drift-check` (`.github/workflows/auto-release.yml:219`) has filed the same tracking issue three times in 60 days, and in every case `qa` was **behind** `main`. The detector is correct; the two things around it are not.

1. Two workflows land commits on `main` with no backmerge into `qa`, so `qa` falls behind by design:
   - `.github/workflows/refresh-user-count.yml:67` pushes `chore(stats): refresh user count` straight to `main` on a daily cron. Confirmed source of #1989.
   - `.github/workflows/auto-release.yml:138` pushes `chore(release): vX.Y.Z` to `main`; the "Reset qa to main" step that would catch `qa` up is gated `github.event_name == 'pull_request'` (`auto-release.yml:165`), so the daily `schedule` safety-net path leaves `qa` behind.
2. The issue body the check writes (`auto-release.yml:301`) explains exactly one cause ("the Reset qa to main step was skipped"), which fitted none of the three occurrences, and its remediation step 3 (`git push origin +origin/main:refs/heads/qa`, `auto-release.yml:306`) destroys un-promoted work whenever `qa` is also ahead.
3. A failed `backmerge-hotfix` run has no signal of its own. Run 33756340840 (Auto Release, `pull_request`, dependabot head branch) is confirmed `conclusion: failure`, and nothing surfaced it except the next morning's generic drift issue.

This is a `.github/workflows/**` change, so per AGENTS.md it needs a `workflow-expert` review with no mechanical-change exemption.

### The constraint that rules out the obvious fix

The issue suggests giving the two push-to-main producers "the same backmerge treatment the hotfix PR path gets". Implemented literally, as a `push: branches: [main]` trigger on the `backmerge-hotfix` job, **it would never fire**. Both producing commits carry `[skip ci]` (`refresh-user-count.yml:66`, `auto-release.yml:136`), and GitHub does not dispatch *any* `push` or `pull_request` workflow for a commit whose message carries that marker. `refresh-user-count.yml:11-15` documents this as the reason the marker is there.

So the backmerge has to happen **inside the producing job**, immediately after it pushes to `main`. That is the central design decision below.

## Approach

**Backmerge in the producing job, via one shared script.** Each of the three paths that puts a commit on `main` calls `.github/scripts/backmerge-main-into-qa.sh` as its last step. All three jobs already mint a `poke-memory-bot` App installation token (required as a bypass actor on the `qa-staging` ruleset), so no new credentials are needed. The script is idempotent: `git merge --no-ff origin/main` on an already-merged `qa` reports "Already up to date", creates no commit, and the subsequent push is a no-op.

*Rejected: a `push: branches: [main]` trigger on `backmerge-hotfix`.* This is the shape the issue suggests and it cannot work: `[skip ci]` on both producing commits suppresses every push-triggered workflow for them. Dropping the marker to make it work would re-fire `ci.yml` and `migration-check.yml` on every daily user-count refresh, which is why the marker exists.

*Rejected: a `workflow_run`-triggered `backmerge-qa.yml`.* This does fire past `[skip ci]` and would centralise the logic in one file. Rejected because `workflow_run` resolves its definition from the default branch only (the same footgun `dependabot-hotfix-label.yml:39-42` documents for `pull_request_target`), it runs on every producer completion including no-ops, and it detaches the failure from the run that caused it. The in-job step keeps cause and signal in the same run.

*Rejected: retargeting `refresh-user-count.yml` to `qa`.* See open question 3.

**Classify the drift, do not assume it.** Once `main` is not an ancestor of `qa`, `BEHIND > 0` is guaranteed by construction, so the issue's suggested "`ahead > 0 && behind == 0` means the reset was skipped" case is unreachable and splitting purely by direction does not work. What distinguishes the causes is *what the main-only commits are*, not the counts. So the new body prints `git log --format='%s' origin/qa..origin/main` verbatim and labels it:

- all subjects match `^chore(stats): refresh user count` → the user-count producer,
- any subject matches `^chore(release): v` → the release commit (reset skipped, or the schedule-path gap),
- anything else → a hotfix PR whose backmerge failed, with a link to the most recent failed Auto Release run.

Remediation is then keyed on `AHEAD`, which is what makes it safe:

- `AHEAD == 0` → `qa` has no unique commits; a fast-forward (`git push origin origin/main:refs/heads/qa`, no `+`) is lossless. Offer that.
- `AHEAD > 0` → offer the merge **only**, and state the count of commits a force-reset would discard. Never print the force-reset command in this case. This is the #2044 hazard (6 ahead, 1 behind) removed at source.

**Keep the drift check alert-only for now.** Whether it should start healing the lossless case is open question 1, not a decision to take here.

## Testing

The changed surface is entirely `.github/**` shell and YAML, so no vitest project covers it and the diff-coverage gate (changed *product* lines) does not apply. Proof comes from three layers.

1. **Script unit tests**, run directly per the repo's existing convention (`bash .github/scripts/<name>.test.sh`):
   - `classify-qa-drift.test.sh`: subjects-in/label-out for user-count-only, release-only, mixed, hotfix/unknown, and empty input. The empty case matters because it is the "main is an ancestor after all" state.
   - `backmerge-main-into-qa.test.sh`: build a throwaway repo with a local bare `origin`, then assert (a) a clean merge produces a merge commit and pushes, (b) a conflicting change on both branches exits non-zero without pushing, (c) an already-merged `qa` exits 0 with no new commit.
   - Note honestly: these `*.test.sh` files are **not wired into CI** today (nothing in `package.json` or `ci.yml` runs them; `parse-closing-refs.test.sh` is invoked by hand). Wiring them into the `lint` chain is a reasonable extra, but it is scope beyond this issue and should be its own change.
2. **Workflow-shape review**: `workflow-expert` on the full diff, mandatory per AGENTS.md, with specific attention to the `needs: release` plus `if: always()` combination (getting that wrong silently skips the drift check on exactly the days the release job fails, which is when it is most needed).
3. **Live verification after merge**, which is the only thing that proves the real credentials and rulesets work:
   - `gh workflow run "Refresh user count badge"` once the file is on `main`, then confirm `git merge-base --is-ancestor origin/main origin/qa` passes and a merge commit landed on `qa`.
   - The release-path backmerge cannot be dry-run: a `workflow_dispatch` with no changelog fragments sets `skip=true` and the new step is gated off it. It is first exercised by the next real scheduled cut. Flagged under risks.
   - To exercise the failure signal deliberately, push a conflicting one-line change to `qa`, dispatch the refresh, and confirm a marker-keyed issue opens with the conflicting path named; then resolve and confirm the next run closes it.

## Risks and unknowns

- **The release-path backmerge ships unexercised.** There is no way to trigger it without cutting a real release. Mitigation: the same script is exercised daily by `refresh-user-count.yml` and on every hotfix merge, so the shared code is well covered even though that one call site is not.
- **`fetch-depth: 0` on `refresh-user-count.yml`** turns a shallow daily clone into a full one. Cheap for this repo, but it is a real change to a job with a 3-minute timeout (`refresh-user-count.yml:30`). Worth watching the first few runs.
- **Lockfile conflicts will recur.** `dependabot.yml` targets `qa` for version updates and `main` for security updates, and both touch `package.json` / `package-lock.json`. That is the structural generator behind the #2044 failure, and this change makes the failure *visible* rather than *rarer*. See open question 2.
- **One shared failure marker across three producers** means a success from producer A closes an issue producer B opened. In practice a successful merge catches `qa` up for all of them, so the next run of B succeeds too. Acceptable, but it is a deliberate simplification.
- **Push races.** If something else pushes to `qa` between the script's fetch and its push, the push is rejected and the job fails. That is now a filed issue rather than a silent gap, which is the intended behaviour, but it is a new source of red runs.
- **Not verified:** the current live `main`/`qa` divergence. `git fetch` and the compare API call were both refused under this session's permission profile, so the numbers in the issue body (#2044 at 6 ahead / 1 behind) are taken as reported. Everything else above was read from the files or confirmed via `gh run view 33756340840`.

## Open questions for Fraser

**1. Should `qa-drift-check` start auto-healing the provably lossless case?**

- **(a) Stay alert-only** (today's behaviour, and a deliberate one per `auto-release.yml:226-229`).
- **(b) Auto fast-forward `qa` to `main` when `AHEAD == 0`, alert otherwise.**

*Recommendation: (b).* When `qa` has zero unique commits a fast-forward cannot lose work, and this is precisely the #1989 shape that sat open for 22 days. Once producers 1 and 2 are fixed, the residual `AHEAD == 0` case is almost always "a backmerge failed", which a human then fixes by hand anyway. *Trade-off:* the job today is deliberately read-only (`contents: read`, `GITHUB_TOKEN`, no push). (b) gives it `contents: write`, an App token and `qa-staging` bypass, so a bug in it can now move a branch. That is a meaningful widening of blast radius for a monitor.

**2. Should the backmerge auto-resolve `package-lock.json` conflicts?**

- **(a) Fail loudly and file the issue** (what this plan implements).
- **(b) On a lock-only conflict, take `main`'s `package.json` and regenerate the lock with `npm install --package-lock-only`.**

*Recommendation: (a), for now.* A silently regenerated lockfile can shift resolved versions nobody reviewed, and on the security-update path that is exactly the wrong place to be casual. *Trade-off:* given the dependabot split across both branches, (a) means recurring manual conflict resolution on a predictable cadence. Ship (a), see the rate over a month, and revisit.

**3. Should `refresh-user-count.yml` keep pushing to `main` at all?**

- **(a) Keep pushing to `main`, add the backmerge** (what this plan implements).
- **(b) Retarget the commit to `qa` and let normal promotion carry it to `main`,** repointing the README badge URL from `.../main/.github/stats/users.json` to `.../qa/...` (`README.md:4`).

*Recommendation: (a).* (b) genuinely removes a push-to-main producer, but it adds a daily noise commit to `qa` that then appears in every promotion PR diff, and it makes a production-facing badge read its value from the staging branch. *Trade-off:* (a) leaves `main` with two automated producers that must each remember to backmerge, which is the class of bug this issue is about. If you would rather shrink the producer set than harden it, say so and I will plan (b) instead.
