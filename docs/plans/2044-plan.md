# Plan: #2044 qa branch has drifted from main

## What this is

The drift is real, but the issue body guesses the wrong cause. The auto-release "Reset qa to main" step was not skipped. Two Dependabot **security** PRs were merged straight into `main` as `hotfix`es, and the `backmerge-hotfix` job in `.github/workflows/auto-release.yml` failed both times on merge conflicts:

| Hotfix on main | Merged | Backmerge run | Result |
|---|---|---|---|
| #2042 browserslist 4.28.2 -> 4.28.7 (`8b1e0c4b`) | 2026-09-03 | 33756340840 | `CONFLICT (content)` in `package.json` and `package-lock.json` |
| #2062 joi 18.2.1 -> 18.2.8 (`a95826b3`) | 2026-09-10 | 34469264706 | same two conflicts |

Meanwhile `qa` picked up its own dependency bumps for the same files: #2036 (browserslist 4.28.8), #2034, #2032, #2040, #2039 and #2070, plus the successful #2041 backmerge. So `main` is 2 commits ahead of `qa` and `qa` is 7 ahead of `main`. `qa` has un-promoted work, so **the issue's step 3 (reset qa to main) would throw away six dependency bumps and must not be used.**

State checked from local `origin/*` refs, which match the SHAs in the issue (`main` `a95826b3`, `qa` `6a6b2104`):

- **`package.json`:** the conflict is only textual. Both sides now say `"browserslist": "^4.28.8"`. The conflict comes from qa's `@vitest/coverage-v8` bump on the line next to it. qa's version is the correct result.
- **`package-lock.json`:** this is where the real differences are. `main` has six entries that are newer than qa's:

  | Package | main | qa |
  |---|---|---|
  | `joi` (dev, via `wait-on`) **security fix from #2062** | 18.2.8 | 18.2.1 |
  | `baseline-browser-mapping` | 2.11.20 | 2.11.16 |
  | `caniuse-lite` | 1.0.30001810 | 1.0.30001809 |
  | `electron-to-chromium` | 1.5.420 | 1.5.411 |
  | `node-releases` | 2.0.54 | 2.0.53 |
  | `update-browserslist-db` | 1.3.2 | 1.3.1 |

  `browserslist` itself already resolves to 4.28.8 on both branches, and the nested `@serwist/turbopack/node_modules/browserslist` 4.28.2 entry exists on both.

- **Promotion PR:** none is open. `gh pr view qa` returns #2009, which is already merged.

This work is a one-off reconciliation PR into `qa`. Whether to also fix the recurrence is a scope call (see Open questions).

## Files to change

- `package-lock.json`: the merge resolution. Take qa's side, then copy in main's newer `version` / `resolved` / `integrity` for the six packages above. For `node-releases`, also take the new `engines: { node: ">=18" }` block. This keeps the joi security fix that a qa-side resolution would lose.
- `package.json`: resolve to qa's side. The net diff against `origin/qa` should be empty.
- No changelog fragment. Everything touched is a devDependency or build-data package, main's own hotfixes had no fragment, and `changelog-gate.yml` only checks `app/**`, `components/**` and `lib/**`.
- No workflow, `WORKFLOW.md` or `.claude/commands/batch-issues.md` changes in this PR, unless Fraser picks option (b) in question 1.

## Approach

1. `git fetch origin`, then branch `chore/2044-reconcile-qa-with-main` off `origin/qa`.
2. `git merge --no-ff origin/main` with **no** `-X` strategy. Expect conflicts in exactly `package.json` and `package-lock.json`, the same as the two failed runs. If anything else conflicts, stop: more has landed on `main` since this plan was written.
3. `package.json`: `git checkout --ours package.json`.
4. `package-lock.json`: `git checkout --ours package-lock.json`, then copy the six entries from `git show origin/main:package-lock.json` word for word. These are separate blocks, and none of their dependency ranges changed in a way qa's `browserslist` 4.28.8 block doesn't already allow.
5. Under Node 24 (`.nvmrc`; this machine defaults to v26, so put `/opt/homebrew/opt/node@24/bin` first on `PATH`), run `npm ci`. It fails on a lockfile/`package.json` mismatch or a bad integrity hash, so it checks the hand edit. Then run `npm run pre-pr`.
6. Commit the merge, then `git push origin chore/2044-reconcile-qa-with-main` and `gh pr create --base qa --head chore/2044-reconcile-qa-with-main`. Put `Refs #2044` in the body, not `Closes`: a PR into `qa` doesn't auto-close issues, and the `qa-drift-check` job closes #2044 itself on its next daily run.
7. Run the `code-reviewer` pass (AGENTS.md: nothing reviews PRs automatically any more).
8. Merge with a **merge commit, not squash**. A squash drops the `main` parent, so the drift would remain. Precedent: #2005 (`a0c75771`) and #1663.

**Rejected:**

- **Issue step 3, reset qa to main:** this destroys #2036, #2034, #2032, #2040, #2039 and #2070.
- **The `batch-issues.md` recipe (b), `git merge -X ours origin/main`:** it would mark `main` as merged but quietly keep qa's joi 18.2.1. Its safety check (`git diff --quiet HEAD origin/qa`) would pass, which gives false confidence. That recipe only works when qa already contains everything main has, which isn't true here.
- **Recipe (a), reset qa and cherry-pick:** a force-push rewrite of `qa` needs admin rights, and it still needs the same lockfile resolution.
- **`npm update <six packages> --package-lock-only` instead of copying entries:** it pulls versions newer than either branch, so the merge commit would carry new, unreviewed bumps. Keep it only as a fallback if `npm ci` rejects the copied entries.
- **Deleting and regenerating the whole lockfile:** every transitive dependency would float.
- **Pushing the merge straight to `qa` with the admin bypass:** that skips `test` and `e2e` on the merged lockfile.

## Testing

- **Ancestry:** `git merge-base --is-ancestor origin/main HEAD` exits 0. This is the exact check `qa-drift-check` runs (`auto-release.yml:258`).
- **Scope of the diff:**
  - `git diff origin/qa -- package.json` is empty.
  - `git diff --stat origin/qa HEAD` lists only `package-lock.json`.
  - That lockfile diff touches only the six entries.
- **Nothing from main is lost:** a one-off, uncommitted node snippet reads the `packages` maps from `git show origin/main:package-lock.json` and from the resolved lockfile, and asserts that every key in main is present in the result at a version no lower than main's.
- **Install is consistent:** `npm ci` succeeds under Node 24.
- **Advisory is gone:** run `npm audit` on `origin/qa` and on the merge result. The joi advisory behind #2062 is reported on the first and not on the second.
- **Local gate:** `npm run pre-pr` passes. No product lines change, so diff coverage passes trivially.
- **CI:** `test` and `e2e` pass on the PR. `ci.yml`'s `e2e_relevant` filter includes `package-lock.json`, so both genuinely run rather than skipping.
- **After merge:** the next scheduled `qa-drift-check` run logs "qa is healthy" and closes #2044. Do not trigger `auto-release.yml` manually to hurry this: `workflow_dispatch` also runs the `release` job, which cuts a release if `main` has any unreleased fragments.

## Risks and unknowns

- **Open PRs into `qa` are unknown.** This lane isn't allowed to run `gh pr list` or `gh api`. Any open `qa` PR that touches `package-lock.json` (for example Monday's Dependabot run) will conflict after this merges. Check at implementation time, and merge this first.
- **More hotfixes may land on `main` first.** Before merging, re-run the ancestry check against a fresh `origin/main`. If it fails, merge `main` in again.
- **This will happen again.** Every Dependabot security PR is labelled `hotfix` and merged to `main` (`dependabot-hotfix-label.yml`). Any of them that touches `package-lock.json` while qa has its own lockfile bumps will fail `backmerge-hotfix` the same way. The failure only shows up as a red run, and the drift issue that follows then blames the wrong cause.
- **The drift issue's instructions are unsafe for this case.** Its step 3 discards un-promoted work. Its step 2, followed by the `-X ours` habit from `batch-issues.md`, drops main's lockfile content.
- **The `node-releases` 2.0.54 entry needs Node >= 18.** Node 24 in CI and `.nvmrc` satisfies it.

## Open questions for Fraser

1. **Scope of this PR: reconciliation only, or harden the drift path as well?**
   - **(a)** Reconciliation-only PR as above, plus two follow-up issues:
     - `backmerge-hotfix` should open or update the drift tracking issue when the merge conflicts, naming the conflicting files and the hotfix PR.
     - The drift issue body, `WORKFLOW.md:807` and `batch-issues.md:70` should name a failed hotfix backmerge as a cause, and warn that step 3 and `-X ours` can lose work.
   - **(b)** Do the reconciliation and the hardening in one PR.
   - **Recommendation: (a).** Unblocking the next promotion is a data-only change that CI can check. Workflow YAML needs a `workflow-expert` review (AGENTS.md) and doesn't belong inside a merge-commit PR. Your default is also to file an issue. The trade-off is that the misleading issue text and the silent backmerge failure stay in place until the follow-up lands.
2. **Should Dependabot security updates for devDependencies keep going straight to `main`?** Both #2042 and #2062 were `chore(deps-dev)`, so they never ship to production, yet they took the `hotfix` path and caused this drift.
   - **(a)** Keep the current path and accept a manual reconciliation like this one every time a lockfile conflict happens.
   - **(b)** Narrow `dependabot-hotfix-label.yml` to runtime `dependencies` only. Dev-only security PRs would then stay blocked by `Restrict main PR source`, and the bump gets redone on `qa` to ride the next promotion.
   - **(c)** Teach `backmerge-hotfix` to auto-resolve lockfile conflicts. This is risky: an automated resolution can drop a security bump the same way `-X ours` would.
   - **Recommendation: (b), tracked as its own issue.** For dev-only packages, the extra time before a fix reaches `main` costs nothing in production, and it removes the most common source of this drift. The trade-off is a manual step per dev-only advisory, plus deciding how the security PRs stuck on `main` get closed.
