That leaves three pieces of work reachable from this ticket, in descending confidence:

1. **A verified defect in the current tree.** The dedupe added by #2003 does not work. Its
   `gh issue list --search "$MARKER in:body"` pre-filter returns nothing, so the next firing
   will open a sixth duplicate rather than commenting on #2031. This is the exact failure
   `cron-health-monitor.yml` documents at lines 77 to 88 (#1919): the GitHub search index
   strips HTML comments, and the marker's colon parses as an unknown search qualifier.
   Confirmed empirically against live GitHub:

   ```
   $ gh issue list --state open --label monitoring --limit 50 \
       --search '<!-- monitor:grade-log-divergence --> in:body' --json number --jq '[.[].number]'
   []                                              # the shipped form: finds nothing
   $ gh issue list --state open --limit 100 --json number,body \
       --jq '[.[] | select(.body | contains("<!-- monitor:grade-log-divergence -->")) | .number]'
   [2031]                                          # the jq form: finds it
   ```

   #2031 does carry the marker in its body, so this is not a "no marked issue exists yet"
   artefact.

2. **The monitor's graduation test is a proxy, and a better signal now exists.** Options A and
   C both approximate "this card graduated" as `MAX(grade) >= 4`. That was the best available
   signal when #1253 and #1357 were written. It is wrong for a card sitting in FSRS learning
   steps: `lib/srs/scheduler.ts:317-326` (case B3 advance) takes a Good at a non-final step,
   increments `learningStep` and leaves `lastReview` null, so `isSyncSafe()`
   (`lib/sync/cloud.ts:92`) keeps blocking the upsert. With `HARD_LEARNING_STEPS` at three
   steps (`lib/srs/constants.ts:24`) and B1 resetting to step 0 on any Again, a card can
   collect Goods across several days without ever graduating. That is precisely the shape the
   Option C copy in #2002 warns about, and it fits the observed data.

   Migration 033 (`db/migrations/033_grade_log_learning_step.sql`, landed 2026-05-30) added
   `grade_log.learning_step`, written post-grade from `nextState.learningStep` at
   `components/review/ReviewSession.tsx:2918`, with `NULL` meaning "graduated at grade time".
   That is an exact graduation signal, and the monitor does not use it yet.

3. **Bookkeeping.** #1999, #2000, #2001, #2002 and #2031 are five open issues describing one
   cleared condition.

## Approach

**The dedupe fix.** Drop `--search`, pull the open issue list once with `--json number,body
--limit 100`, and match the marker with `jq`'s `contains`. Keep `set -euo pipefail` and no
`2>/dev/null`, so a `gh` failure surfaces as a failed run rather than looking like "no
existing issue" and filing a duplicate. This is a straight port of a pattern already proven in
this repo, and both the broken and the fixed form are verified above against live GitHub. I
rejected keeping `--search` with a quoted or non-comment marker: the search index behaviour is
the problem, and #1919 already paid for that lesson once.

**The graduation predicate.** Replace the proxy with the exact signal:

```sql
-- was: AND MAX(grade) >= 4
   AND bool_or(learning_step IS NULL)
```

`learning_step IS NULL` means the card was graduated immediately after that grade, so
`isSyncSafe()` returned true and a `card_reviews` row was owed. It is more accurate in both
directions:

- Removes a false positive: an in-step card graded Good at a non-final step no longer matches.
  This is the class that produced #1999 to #2002 and #2031, if the historical hits were benign.
- Removes a false negative: an already-graduated card graded only Hard (case A4, `learningStep`
  stays null) is sync-owed but never reaches `MAX(grade) >= 4`, so it is invisible today.

I rejected the two obvious alternatives. Widening the grace window (the reflex the #1357
comment explicitly forbids) recreates the blind spot Option C exists to cover. Raising
`DIVERGENCE_THRESHOLD` above 0 mutes a genuine signal and the script's own header says not to.

**Option A becomes redundant.** Worth stating plainly, because it is a design consequence
rather than a side effect. A and C share grouping keys and the same 4-day floor; A only adds
`HAVING MAX(entry_date) <= today - 2`. So A's result set is already a strict subset of C's,
today and after this change, which the observed data confirms: A has never fired without C.
A's remaining value is as an age signal ("this orphan has persisted 2+ days"), not as a
detector. Whether to keep it is Open question 1.

**Sequencing.** The dedupe fix stands alone and should land first, since it is a verified
defect. The predicate change is independent of it.

## Risks and unknowns

- **The root cause is still unclassified, and I could not classify it from here.** This session
  has no Supabase MCP access, so I could not query prod. The two candidate explanations produce
  identical monitor output: (a) a card genuinely stuck in learning steps with a Good in its
  history, which is benign and which the predicate change silences; (b) a transient real break
  where the `grade_log` push landed but the `card_reviews` push failed, healed by a later
  session. If it was (b), this plan improves the monitor but fixes no sync bug. The
  discriminating query, to run against prod before or alongside the change:

  ```sql
  SELECT subject_key, card_type, entry_date, grade, learning_step
  FROM grade_log
  WHERE user_id::text LIKE 'dff21628%'
    AND entry_date BETWEEN '2026-08-09' AND '2026-08-22'
  ORDER BY occurred_at;
  ```

  Any row with `learning_step IS NULL` for the flagged subject means it did graduate, which
  points at (b) and a real dropped write. All rows non-null means (a), benign, and the
  predicate change is the whole fix. I would run this first; it is cheap and it decides whether
  a follow-up issue is needed.
- **Pre-033 rows read as graduated.** `learning_step` was backfilled NULL by design, so a row
  written before 2026-05-30 is indistinguishable from a graduated one. Irrelevant at a 4-day
  look-back today, but it makes the predicate unsafe if anyone later widens
  `OPTION_A_LOWER_BOUND_DAYS_AGO` past that date. Worth a comment in the query, not a guard.
- **This is the fifth round of tuning on these queries** (#1221, #1229, #1253, #1357). Each
  round silenced a false-positive class and each was defensible. The honest risk is that
  tightening again trades a real detection for quiet. The `learning_step` predicate is
  narrower on one axis and wider on another, which is why case 5 above matters: if it does not
  pass, the change is a net loss of coverage and should not ship.
- **Clean for 14 days is not proof of benign.** The same user could simply not have reviewed
  that card. The predicate change does not depend on this either way.

## Open questions for Fraser

**1. Now that A is provably a subset of C, keep Option A or retire it?**
- *Keep it* (recommended): the alert body gains a persistence signal. "A and C both fired"
  means the orphan is at least 2 days old, which is the difference between "look today" and
  "look this week". Cost is one extra query per tick and a monitor with a redundant arm to
  explain.
- *Retire it*, leaving B and C: less to keep in sync, and the arms stop overlapping. Cost is
  losing the age signal unless C's markdown starts reporting `last_entry_date`.
- Trade-off: keeping A buys triage information for a query that can never fire alone. Retiring
  it is cleaner but loses the loudest-signal semantics the alert body currently relies on.

**2. Should a clean run auto-close the open alert issue?**
- *Yes* (recommended): `cron-health-monitor.yml:248-253` already does this, so it is an
  established pattern here, not a new one. It would have closed #1999 to #2002 on Aug 17 by
  itself. Add a step gated on `steps.check.outputs.alert == 'false'` that finds the marked
  issue and closes it with a "clean for N consecutive runs" comment.
- *No*: an intermittent divergence (exactly what we have) would open and close repeatedly, and
  a self-closing issue can hide a problem that is oscillating rather than fixed.
- Trade-off: auto-close removes stale-issue noise but makes the flapping pattern harder to
  see, which is the one thing the run-log table above made obvious. A middle option is to close
  only after N consecutive clean runs (3 would have held #2002 open through the Aug 21
  recurrence), at the cost of persisting a counter somewhere.

**3. Migration 032's reconciler uses the same proxy. Fix it here, or file a follow-up?**
`db/migrations/032_reconcile_grade_log_orphans.sql:154` heals orphans selected by
`HAVING MAX(n.grade) >= 4`, the same imprecise test. If it is ever flipped from dry-run to
live (#1360's deferred manual step, and I cannot check prod's current cron state from here), it
would insert a placeholder `card_reviews` row with `fsrs_state = 'review'` for a card still in
learning steps, which is a write of wrong state to a table with no PITR (#298).
- *Follow-up issue* (recommended): it needs a migration, an integration test, and confirmation
  of the live cron state, which is a different change from a monitoring fix, and AGENTS.md
  prefers one issue per change.
- *Fix in the same PR*: the two proxies stay consistent and there is no window where the
  monitor and the healer disagree.
- Trade-off: bundling keeps them aligned but puts a production migration in what is otherwise a
  zero-risk monitoring PR.

#2031, keep #2031 as the single tracking issue, and close it when the predicate change lands.
Say the word and I will do it, or leave them if you would rather they close themselves under
