# Plan: #2074 Playwright image is pinned to v1.60.0 in six workflows, so the Dependabot bump to 1.62.1 (#2035) fails every browser job

## What this is

Playwright's version is recorded in two places that must agree: the lockfile and the `mcr.microsoft.com/playwright` container tag. Dependabot only moves the lockfile. This change does two things:

1. Lands 1.62.1 properly: package bump plus every image tag in the same PR.
2. Adds a drift check, in the style of `node-version-drift.yml`. The next half-done bump will then fail with a named error that lists every `file:line` to fix.

Checked on 2026-09-17 against this branch (which is `origin/qa` head `6a6b2104`):

- The locked version is 1.60.0 for `@playwright/test`, `playwright` and `playwright-core` (`package-lock.json:2806`, `:11336`, `:11355`).
- #2035 is still open. It touches only `package.json` and `package-lock.json`, and has not been updated since 2026-08-24.

The plan below follows the pin-and-check approach that the issue suggests. The one real direction call is whether to pin the tag at all or derive it at run time. It is under Open questions, and the plan works as written if you take the recommendation.

## Approach

**One PR off `origin/qa` that replaces #2035**, rather than a commit pushed onto Dependabot's branch.
- Once someone else pushes to a Dependabot branch, Dependabot stops rebasing it, and a manual push onto a bot branch is the kind of shared-state change the house rules ask about first.
- A fresh PR carries the same package diff, so Dependabot should close #2035 itself once `qa` already has 1.62.1.

**Implementation order.** The order proves the check against the real failure before fixing it:
1. Branch off `origin/qa` and fetch first.
2. Verify the image: see Risks 1 and 2.
3. Bump the package.
4. Write the helper, tests and CLI. Run the CLI and confirm it fails, listing every stale site above.
5. Move the tags and remove the versions from the prose. Run the CLI again: it now passes.
6. Add the workflow file and get the `workflow-expert` review, which is mandatory for any `.github/workflows/**` change.
7. Run `npm run pre-pr`, then `./scripts/pre-pr-smoke.sh`.
8. Open the PR: `gh pr create --base qa --head <branch>`, with `Closes #2074` and a note that it replaces #2035.
9. Run `code-reviewer`. Nothing reviews PRs automatically any more.

**Why a standalone path-filtered workflow rather than another step in `npm run lint`.**
- It matches the `node-version-drift.yml` precedent the issue asks for.
- A Dependabot PR shows a check named "Playwright version drift check" in the list. A lint step would show up only as a red `test` whose log you have to open.
- I am not proposing it as a required check. A path-filtered workflow set as required leaves unrelated PRs waiting forever on a check that never runs, and the required `e2e` check already blocks the merge.

**Why an explicit scan list rather than a repo-wide grep.** A repo-wide scan would flag historical mentions in `CHANGELOG.md`, `changelog.d/` and `docs/plans/` (this file included) that must never be rewritten.

**Why remove the versions from prose.** Fewer copies to move on each bump: the literals stay only where something runs them (six `image:` lines, `pre-pr-smoke.sh` and two documented `docker run` commands). The checker still scans the prose files, so a literal that creeps back in is caught.

**Rejected alternatives**
- A bot workflow that pushes the tag commit onto Dependabot branches. It needs `pull_request_target` with a write token on bot-authored branches, and it still stops Dependabot rebasing the PR. Too much risk for a roughly monthly chore.
- Deriving the tag at run time. This is a real option, not a rejected one: see Open questions.

## Risks and unknowns

1. **The `v1.62.1-noble` tag is not yet confirmed as published.** This run could not reach the registry: `curl` and WebFetch to `mcr.microsoft.com/v2/playwright/tags/list` were both refused. The implementer must confirm it first, with `docker pull mcr.microsoft.com/playwright:v1.62.1-noble` or that tags list.
2. **The Node major inside the new image must be 24.**
   - `preinstall` and `prebuild` both run `scripts/check-node-version.mjs`, which requires an exact match with `.nvmrc` (24).
   - All six jobs run `npm ci` inside the container, so a different Node major in the image would fail every one of them at install.
   - Check with `docker run --rm mcr.microsoft.com/playwright:v1.62.1-noble node --version`.
   - If it is not 24.x, stop and raise it: that is a Node-policy decision, not part of this fix.
3. **A newer browser build can move rendering and timings.** Visual baselines may need regenerating (see Testing). The Perf budget is not required, but its thresholds could shift. Treat a Perf budget failure as something to investigate, not a reason to raise the thresholds.
4. **#2035 may not close itself.** Dependabot normally closes a PR once the base branch already has the version, but if #2035 lingers, closing it is a GitHub mutation that needs your OK.
5. **A newer Playwright may be out by implementation time.** Stick to 1.62.1 so this PR supersedes #2035 cleanly. Dependabot's next PR will then be the first live test of the new check.
6. **Future Playwright bumps will still arrive red** under this approach. The failure will be a clear, named one, but a person still has to commit the tag move. That is the trade-off behind the open question below.
7. **Stale wording spotted in lines this change edits.** `WORKFLOW.md:281` and `:292` say the baseline regeneration commit carries `[skip ci]`. `visual-baseline-update.yml:37-48` and `:233` show that marker was dropped (#1145). Fix the wording while editing those lines.
8. **The workflow edits are mechanical but still need the mandatory `workflow-expert` review** (AGENTS.md file-ownership table, #1859/#1815/#1806).

## Open questions for Fraser

**Q1. Keep pinned image tags plus a drift check, or derive the tag from `package-lock.json` at run time?**

- **Option A: pin and check.** This is the issue's suggestion and the plan above.
  - For: a small, readable diff.
  - For: the tag edit touches `visual-regression.yml`, so each Playwright bump PR runs the baseline comparison.
  - Against: every Playwright bump, roughly monthly, still needs a person to commit the tag move on top of Dependabot's change. Until then the Dependabot PR stays red, although now with a named reason.
- **Option B: derive at run time.**
  - How it works:
    - A job each workflow already has (`changes` in `ci.yml` and `perf-budget.yml`, `decide` in `visual-regression.yml`, `gate` in `visual-baseline-update.yml`) reads the locked version and outputs it. `e2e.yml` would need a new small job for this.
    - Each Playwright job then uses `image: mcr.microsoft.com/playwright:v${{ needs.<job>.outputs.playwright_version }}-noble`.
    - The drift check changes to flag any literal tag in a workflow, as `node-version-drift` does for `node-version:`.
  - For: a Dependabot bump goes green without anyone touching it, as long as the image is published.
  - Against:
    - A larger YAML change across five files and six jobs.
    - It relies on the `needs` context being available in `jobs.<id>.container`. GitHub's context-availability table lists it, but `workflow-expert` should confirm that before we rely on it.
    - It quietly loses visual coverage on bumps: `visual-regression.yml` skips Dependabot PRs (`:61`) and does not filter on `package-lock.json`. The browser change would then surface as a baseline failure on the next unrelated UI PR.
    - A bump that lands before the image is published fails with an image pull error.
- **Recommendation: A now.** It fixes #2035 with the smallest reviewable change and keeps baseline comparison on every bump. B could be a follow-up once Playwright bumps can force a visual-regression run.
