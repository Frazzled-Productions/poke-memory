## Approach

**The decision I am making:** report the issue as a false positive rather than manufacture a
change for it. A plan that invents a Next.js bump for a repo already on 16.3.1 would be
actively harmful, because it reads as authoritative and would produce a no-op PR.

**What I rejected:**

- *Bumping `next` anyway, to 16.3.1 or later.* Rejected: `main` is already there. Bumping past
  16.3.1 would be an unrelated dependency-currency change, not this issue, and Dependabot owns
  that lane already (weekly Monday, `next` group, `.github/dependabot.yml`).
- *Reopening or rebasing #1983.* Rejected: it is closed, `CONFLICTING`, and every advisory it
  carried is already resolved on `main` via #2006 and `a33e3755`.
- *Fixing the Porter monitor's stale-ref read.* Rejected as out of repo scope, per the grep
  above. Worth a note to Fraser regardless, since this is the same failure mode as the standing
  "investigate against origin, not stale local" lesson.

**The design, if option B or C is chosen.** Add a `promotion-staleness-check` job to
`auto-release.yml`, cloned structurally from `qa-drift-check` (lines 219-320), which is already
a proven marker-keyed, alert-only, self-closing tracking-issue pattern in this repo:

- Gate it to `github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'`,
  matching `qa-drift-check:236`, so it never races the `pull_request` promotion path.
- Compute the age of the oldest un-promoted commit:
  `git log origin/main..origin/qa --format=%ct | tail -n1`. Unhealthy when that commit is older
  than a threshold and the range is non-empty.
- **Threshold: 7 days.** This is a HOW call I am owning, with a stated rationale: `auto-release`
  runs daily and Dependabot opens its batch weekly on Monday, so "un-promoted for 7 days" means
  a full Dependabot cycle has been staged on `qa` and never reached production. Trivially
  tunable as a single constant.
- Dedup with an HTML marker (`<!-- promotion-staleness-check -->`) matched locally with `jq`
  over `gh issue list --json number,body --limit 100`. **Do not use `gh issue list --search`**:
  the GitHub search index strips HTML comments, which is the documented cause of #1919 and is
  called out in the comments at `cron-health-monitor.yml:77-88` and `auto-release.yml:264-271`.
- Close the tracking issue automatically when the range empties, mirroring
  `qa-drift-check:276-284`. **This is the property #2012 itself lacked**: a Porter-filed issue
  with no self-close stayed open for 17 days after the underlying problem was fixed.
- Permissions `contents: read` + `issues: write`, `GITHUB_TOKEN` only, no App token, matching
  `qa-drift-check:237-239`.

Per AGENTS.md's file-ownership table, **any** `.github/workflows/**` change gets a
`workflow-expert` review with no mechanical-change exception, so that review is a required step
of the implementation, not optional.

## Testing

Under the recommended answer, there is nothing to test: the verification is the evidence table
above, and it is already done. It is reproducible with these exact commands from the worktree:

```
git show origin/main:package.json      | grep -nE '"(next|eslint-config-next)"'
git show origin/main:package-lock.json | grep -n -A2 '"node_modules/fast-uri"'
gh pr view 2009 --repo Frazzled-Productions/poke-memory --json mergedAt,baseRefName,headRefName
gh pr view 1983 --repo Frazzled-Productions/poke-memory --json state,mergeStateStatus,closedAt
```

If option B or C is chosen, the workflow job is shell inside YAML and is not reachable by
`vitest`, so it is tested the way this repo already tests its other monitor jobs:

1. **`workflow_dispatch` on a healthy repo.** `main` is currently 1 commit *ahead* of `qa`, so
   the `origin/main..origin/qa` range is a good live case. Assert the job logs healthy, opens
   nothing, and closes nothing.
2. **`workflow_dispatch` with the threshold temporarily set to 0 on a branch.** Forces the
   unhealthy path. Assert exactly one issue opens, carrying the marker.
3. **Re-dispatch while still unhealthy.** Assert it edits issue N in place and does **not** open
   a second one. This is the specific regression #1919 was, and it is the only failure mode that
   matters for a marker-dedup job.
4. **Restore the threshold and re-dispatch.** Assert the tracking issue auto-closes.
5. `npm run lint` (the chain includes `lint:agents-size`) if `WORKFLOW.md` gains a catalogue row.

No `npm run pre-pr` gate run is needed for a workflows-plus-docs diff beyond lint, since no
product line changes and diff coverage has nothing to measure.

## Risks and unknowns

- **Highest-value finding, and it is outside this repo.** The Porter loop compared a five-day-old
  local checkout against live npm publish dates. Nothing I change in `poke-memory` prevents that
  recurring, and it will recur on any issue where the loop reasons about branch state. It also
  produced an issue with no self-close, so it stayed open 17 days past its own resolution. Both
  properties are harness bugs, and both are worth a fix wherever the loop's code actually lives.
- **The detector might be pure noise.** If Fraser routinely leaves `qa` unpromoted for over a
  week on purpose, a cadence-based alert fires on normal behaviour and gets ignored, which is
  the exact "a signal that never changes stops being read" failure #2012 complains about. This
  is the substance of Q2 and is the main argument for doing nothing.
- **Unverified: whether `GITHUB_TOKEN` can read Dependabot alerts.** The severity-aware variant
  in Q2 needs `GET /repos/{owner}/{repo}/dependabot/alerts` with a `security-events: read`
  permission. I have not confirmed the built-in `GITHUB_TOKEN` is sufficient on a personal-account
  repo, and `gh api` is not runnable in this unattended session (permission-denied). **Probe this
  with a throwaway `workflow_dispatch` before committing to that design**, rather than assuming
  it works.
- **My refs could be stale, which is the same trap.** I could not `git fetch` (permission-denied
  unattended). I mitigated this by cross-checking against live GitHub via `gh pr view` / `gh issue
  view`, which confirmed #2009 merged and #1983 closed. The local `origin/main` ref carries a
  commit dated 2026-09-03, so it is at most a day old. The conclusion is safe, but re-run the
  four commands above after a fetch before closing anything.
- **Not assessed: whether `main` carries any *other* open advisory today.** I verified the eight
  advisories named in #2012 are fixed. I did not run `npm audit` or read Dependabot alerts, so
  "no other exposure" is not something this plan asserts.

## Open questions for Fraser

**Q1. What happens to #2012 itself?**

- **Option A - close it as already resolved, and stop.** Comment with the timeline (fixed by
  #2009 at 08:57Z, filed at 10:58Z), close, and do nothing else. Cost: zero. Trade-off: the
  failure class stays undetected. Note that on this occasion nothing was actually at risk, since
  the promotion had already happened, so "undetected" is a hypothetical, not a near-miss.
- **Option B (recommended) - close #2012 as a false positive, and open a separate small issue
  for the `promotion-staleness-check` job.** Keeps the record honest (this issue was wrong, and
  saying so is the useful outcome) while capturing the one genuinely reusable idea. Cost: roughly
  one workflow job plus a `workflow-expert` review.
- **Option C - repurpose #2012 in place** into the detector issue. Cheaper by one issue, but it
  leaves a permanent record claiming production was four weeks behind on a security release when
  it was not, which will mislead any future search of the backlog.

I recommend **B**. The correction is worth writing down explicitly, and separating it means the
detector can be prioritised, or dropped, on its own merits rather than inheriting #2012's
security framing.

**Q2. If B or C: what should the detector actually watch?** These differ in what wakes you up.

- **Option 1 (recommended) - cadence.** "`qa` has had un-promoted commits for more than 7 days."
  Pure `git`, no extra permissions, provably implementable today, and catches every cause
  including ones nobody predicted. Trade-off: fires on a deliberate slow week, so it can become
  noise. Mitigated by the auto-close, which means it self-clears the moment you promote.
- **Option 2 - severity.** "`main` has an open high or critical Dependabot alert." Near-zero
  false positives and it alerts on real exposure rather than on process. Trade-offs: it needs the
  `security-events` permission probe in Risks above before it can be committed to, and it is
  blind to a security fix that is not a dependency bump.
- **Option 3 - both, cadence gated on severity.** Alert only when `qa` is unpromoted **and**
  `main` carries an open high or critical alert. Tightest signal, most moving parts, and it
  inherits Option 2's unverified permission.

I recommend **Option 1**, because it is the only one I can currently promise works, and because
the auto-close makes its worst case (a benign alert during a quiet week) cheap. Option 3 is the
better end state if the permission probe comes back clean, but it should not be designed before
that probe runs.
