# Plan: #2031 [monitoring] grade_log divergence detected (1 users)

## What this is

An automated alert, not a feature request. On 2026-08-21 the daily monitor's **Option C** arm flagged one subject for user prefix `373c9b61`: something graded `>= 4` in the last 4 days with no `card_reviews` row. Options A and B were zero.

Verified from the repo, run logs and GitHub (this lane has no database access):

- **It cleared within a day and has not come back.** Run `32464587942` (21 Aug, 08:45 UTC) logged `Option A: 0 ... Option B: 0 ... Option C: 1 user(s)`. Run `32562612117` (22 Aug, 08:34 UTC) logged all three at 0 and printed `OK`. Every scheduled run since, up to `34858348378` on 14 Sep, concluded `success` with no new `monitoring` issue and no comment on #2031. A firing always leaves one or the other (and under `set -euo pipefail` a failed `gh` call fails the run).
- **The server-side reconciler did not heal it.** `reconcile_grade_log_orphans` (`db/migrations/032_reconcile_grade_log_orphans.sql`) is scheduled `0 4 * * 0`, Sundays 04:00 UTC, and 21 to 22 Aug 2026 is Friday to Saturday. Whether or not it was ever flipped live, it didn't run in that window. So a client wrote the row, or `reset_all_progress` removed the grade rows (`docs/sync.md`, per-table conflict policy).
- **The alert text points investigators the wrong way.** "Pull the affected user_ids from the workflow logs" is false: the logs carry only `user_id_prefix` (see the 21 Aug log). You have to match on the prefix.

**Leading hypothesis: the benign in-step shape Option C already documents, in its commonest form.** A brand-new card graded Good does not graduate. It enters learning step 0 with `lastReview` still null (`lib/srs/scheduler.ts:390-398`, case A1). So `isSyncSafe()` (`lib/sync/cloud.ts:92-94`) blocks the upsert (`lib/sync/usePerGradeSync.ts:291`), while `grade_log` already holds a grade 4. If the 08:00 UTC run lands while a user has left such a card mid-steps, Option C fires. It clears on the next session when the card graduates. That matches a one-subject, one-day hit exactly.

The competing explanation is a real but delayed push that the persisted pending queue delivered on the next visit (offline, tab closed inside the 200 ms debounce, failed beacon; `docs/sync.md` "Offline behaviour"). Both self-heal. Only the second is a sync event worth recording.

**What makes this decidable now.** When #1357 accepted Option C's noise, `grade_log.learning_step` didn't exist yet (migration 033, #1416). The client writes the **post-grade** step (`components/review/ReviewSession.tsx:2910-2919`). The scheduler sets it to `null` on exactly the graduating transitions: B3 `:341`, B4 `:357`, A2 `:383`, A4 `:424`. It sets a step index otherwise: A1 `:395`, A3 `:411`. So a row with `grade >= 4 AND learning_step IS NULL` means "this grade left the card graduated". That's the fact Option C approximates today with `MAX(grade) >= 4`.

This can't be closed on evidence yet, and it isn't a code fix on its own. It needs the read-only check in Approach step 1, then Fraser's call in the open questions.

## Approach

### Step 1: verify before changing anything (needs Supabase access)

Run read-only against prod from a session that has `mcp__supabase__execute_sql`. `entry_date` is the user's local day (`ReviewSession.tsx:2898-2914`, `date: localToday`), so the window is widened by a day on each side. The timestamp is when the 21 Aug run queried.

```sql
SELECT
  gl.user_id, gl.card_type, gl.subject_key, gl.locale,
  array_agg(gl.grade         ORDER BY gl.occurred_at) AS grades,
  array_agg(gl.learning_step ORDER BY gl.occurred_at) AS step_after_grade,
  array_agg(to_timestamp(gl.occurred_at / 1000.0) ORDER BY gl.occurred_at) AS graded_at,
  bool_or(gl.grade >= 4 AND gl.learning_step IS NULL
          AND to_timestamp(gl.occurred_at / 1000.0) < TIMESTAMPTZ '2026-08-21 08:45:05+00')
    AS graduated_before_alert,
  cr.first_seen, cr.last_review, cr.reps, cr.updated_at
FROM grade_log gl
LEFT JOIN card_reviews cr
  ON cr.user_id = gl.user_id
 AND cr.card_type = CASE gl.card_type
                      WHEN 'evolution' THEN 'evolution-edge'
                      WHEN 'reverse-evolution' THEN 'reverse-evolution-edge'
                      ELSE gl.card_type
                    END
 AND cr.subject_key = gl.subject_key
 AND cr.locale = gl.locale
WHERE gl.user_id::text LIKE '373c9b61%'
  AND gl.entry_date BETWEEN DATE '2026-08-16' AND DATE '2026-08-22'
GROUP BY gl.user_id, gl.card_type, gl.subject_key, gl.locale,
         cr.first_seen, cr.last_review, cr.reps, cr.updated_at
HAVING bool_or(gl.grade >= 4
               AND to_timestamp(gl.occurred_at / 1000.0) < TIMESTAMPTZ '2026-08-21 08:45:05+00')
   AND (cr.updated_at IS NULL OR cr.updated_at > TIMESTAMPTZ '2026-08-21 08:45:05+00')
ORDER BY min(gl.occurred_at);
```

What the result means:

- **No rows.** The grade rows are gone, most likely a progress reset. Close.
- **Candidates exist, all with `graduated_before_alert = false`.** Every Good/Easy before the run left the card in steps. Benign in-step Good, the leading hypothesis. Close with the evidence.
- **Some candidate has `graduated_before_alert = true`.** The card had graduated and its row was missing at run time: a real push that arrived late. Look at `graded_at` against `last_review`. If `last_review` matches the pre-alert graduation, the original push was just delayed (the transient class the persisted queue already covers); record it and close. If the row only appeared when the user graded that card again, the push was lost, not delayed. That's a #584-shape investigation (`docs/sync.md`), and step 2 pauses.
- **Several `user_id`s come back.** The prefix isn't unique; narrow it before reading anything.

Caveat (the #1243 lesson): `card_reviews.updated_at` moves on every upsert (migration 043). Its filter only narrows the candidates. The grade timestamps are the evidence.

### Step 2 (if Q1 is (b)): fix the proxy, not the timing

**Chosen: define "graduated" per row as `grade >= 4 AND learning_step IS NULL`.** It matches a strict subset of what Option C matches today. The only subjects it drops are those where every Good/Easy in the window left the card still in steps, which is exactly the "single Good at an intermediate learning step" noise the arm's own comment describes. It keeps the property #1357 insists on: a graduated orphan still fires at any age, with no grace.

It can't be quieter than today for old clients. A client bundle older than #1416 writes `learning_step = NULL` on every row (`lib/sync/gradeLog.ts:38`, `?? null`). For those rows the predicate collapses back to `grade >= 4`.

Rejected:

- **Only alert when a subject is orphaned on two consecutive runs.** Needs state between runs, and it's a 24-hour grace in disguise. #1357's comment forbids exactly that.
- **An upper-bound recency grace on Option C.** Recreates the blind spot Option A already has (#1357).
- **Raising `DIVERGENCE_THRESHOLD`.** Mutes real single-subject orphans along with the noise.
- **Dropping Option C.** Loses the #1344 coverage (15 of 24 orphans were only visible to this shape).

## Risks and unknowns

- **Step 1 hasn't been run.** The hypothesis comes from code and run logs, not data. If the flagged card had graduated before the run, this becomes a sync-path investigation and step 2 waits.
- **Prod schema assumption:** `grade_log.learning_step` exists in prod (migration 033; `migration-check.yml` asserts prod parity on push to `main`). The step 1 query fails loudly if it doesn't.
- **Residual blind spot of the new predicate:** a previously graduated hard card (difficulty above 7, which gets two relearning steps, `lib/srs/constants.ts:25`) whose only in-window Good is at the intermediate relearning step. It's sync-safe (A3 sets `lastReview`) but wouldn't be flagged. Its row should already exist from its original graduation, so a missing row is the existing #1230 look-back-floor class, not something new. Name it in the rewritten comment.
- **Adjacent, verified today, not in scope:** the dedupe lookup (`gh issue list --state open --label monitoring --search "<!-- monitor:grade-log-divergence --> in:body"`) returns `[]` while #2031 is open, labelled and carries that marker. That confirms #2010: search doesn't index HTML comments, so the next firing opens a new issue instead of commenting. Leaving #2031 open doesn't suppress duplicates. The fix belongs to #2010.
- **Adjacent, not in scope:** all three arms join `card_reviews` on `(user_id, card_type, subject_key)` without `locale`. The PK has included `locale` since migration 029, and the reconciler does join on it. A graduated `ja` orphan is invisible whenever an `en` row exists. That's a false negative, the opposite problem to this one, so it wants its own issue.
