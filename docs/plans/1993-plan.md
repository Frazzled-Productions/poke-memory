# Plan: #1993 AGENTS.md pushes toward delegation, but Opus 5 already over-delegates

## What this is

A documentation and harness-configuration change, no product code. Three parts, in
descending confidence:

1. **Reframe the sandbox line** so `AGENTS.md` stops reading as a thumb on the scale
   toward delegating, and add a short, operative "when to delegate" test where the model
   will actually see it. Fully specified below, ready to implement.
2. **Dispatch cap hook.** I have a design, but whether to install a hard block on your own
   sessions is your call, and the number interacts with `/batch-issues`. See
   [Open questions](#open-questions-for-fraser), Q1.
3. **Roster review.** I measured the actual per-session cost of the roster before
   recommending anything, and it is smaller than the issue assumes. See Q2.

Two facts worth having up front, both measured in this worktree:

- The roster is **14 agents**, not 15 (`.claude/agents/*.md`). The issue's count may include
  the orchestrator, or an agent that has since gone.
- The per-session context tax of the roster is **only the 14 `description:` frontmatter
  lines: 4,525 bytes, roughly 1.1k tokens**. The agent bodies (about 1,045 lines in total)
  load only when an agent is dispatched. So "15 agents is a lot of descriptions taxing
  dispatch context" is true in kind but small in degree: the roster costs about 4.5 KB
  against `AGENTS.md`'s own 24 KB. Trimming the roster to save context is not a good trade;
  trimming it to reduce dispatch *bias* might be, which is a different argument and is what
  Q2 asks about.

## Approach

**The reframe.** Replace line 5 with something like:

> This repo is also where Claude Code sub-agent patterns get proven - see the roster and
> playbook in [WORKFLOW.md](WORKFLOW.md#sub-agent-roster). That is a reason to keep the
> roster sharp, not a reason to reach for it: an agent has to earn its keep on the task in
> front of you.

Then, under "Sub-agents and orchestration":

> **When to delegate.** Delegate for a large, genuinely independent, parallelisable track
> of work: a wide multi-file investigation, or one issue per agent in a batch drain. Do not
> delegate what you can finish in a handful of tool calls. If one agent can do it, use one.
> The named review and pre-consult gates below are deliberate exceptions and still apply.

**The one real design decision: do not import Anthropic's suggested wording verbatim.**
Their sentence "do not use subagents to verify or double-check your own work" would, dropped
into this repo unqualified, silently repeal four things that exist for documented reasons:
the `code-reviewer` pass after every non-trivial change; the hard rule that
`workflow-expert` reviews *every* `.github/workflows/**` change (#1859, #1815, #1806 all
came from skipping it); the `ux-advisor` design-time consult before onboarding code
(#1276); and the specialist pre-consult on the brief (#1259, #1260). Those are not the
model double-checking itself, they are independent domain gates that caught real bugs. So
the rule ships with the carve-out named inline, rather than as generic advice that a future
session resolves in whichever direction it feels like.

**Rejected: putting the criteria only in `WORKFLOW.md`.** It is the tidier home and the
existing one-liner is already there, but `WORKFLOW.md` is 1,026 lines and is not loaded
into a session; a delegation rule that is not in context when the dispatch happens is a
rule that does not exist. The split is: short operative test in `AGENTS.md`, elaboration
and carve-out list in `WORKFLOW.md`.

**Rejected: applying the same lens to `/batch-issues` fan-out and the `ui-coder`
multi-surface decomposition gate.** Both raise agent counts, so both look like targets. They
are not: the decomposition gate (`.claude/agents/ui-coder.md`, step 0, #1766/#1767) exists
because *one over-wide agent stalled three times* and had to be salvaged by the
orchestrator. That is right-sizing a delegation already decided on, not eagerness to
delegate. Re-opening it would re-open a documented incident. Same for the per-issue fan-out.

**Rejected: deleting agents to save context.** See the 4.5 KB measurement above.

**Hook design, if Q1 lands on option C.** Adapted, not copied, because koinori caps
build-capable agents over a shared build resource and this repo has no such resource:

- `PreToolUse` matcher covering **both** `Agent` and `Task` (the tool has been called both;
  `settings.json` still allow-lists the old name).
- **Counts all agent types, not just write-capable ones.** The constraint here is cost and
  wall-clock, which a read-only `researcher` burns just as happily as a `ui-coder`. This is
  the classification rethink the issue asks for.
- Concurrency, not cumulative: increment a per-`session_id` counter file under `$TMPDIR` on
  `PreToolUse`, decrement on `SubagentStop`, with a TTL so a crashed agent cannot leak a
  permanent lockout.
- Deny above the cap with a reason string that states the cap, the override, and how to
  clear a stuck counter.
- `POKE_AGENT_CAP=<n>` override, `0` to disable, mirroring koinori's env escape hatch.

## Testing

This is docs plus harness config, so "what proves it works" is mostly gates plus one real
dispatch. Specifically:

- **`npm run lint`** - the load-bearing one here is `lint:agents-size`
  (`scripts/lint-agents-size.mjs`). `AGENTS.md` is currently **206/240 lines, 24,397/26,624
  bytes**, so there are only about 2.2 KB of headroom and the new paragraph has to fit
  inside it. `lint:em-dash` also runs, which matters for a prose change.
- **`npm run pre-pr`** - the standard repo gate (lint, typecheck, build, test, coverage,
  diff-coverage), per `AGENTS.md` "Pre-PR build gate".
- **No changelog fragment is required.** `changelog-gate.yml` only fires on `app/**`,
  `components/**`, `lib/**`; this change touches none of them. Adding one anyway is
  harmless, but it is not a gate failure waiting to happen.
- **If the hook ships**, `scripts/guard-agent-dispatch-cap.test.mjs` in the `node` project,
  spawning the script with crafted stdin payloads. Named cases: under the cap allows and
  emits nothing; at the cap denies with the reason string; `POKE_AGENT_CAP` raises the cap;
  `POKE_AGENT_CAP=0` disables it; a non-dispatch `tool_name` passes through untouched;
  empty or malformed stdin exits 0 rather than blocking (a guard that fails closed on a
  parse error is worse than no guard); a counter entry older than the TTL is ignored.
- **One real dispatch in a scratch session**, because the unit test proves the script works
  and proves nothing about whether the harness ever calls it. A registered-but-never-firing
  hook is exactly the silent-failure mode this repo already writes down for GitHub Actions
  YAML. Confirm the deny actually surfaces at cap+1, then confirm a normal dispatch below
  the cap is unaffected.
- **`workflow-expert` review** if any `.claude/agents/**` file changes (Q2 option (i)), per
  the file-ownership table. Yes, that is a mandatory delegation inside a change about
  delegating less. It is one of the carve-outs, which is rather the point.

## Risks and unknowns

- **I could not read the two prior-art sources.** `koinori`'s
  `.claude/hooks/guard-build-agent-cap.sh` and the `frazzled-claude` README are outside this
  session's allowed working directories, and `gh api` calls against other repos were denied
  in this unattended run. The hook design above is built from the issue's description of
  koinori's hook, not from its source. Worth a five-minute read-across before implementing.
- **Hook API details are unverified.** The `PreToolUse` JSON schema (the
  `hookSpecificOutput.permissionDecision` shape versus exit-code-2 blocking), and whether
  the matcher sees `Agent` or `Task` in the installed CLI, need checking against the current
  hooks documentation before the script is written. The stale `Task(*)` entry in
  `settings.json` shows this name has already moved once.
- **Counter leak.** `SubagentStop` firing is the load-bearing assumption for concurrency
  tracking. If an agent is killed with `TaskStop`, or the session dies, the decrement may
  never happen. The TTL is the mitigation; it is a mitigation, not a proof.
- **A concurrency cap does not catch the failure mode the issue actually describes.**
  Over-delegation as Anthropic describes it is many *small* agents, often one at a time. A
  concurrency cap never fires on that. It catches fan-out storms. The prose rule catches the
  small-task case. Neither covers both, and it is worth being honest that the hook is a
  circuit breaker rather than a fix.
- **This repo's own incident history points the other way.** The documented pain in
  `/batch-issues` is agents *stalling* and needing orchestrator takeover (#1766/#1767, three
  stalled implementers; #1394, two stalled fix agents), not agents being too numerous. That
  is an argument for setting any cap generously, and a mild argument for option A.
- **The 14-versus-15 discrepancy** is unexplained; if the issue was written against a
  different checkout, something may have been removed since.

## Open questions for Fraser

### Q1. Do we install a dispatch cap hook, and does it block or only advise?

- **A. No hook.** Prose only. Cheapest, zero mechanism to maintain, no risk of a stuck
  counter locking a session. Against it: koinori's own header is the counter-argument
  ("prose does not enforce"), and this repo has a track record of prose rules being
  bypassed until a gate existed (`workflow-expert`, the changelog gate, `lint:agents-size`).
- **B. Advisory hook.** Fires on every dispatch, never blocks, prints a reminder. Sounds
  like the safe middle, and I think it is close to worthless: a `PreToolUse` hook that exits
  0 writes to the transcript, not reliably into the model's context, so the thing it is
  meant to influence may never see it. Listed for completeness, not recommended.
- **C. Blocking concurrency cap**, all agent types counted, `POKE_AGENT_CAP` override,
  `/batch-issues` updated in the same change. Real enforcement; costs a script, a test, and
  the leak risk above.

**Recommendation: C, with the cap at 4 concurrent.** The trade-off to weigh is that the cap
number is only meaningful if `/batch-issues` stays under it. If your normal drain batch is
five or six issues, the override becomes routine and the cap becomes theatre, at which point
A is more honest than a gate everyone steps around. **I need your typical batch width to
pick the number.** If you would rather not have a hard block interrupt a session at all,
say so and I will implement A, which still delivers the whole of part 1.

### Q2. Do we trim the roster, and how far?

- **(i) No deletions; tighten descriptions.** Only **1 of the 14** descriptions
  (`pokeapi-expert`) states when *not* to use the agent. Several say "use BEFORE writing
  code, not after", which is sequencing, not a skip condition. Adding one skip clause each
  is a small edit that attacks dispatch bias directly, and costs no capability.
- **(ii) Retire the thin generalists.** `researcher` (30 lines) and `next16-expert` (26
  lines) overlap the built-in `Explore` and `general-purpose` agents. Saves roughly 0.6 KB
  of session context, which is negligible, and removes two plausible-looking destinations
  for a dispatch, which is the actual benefit. Cost: `next16-expert` encodes the "this is
  NOT the Next.js you know" rule, and a built-in agent will not know to read
  `node_modules/next/dist/docs/`.
- **(iii) Full three-tier restructure** along the `frazzled-claude` model. I cannot read
  that README from here, so I cannot plan it responsibly today.

**Recommendation: (i) now, and file (iii) as a separate issue** for a session that can read
`frazzled-claude`. I would leave (ii) alone unless you want the roster smaller for its own
sake, because the context saving is not the reason to do it and the `next16-expert` loss is
real. This repo being a sub-agent sandbox is a genuine reason to keep a slightly wider
roster than pure utility justifies, which is exactly the intent the issue says is worth
preserving.
