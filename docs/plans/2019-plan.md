# Plan: #2019 next/image `priority` is deprecated in Next 16, still used at 8 call sites, and the promised tracking issue does not exist

## What this is

`docs/sprites.md:62` promises a follow-up tracking issue for the `priority` to `preload`
migration. No such issue was ever filed, so the note has asserted a false state of the world
since 2026-06-07. #2019 is now that tracking issue.

The issue asks for one of two outcomes, and picking between them is a scope call (see
"Open questions for Fraser"). This plan specifies both: **Branch A** (migrate now, recommended)
and **Branch B** (record a deliberate deferral). Branch B is a two-line doc edit; everything
else below is Branch A.

### What the installed Next actually does (read, not recalled)

This worktree has no `node_modules`, so the paths below were read from the main checkout at
`poke-memory/node_modules`, which has `next@16.2.9` installed.

- `next/dist/shared/lib/get-img-props.d.ts:24-28` marks `priority?: boolean` with
  `@deprecated Use \`preload\` prop instead.` It is a type-level deprecation: editors strike it
  through, `tsc` does not fail.
- `get-img-props.js:584` returns `preload: preload || priority`, and `:269` computes
  `isLazy = !priority && !preload && (loading === 'lazy' || typeof loading === 'undefined')`.
  **`preload` is an exact runtime alias for `priority`.** A 1:1 rename is behaviour-identical.
- Neither prop touches `fetchPriority` (`:569` passes it straight through). So
  `fetchPriority="high"` is a genuinely different behaviour, not a synonym.
- Passing both throws (`:404-405`); `priority` with `loading="lazy"` throws (`:390-391`).
- There is **no runtime deprecation warning** for `priority`. The only `warnOnce` in that file is
  for `onLoadingComplete` (`:467`). Nothing is failing or logging today, so this is a clock
  running towards a future major, not a live defect.
- `priority={false}` is the default value, so the three `priority={false}` sites can drop the
  prop outright with zero behaviour change.

The issue's count of 8 call sites across 7 files is correct, verified by grep over
`components/`, `app/`, `lib/`, `e2e/` and `scripts/`. No test asserts the prop.

  message:

It belongs in the block scoped to `components/**` and `app/**` (`eslint.config.mjs:70-73`),
which is where all eight sites live. There are no `<Image>` call sites under `lib/**`.

## Approach

**Rename to `preload` at the five truthy sites, delete the prop at the three `priority={false}`
sites, fix both documents that still teach `priority`, and add a lint rule so the surface cannot
grow again.** The runtime reading above is what makes this safe: `preload: preload || priority`
means the rename cannot change a single byte of rendered output.

Rejected:

- **Re-deciding the loading strategy per site while renaming.** The Next docs do say "in most
  cases, you should use `loading="eager"` or `fetchPriority="high"` instead of `preload`", and
  that hint is the strongest argument for treating this as more than a rename. But acting on it
  changes real behaviour on the app's hottest surface with no measurement in the repo to justify
  it, and it would make a zero-risk change into one that needs perf evidence. Raised as Q2
  rather than decided here.
- **A codemod.** Eight sites across seven files, four of which have an adjacent comment that
  needs updating by hand. A codemod would do the easy half and leave the prose wrong.
- **`@typescript-eslint/no-deprecated` as the forcing function.** It needs type-aware linting,
  which `eslint.config.mjs` does not configure today (it composes `eslint-config-next/core-web-vitals`
  and `/typescript` only), and it would slow the lint job for one rule. The `no-restricted-syntax`
  JSX selector is the established local pattern: #1456's sprite pixel-literal ban at
  `eslint.config.mjs:168-179` is the same shape.
- **Fixing the doc without the lint rule.** The issue's own point is that the count is not
  static. Prose is what failed here the first time.

## Testing

`npm run pre-pr` is the gate (lint, typecheck, build, test, coverage, diff-coverage). What each
leg actually proves here:

- **`npm run typecheck`** is the prop-name gate: a mistyped `preLoad` is an excess-property error
  on the JSX element, and after the change no `@deprecated` member is referenced anywhere.
- **`npm run lint`**, with the new rule, is the *completeness* gate: it fails if any `priority`
  survives under `components/**` or `app/**`. This is the check that proves "all 8" rather than
  "the ones I remembered".
- **Existing suites that must stay green** (they render the touched components):
  `components/pokedex/PokemonDetailDisclosure.test.tsx` (the "sprite sizes (#931)" describe at
  `:360`), `components/review/EvolutionCardLayout.test.tsx`,
  `components/review/MultipleChoiceNameCard.test.tsx`,
  `components/review/TypedEntryNameCard.test.tsx`, `components/review/ReviewSession.test.tsx`
  (the only path that renders `PokemonCard`), `components/theme/ThemeWatermark.test.tsx`,
  `components/pasture/NextArrivalsStrip.test.tsx`,
  `components/onboarding/KnownPokemonQuiz.test.tsx`.
- **Manual proof in a production build**, which is the only thing that exercises real
  `next/image`: `npm run build && npm start`, then on `/pokedex/25` confirm a
  `<link rel="preload" as="image">` for the 192 px hero variant in `<head>` and that the hero
  `<img>` carries no `loading="lazy"`; on the review route confirm the flip-card sprite likewise
  has no `loading="lazy"`. Run the same two checks against `qa` first so this is a before/after
  diff rather than an assertion from memory.
- **Optional e2e** (owned by the `playwright` agent, `e2e/**`): one assertion on `/pokedex/25`
  that the hero image has no `loading="lazy"`. This adds no new user flow, so the repo's
  "every new user-facing flow gets a test" rule does not compel it; it is cheap insurance
  against a future accidental delete of the prop.

**Do not write a unit test that asserts `preload` or `loading` and call it proof.** See the first
risk below.

## Risks and unknowns

- **Unit tests cannot prove anything about this change.** Every component test mocks `next/image`
  as `<img {...props} />` (for example `components/pokedex/PokemonDetailDisclosure.test.tsx:10-15`),
  so the prop is spread verbatim onto a DOM node. An assertion on `loading` or `preload` would be
  testing the mock, not Next. The real signal is typecheck, lint, and the production-build check.
- **Diff coverage.** The changed lines are JSX prop lines inside rendered components, and
  `components/review/PokemonCard.tsx` has no test file of its own: it is reached only through
  `ReviewSession.tsx:3090` and `:3389`. If `ReviewSession.test.tsx` does not render that branch,
  the changed line is uncovered and `npm run test:diff-coverage` (90% floor) fails. Check this
  before opening the PR rather than discovering it in the gate.
- **"Preload" is a slight misnomer mid-session.** `image-component.js:218` calls
  `ReactDOM.preload()` for every preloaded image, so after the first review card the "preload"
  fires at the same moment the visible `<img>` mounts. That is already true under `priority`, so
  it is not a regression, but do not read the new prop name as promising more than it does.
- **No removal date is documented.** The installed Next docs
  (`01-app/03-api-reference/02-components/image.md:293` and the version table at `:1402`) say
  deprecated in 16.0.0 and say nothing about removal. "Next 17 forces the issue" in the issue body
  is an assumption. Nothing here is time-critical, which is exactly why Branch B is defensible.
- **Version drift nearby, out of scope.** `AGENTS.md:8` says Next 16.2.6, `package.json:53` pins
  16.3.1, and the installed tree is 16.2.9. Three-way drift in the same neighbourhood as this
  issue, but not this issue's job. Worth a separate Porter issue.
- **Stale prose spotted while verifying, out of scope.** `WORKFLOW.md:801` says the release cut
  bumps minor for "Added/Changed/Removed/Deprecated" fragments. `cut-release.mjs:15-16` and `:100`
  only bump minor on an explicit `minor-bump` fragment. The script is right and the doc is wrong.

## Open questions for Fraser

**Q1. Migrate now, or record a deliberate deferral?**

- **A (recommended): migrate now.** The rename is provably behaviour-identical, three of the eight
  sites are pure deletions, and the lint rule closes the growth path the issue identifies. One PR,
  no perf risk, and `docs/sprites.md` becomes true again by describing what the code does rather
  than by pointing at a tracker entry.
- **B: stay on `priority` until removal, and say so in the note.** Cheaper today (one doc edit)
  and honest, since nothing warns at runtime and no removal version is announced. The cost is that
  `AGENTS.md:139` and the `docs/sprites.md` table keep teaching the deprecated prop, so the eight
  sites become nine, and the migration lands later with more surface.
- Trade-off in one line: A spends roughly an hour now to stop the surface growing; B spends nothing
  now and accepts that the next sprite surface adds another call site.

**Q2. If A: 1:1 rename, or re-decide the loading strategy per site?**

- **A (recommended): 1:1 rename, semantics untouched.** `preload` is a byte-for-byte alias, so the
  PR carries no perf risk and needs no measurement.
- **B: follow the Next docs' hint** and move the four review flip-card sprites to
  `fetchPriority="high"` (a hint on the `<img>`, no head preload link), keeping `preload` only for
  the Pokédex detail hero, which is the one genuine document-load LCP element.
- Trade-off: B is arguably what the Next team means the props for, and it removes preload links for
  images that are only the LCP on the very first card of a session. But it is a real behaviour
  change on the app's hottest surface, we have no LCP measurement in the repo to compare against,
  and it would put the visual-snapshot suite in play. My recommendation is A now, plus a separate
  perf issue if we ever want to tune review-card sprite loading with numbers behind it.
