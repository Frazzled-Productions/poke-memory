# Plan: #2010 monitor-grade-log-divergence opens a new issue every day instead of updating the open one

## What this is

The issue's diagnosis is right and its code citation is stale. Dedup already landed in
`9420abda` ("Remove the Claude automation, and stop the monitor filing duplicates", #2003,
2026-08-16); #2010 was filed 2026-08-18 against the pre-#2003 blob. The step is no longer an
unconditional `gh issue create`, and the file is 133 lines, not 107.

The dedup that landed is inert. It resolves the marker with the one lookup the repo forbids:

`.github/workflows/monitor-grade-log-divergence.yml:117-120`

```yaml
          EXISTING=$(gh issue list \
            --state open --label monitoring --limit 50 \
            --search "$MARKER in:body" \
            --json number --jq '.[0].number // empty')
```

WORKFLOW.md:93 states the rule ("GitHub's search index strips HTML comments, so a `<!-- marker -->`
dedup that relies on search to find prior comments silently fails"), and three sibling workflows
carry the same warning in-line: `cron-health-monitor.yml:77-88` (which names #1919, the first time
this exact bug shipped), `pokeapi-species-monitor.yml:95-103`, `auto-release.yml:265`.

Probes run against the live repo on 2026-09-05:

| probe | result |
|---|---|
| the current impl verbatim: `--search "<!-- monitor:grade-log-divergence --> in:body"` | empty, exit 0 |
| local jq match on `--json number,body` (the sibling pattern) | `2031` |
| `--search '"<!-- monitor:grade-log-divergence -->" in:body'` (marker quoted) | `[2031, 2010, 1999, 2002, 2001, 2000]` |

#2031 is open, carries the `monitoring` label, and contains that marker verbatim as its first body
line, so row 1 is a false negative. `monitor:` parses as an unknown search qualifier, which is the
precise #1919 failure mode recorded at `cron-health-monitor.yml:79-82`. Row 3 shows that quoting the
marker is not a fix either: search drops the comment punctuation and matches on the words, so it
returns issues that do not contain the marker at all, including #2010 itself. The monitor would then
post its recurrence comments onto this issue.

Because an empty result exits 0, `set -euo pipefail` cannot catch it. Every alerting run takes the
create branch.

State in production: after #2003 landed, one alert fired (2026-08-21) and duly created a new issue,
#2031, because #1999-#2002 predate the marker. Every run from 2026-08-22 to 2026-09-04 succeeded and
#2031 has zero comments, so the check has been returning `OK` since. The bug is dormant, not fixed,
and the next genuine divergence resumes daily duplicates.

## Approach

Adopt the pattern the other three monitors already use, without inventing a fourth variant.

- **Lookup.** `gh issue list --repo "$REPO" --state open --json number,body --limit 100`, piped to
  `jq -r --arg marker "$MARKER" '[.[] | select(.body | contains($marker))] | .[0].number // empty'`.
  Byte-for-byte the shape at `cron-health-monitor.yml:244-245` and `pokeapi-species-monitor.yml:104-107`.
  No `2>/dev/null`, so a `gh` failure fails the step rather than masquerading as "no existing issue".
- **Drop `--label monitoring --limit 50`.** Both precedents fetch the unfiltered open list, and a
  human removing the label during triage would silently restart duplicate-filing. 34 issues are open
  today, so the 100 cap has 3x headroom.
- **Keep the marker string `<!-- monitor:grade-log-divergence -->` exactly as it is.** Rejected:
  renaming it to a colon-free marker. The colon only ever hurt `--search`, which is being removed,
  and a rename orphans #2031, which already carries the current marker, guaranteeing one more
  duplicate on the next alert.
- **Rejected: keep `--search` and quote the marker.** Probed above: it produces false positives, so
  the monitor would comment on unrelated issues.
- **Update in place, do not only comment.** `gh issue edit "$EXISTING" --body-file` with the freshly
  generated body, `--title` with the current user count (the count is in the title and drifts), then
  a short recurrence comment carrying the marker, the UTC timestamp and the run URL. Comment-only
  leaves the body frozen at day-one numbers, which is exactly what makes a long-lived tracking issue
  misleading. Same shape as `pokeapi-species-monitor.yml:126-130`.
- **One body for both branches.** Assemble `/tmp/divergence-body-marked.md` (marker line, blank line,
  then `/tmp/divergence-body.md`) before the `if`, so a created issue and an edited issue are
  structurally identical.
- **House style in touched comments.** The existing comment block uses em dashes. The em-dash linter
  scans `app`, `components`, `lib`, `scripts`, `e2e`, `db`, `i18n`, `changelog.d` and `CHANGELOG.md`
  only (`scripts/check-no-em-dash.mjs:53`), so `.github/**` is unpoliced; replace them with spaced
  hyphens in any comment line the change rewrites.
- **Process.** `.github/workflows/**` takes a mandatory `workflow-expert` review (AGENTS.md file
  ownership), and WORKFLOW.md:93 additionally requires consulting `workflow-expert` *before* writing
  a marker-dedup change, not only as a reviewer afterwards. Do that first, then implement, then
  review.

## Testing

1. **Read-only probe, before and after** (this is what proved the bug, and it is the only way to
   exercise the real lookup against real data). From the branch, with real `gh` auth: the new
   pipeline must print `2031`; the old `--search` form must print nothing. Both are read-only.
2. **Dry run of the step body.** Copy the step's `run:` block to a scratch file, export `REPO`,
   `USER_COUNT=1` and `MARKER`, stub `gh issue edit` / `gh issue comment` / `gh issue create` with
   `echo` shims on `PATH`, and confirm it takes the edit-plus-comment branch and names #2031. Then
   re-run with a nonsense marker and confirm it takes the create branch. This is the only offline
   check of the branch logic; nothing else covers it.
3. **`npm run pre-pr`.** Required by the pre-PR gate regardless; `lint:changelog` validates the new
   fragment, and the rest is a no-op for a YAML-plus-docs diff.
4. **Post-merge, deferred.** The alert path cannot be forced: the check only alerts when the Supabase
   queries actually diverge, and the `threshold` dispatch input can only raise the bar, never lower
   it below the default 0. So `workflow_dispatch` proves the job still runs green, not that dedup
   works. The real proof is the next genuine alert: #2031 gains a comment, its body and title
   refresh, and `gh issue list --state all --search '"grade_log divergence detected" in:title'` stays
   at its current count.
5. **Not covered: automated tests.** `.github/scripts/check-issue-staleness.test.sh` shows the repo's
   `gh`-stub bash-test pattern, but grep of `.github/workflows/**` and `package.json` finds no runner
   for `*.test.sh`, so a test written today would only ever run by hand. Whether to close that gap is
   open question 1.

## Risks and unknowns

- **The `--limit 100` cap.** `gh issue list` returns newest-first, so once the open backlog passes
  100 the (by then old) tracking issue falls out of the window and duplicates silently resume. 34
  open today. `--paginate` via `gh api` removes the cap but diverges from both precedents; flagged
  rather than taken.
- **Adoption is automatic for #2031 only.** #1999, #2000, #2001 and #2002 have no marker and will
  never be adopted; they stay open until closed by hand (open question 2).
- **Closing #2031 while the divergence persists** makes the next run open a fresh issue. That is
  intended behaviour (closed means handled) but is worth knowing before triage.
- **Dormancy hides the fix.** The check has returned `OK` since 2026-08-22, so nothing will confirm
  the fix in production until the next real divergence, possibly weeks out. "No new duplicate
  appeared" is not evidence before then.
- **`gh issue edit --title` every run.** I expect GitHub to record a title-change event only when the
  value actually differs, so a steady user count produces no timeline noise, but I have not verified
  that and will not mutate a live issue to find out. If it does prove noisy, guard the `--title` with
  a comparison against the current title.
- **Out of scope: whether the alert is correct.** This change makes one persistent divergence read as
  one ticket. It says nothing about whether user `dff21628` is a genuine sync break (see open
  question 4).

## Open questions for Fraser

**1. How far to go on prevention?**
- (a) Inline fix only, matching the two sibling monitors.
- (b) Inline fix plus a `lint:workflow-markers` guard in the `lint` chain, failing when any
  `.github/workflows/**` file passes an HTML-comment marker to `gh ... --search`.
- (c) Inline fix plus extracting the upsert into `.github/scripts/upsert-monitor-issue.sh` with a
  colocated `.test.sh`, and a CI runner for `*.test.sh` (which does not exist today).

  Recommendation: **(b)**. This is the same platform quirk shipping for the second time (#1919 fixed
  `cron-health-monitor`, #2003 reintroduced it here from a copy of the old shape), and the repo's
  stated answer to a recurring class is a forcing function, not another careful fix. It is roughly 30
  lines and covers every future monitor. Trade-off: one more script and one more link in the lint
  chain. (c) is more thorough but roughly doubles the diff, and its value is gated on building the
  CI runner that (c) also has to add.

**2. Tidy-up of the five open duplicates.** Shared GitHub state, so your call.
- Option 1: keep #2031 (it already carries the marker, so the fixed workflow adopts it) and close
  #1999, #2000, #2001, #2002 as duplicates of it.
- Option 2: keep #1999 (the original), paste the marker into its body by hand, close the other four.

  Recommendation: **option 1**. It needs no body edit and matches what the workflow will do on its
  own. Trade-off: the earliest first-observed date lives on a closed issue, so #2031's created-date
  understates how long this has been running. A line in #2031 pointing back at #1999 fixes that.

**3. Should the monitor auto-close its tracking issue when the divergence clears?**
`cron-health-monitor.yml:247-254` does exactly that for its own alerts.
- Option 1: no auto-close.
- Option 2: close after N consecutive clean runs (needs run-to-run state, e.g. a counter written into
  the issue body).

  Recommendation: **option 1** for this change. The signal went quiet on 2026-08-22 without anyone
  establishing why, and an auto-close would have erased that fact rather than surfaced it; unlike a
  cron workflow being healthy again, "no divergent rows today" is not evidence the sync break was
  fixed. Trade-off: someone closes it by hand once the underlying data is understood.
