# Plan: #2016 Vercel Ignored Build Step can skip a deploy for messages/, i18n/ and instrumentation changes

## What this is

`vercel.json:3` runs `scripts/vercel-ignored-build.sh` as Vercel's Ignored Build Step. The script
diffs `VERCEL_GIT_PREVIOUS_SHA..HEAD` against a hand-maintained `WATCH_PATHS` allowlist
(`scripts/vercel-ignored-build.sh:17-30`) and exits 0 (skip the build) when nothing in the list
changed. Three deployed build inputs are missing from that list, so a promotion to `main` confined
to them is recorded as a skipped deployment and the previous bundle stays live.

Verified in the working copy:

- `messages/` (`en.json`, `ja.json`, `zh-Hans.json`, `zh-Hant.json`, `xx-pseudo.json`) is pulled in
  by the dynamic `import("../messages/${locale}.json")` at `i18n/request.ts:53`, and also imported
  directly at runtime by two deployed route handlers: `app/api/push/send-daily/route.ts:111` and
  `app/api/push/send-streak-nudge/route.ts:93` (`@/messages/en.json`). So a copy fix to
  `messages/en.json` alone changes both the UI and the push-notification text, and today ships
  neither.
- `i18n/` (`request.ts`, `locales.ts`) is wired into the build by
  `createNextIntlPlugin("./i18n/request.ts")` at `next.config.ts:113`.
- The four root `instrumentation*.ts` files (`instrumentation.ts`, `instrumentation-client.ts`,
  `instrumentation-node.ts`, `instrumentation-edge.ts`) are Next's instrumentation hooks and are
  where Sentry is initialised (`instrumentation.ts` dispatches on `NEXT_RUNTIME`).

Blast radius is bounded: `vercel.json:5-8` sets `deploymentEnabled` to `{"**": false, "main": true}`,
so the ignore script only ever runs for pushes to `main`. Over-triggering costs one build on `main`;
under-triggering silently serves a stale bundle. The asymmetry is the whole argument for the fix.

This is latent, not an active incident (see the issue's honest-scoping note), and the same list
already drifted once before (`scripts/vercel-ignored-build.sh:31-34`, `scripts/` added after #1752).

## Files to change

- `scripts/vercel-ignored-build.sh` (exists) - add `i18n/`, `messages/` to the directory block and
  `'instrumentation*.ts'` to the root-file block of `WATCH_PATHS`, because all three are compiled
  into or read by the deployed build. Extend the rationale comment below the array in the same style
  as the existing `scripts/` note, citing #2016, so the next reader sees why each entry is there.
- `scripts/vercel-ignored-build.test.mjs` (NEW) - behavioural test for the script, run by the
  existing vitest `node` project (`vitest.config.ts:87` already includes `scripts/**/*.test.mjs`).
  Builds a throwaway git repo in a temp dir, commits, then commits a single-path change and asserts
  the script's exit code. This is the first test the script has ever had; grep confirms it is
  referenced today only by `vercel.json` and `WORKFLOW.md:808`.

No other file needs to change. `WORKFLOW.md:808` is the only prose that mentions `WATCH_PATHS` and
it stays accurate (it asserts `package.json` is watched, which is unaffected). No changelog fragment:
this is internal build infrastructure with no user-visible behaviour change of its own, and
`changelog.d/README.md` plus the release pipeline treat a fragment as optional for internal work.

## Approach

**Add to the existing allowlist rather than restructure the script.** The script's fail-open
handling of a missing or unreachable `VERCEL_GIT_PREVIOUS_SHA` (`:41-51`) is sound and untouched.

Two implementation decisions inside that:

1. **`'instrumentation*.ts'` as a quoted glob, not four literal paths.** Rejected the four-path
   listing precisely because it is the failure mode being fixed: it drifts the moment Next adds a
   fifth hook file. The quotes matter. Bash performs pathname expansion on unquoted words during
   array assignment, so an unquoted `instrumentation*.ts` would expand against the shell's cwd at
   assignment time; quoting passes the pattern through to git as a pathspec instead. Git pathspec
   globs are wildmatch without `WM_PATHNAME`, so `*` crosses `/` (verified in this working copy:
   `git ls-files -- 'lib*derive.ts'` returns `lib/badges/derive.ts` and `lib/stats/derive.ts`). That
   means the pattern would also match a nested `.../instrumentation-x.ts`, which today can only
   exist inside `app/`, `lib/` or `components/`, all already watched, so the extra reach is inert.
   `git diff` tolerates a pathspec matching nothing (verified: `git diff --stat HEAD~1 HEAD --
   'nosuchthing*.ts'` is silent and clean), so the entry is safe even if every instrumentation file
   were deleted.

2. **A real behavioural test rather than an eyeball of the diff.** The script only executes on
   Vercel, so it has no natural exercise path; a temp-repo harness is the only way to prove exit
   codes without a deploy. It needs no network: `git cat-file -e` succeeds against a local SHA, so
   the fetch and unshallow branches are never reached.

Rejected: inverting the script to a denylist (build unless the diff touches only known-irrelevant
paths). That is the design that actually fails safe, and it is the honest long-term answer to a list
that has now drifted twice. It is also a larger rewrite than the issue asks for, and it changes the
maintenance contract, so it goes to Fraser as an open question rather than being taken unilaterally.

## Testing

`scripts/vercel-ignored-build.test.mjs`, in the vitest `node` project, driving the real script with
`execFileSync("bash", [absoluteScriptPath], { cwd: tmpRepo, env: { ...process.env,
VERCEL_GIT_PREVIOUS_SHA: <base sha> } })` and asserting on the exit code (0 = skip, 1 = build):

- `messages/ja.json` changed alone -> exit 1. The translation-only promotion from the issue.
- `i18n/request.ts` changed alone -> exit 1.
- `instrumentation-node.ts` changed alone -> exit 1. The Sentry-sampling tweak from the issue.
- `instrumentation-client.ts` changed alone -> exit 1. Proves the glob covers every hook file, not
  just the one spelled `instrumentation.ts`.
- `app/page.tsx` changed alone -> exit 1. Regression guard on the pre-existing entries.
- `docs/foo.md` (or `README.md`) changed alone -> exit 0. The guard against over-broadening: if a
  future edit drops the `.ts` suffix or otherwise widens a pattern, this is the test that fails.
- `VERCEL_GIT_PREVIOUS_SHA` unset -> exit 1 (the existing fail-open at `:8-11`).

Harness notes for whoever implements it: `git init -b main` in `fs.mkdtempSync`, commit with
`git -c user.email=... -c user.name=...` so the test does not depend on the machine's git identity,
and pass the script by absolute path while keeping `cwd` on the temp repo, since the script diffs
whatever repository it is run inside.

Gate: `npm run pre-pr` (lint -> typecheck -> build -> test -> coverage -> diff-coverage). Diff
coverage is not a factor here: `scripts/**` is excluded from the coverage `include`
(`vitest.config.ts:54`), and a `.sh` file is not instrumented at all. No e2e and no screenshot
regeneration: nothing user-facing renders differently.

What this cannot prove locally: that Vercel itself honours the new list. The first real confirmation
is the next promotion to `main` whose diff touches a newly-watched path showing a real deployment
rather than "Skipped" in the Vercel dashboard.

## Risks and unknowns

- **Over-triggering.** Every `main` push touching `messages/`, `i18n/` or an instrumentation file now
  builds. That is the intended trade and, given batched `qa -> main` promotions almost always touch
  `app/` anyway, it changes the build count barely at all.
- **The guard is still a hand-maintained list.** This fix closes three known gaps; it does not stop
  the fourth. That is what open question 2 is about.
- **Unknown, low impact: `.nvmrc` and `.npmrc` stay unwatched.** They shape the build environment
  rather than the served output, and Vercel's Node major comes from project settings and
  `package.json` (already watched), so I have deliberately left them out rather than guess.

## Open questions for Fraser

**1. Should `CHANGELOG.md` be added to `WATCH_PATHS` in the same change?**

It is the same class of gap, found while checking the others. `/whats-new` reads `CHANGELOG.md` from
the deployment bundle at render time (`lib/changelog/parse.ts:146`, traced in via
`outputFileTracingIncludes` at `next.config.ts:47-49`), so a hand-edited typo fix to `CHANGELOG.md`
alone would not reach the live page.

- **Option A:** fix exactly the three paths the issue names. Smallest diff, exactly the filed scope.
- **Option B:** add `CHANGELOG.md` as a fourth entry.

**Recommendation: B.** One line, same asymmetry, and it almost never fires in practice because the
`auto-release.yml` cut touches `package.json` in the same commit (`WORKFLOW.md:808`), so it only
bites on a manual changelog edit, which is precisely the uncovered case.

**2. How hard do we want to stop the next drift?**

- **Option A:** the allowlist patch only. Cheapest; the list will drift a third time.
- **Option B:** patch plus a drift-guard test in the same new test file, asserting that every
  top-level tracked entry (`git ls-files` at depth 1) is either in `WATCH_PATHS` or in an explicit
  `NOT_A_BUILD_INPUT` list in the test. Adding a new root-level file then fails CI until it is
  classified one way or the other. This would have caught all three of today's misses, since all
  three are root-level. Cost: a small classification ritual on every new root-level entry, and it is
  blind to a new build input nested inside an unwatched tree.
- **Option C:** invert the script to a denylist, so an unrecognised path builds by default. Fails
  safe permanently and needs no ritual, but it is a rewrite of a script that cannot be exercised
  outside Vercel, and any incomplete ignore list shows up as extra builds rather than as a visible
  error.

**Recommendation: B.** It matches the forcing-function pattern the repo already uses for
single-source-of-truth drift (AGENTS.md, the #1356 parity test), it is cheap, and it is testable
locally. C is the better end state if this recurs a third time, and the guard from B makes that
recurrence visible instead of silent.
