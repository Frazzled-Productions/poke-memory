# Plan: #1999 [monitoring] grade_log divergence detected (1 users)

## What this is

Triage of a monitoring alert, not a feature. Five findings, in the order they change the decision.

**1. This is very likely a real orphan, not an Option C false positive.** The alert escalated across four consecutive ticks for the same user (prefix `dff21628`), same single subject:

| issue | fired | arms |
|---|---|---|
| #1999 | 2026-08-13 09:16 UTC | Option C only |
| #2000 | 2026-08-14 09:10 UTC | Option A **and** Option C |
| #2001 | 2026-08-15 08:32 UTC | Option A **and** Option C |
| #2002 | 2026-08-16 08:33 UTC | Option A **and** Option C |

Option A is the strict arm: it applies both the 2-day in-step grace (#1221) and the `MAX(grade) >= 4` stuck-in-steps filter (#1253). Three consecutive Option A hits is the #584 signature the monitor exists to catch, and it is exactly the progression `check-grade-log-divergence.mjs` predicts for a genuine break ("real #584 breaks reappear in the same window the next day and the day after"). The noisy-proxy caveat in the issue body applies to Option C alone and does not survive #2000.

**2. It stopped because the window closed, not because it healed.** The arithmetic pins the subject's last grade to 2026-08-12. Option A requires `MAX(entry_date) <= CURRENT_DATE - 2`, so it could not fire on 13 Aug but did on 14 Aug. All arms floor at `entry_date >= CURRENT_DATE - 4` (`OPTION_A_LOWER_BOUND_DAYS_AGO = 4`, reused verbatim as `OPTION_C_LOWER_BOUND_DAYS_AGO`), so 16 Aug is the last day a 12 Aug grade qualifies. Nothing fired on 17 Aug, and nothing has fired since. The monitor has run daily and succeeded throughout; run `33964105142` (2026-09-05 11:43 UTC) logged `Option A: 0 ... Option B: 0 ... Option C: 0` and printed `OK`. A clean monitor today is therefore consistent with the row still being missing. The floor is a deliberate, documented blind spot (#1230).

The contrast case validates the reading: #2031 (2026-08-21, a different user, `373c9b61`) fired Option C once, carries the dedupe marker, has no recurrence comment, and never aged into Option A. That one plausibly did heal. `dff21628`'s did not.

**3. The safety net that should have healed it has never run live.** `reconcile_grade_log_orphans` (`db/migrations/032_reconcile_grade_log_orphans.sql`, #1360) is scheduled weekly, Sunday 04:00 UTC, with `p_dry_run := true`. Live activation was left as a manual dashboard step after roughly two weeks of observation from 2026-05-30, so it was due around mid-June. No migration in `db/migrations/` flips it, and `CHANGELOG.md:391` still describes it as dry-run. It also carries the same hardcoded 4-day window, so even live it would not have healed a subject last graded on 12 Aug once the following Sunday passed.

**4. The issue's own "Next steps" step 1 is wrong.** `maskUserId` is applied on every output path in `.github/scripts/check-grade-log-divergence.mjs` (all three markdown sections and the stdout JSON), and the stderr summary carries counts only. The full UUID is never written to the workflow log. Recovering the user needs a prefix match in Supabase: `WHERE user_id::text LIKE 'dff21628%'`.

**5. The duplicates are already fixed in code.** The dedupe landed in commit `9420abda` (PR #2003, 2026-08-16 17:07). #2010, which reported the duplicate-filing defect, is still open. Closing anything is a shared-GitHub-state change, so it is under Open questions.

## Files to change

Phase 0 changes no files and gates everything else. Phase 1 is contingent on Q1.

**Phase 0, diagnostic, read-only, no repo change.** Run against prod via `mcp__supabase__execute_sql`. This is the query the 4-day floor prevents the monitor from running:

```sql
WITH gl AS (
  SELECT
    user_id,
    CASE card_type
      WHEN 'evolution'         THEN 'evolution-edge'
      WHEN 'reverse-evolution' THEN 'reverse-evolution-edge'
      ELSE card_type
    END AS card_type,
    subject_key,
    locale,
    MIN(entry_date) AS first_grade,
    MAX(entry_date) AS last_grade,
    MAX(grade)      AS max_grade,
    COUNT(*)        AS grades
  FROM grade_log
  GROUP BY 1, 2, 3, 4
  HAVING MAX(grade) >= 4
)
SELECT g.*
FROM gl g
LEFT JOIN card_reviews cr
  ON cr.user_id = g.user_id AND cr.card_type = g.card_type
 AND cr.subject_key = g.subject_key AND cr.locale = g.locale
WHERE cr.user_id IS NULL
ORDER BY g.user_id, g.last_grade DESC;
```

Filter to `g.user_id::text LIKE 'dff21628%'` for the #1999 row specifically; run it unfiltered first to size the whole backlog. Also check `SELECT id FROM auth.users WHERE id::text LIKE 'dff21628%'` so an empty result can be told apart from a deleted account (`delete_account`, migration 027, cascades from `auth.users`).

## Approach

Treat #1999 as a data-repair job with a standing-safety-net gap behind it, not as a fresh bug hunt.

The reasoning is that the diagnostic evidence for a new root-cause investigation is gone and will not come back, whereas the repair is cheap and the gap is concrete. #1288 succeeded because it ran three days after its alert, while `card_reviews.updated_at` could still discriminate rows that existed at alert time. Three and a half weeks on that is impossible, and migration 043 added an `updated_at` trigger that refreshes the column on every write, so the discriminator is now strictly less useful for archaeology than it was in May. What remains recoverable is the orphan itself: `grade_log` is append-only at the DB layer (migration 018 dropped its UPDATE and DELETE policies), so the grade history that proves the card graduated is intact and the Phase 0 query will answer definitively whether the `card_reviews` row is still absent.

The gap the alert exposes is that both the detector and the healer floor at the same 4 days. An orphan whose subject goes quiet becomes invisible to the monitor and unreachable by the heal in the same week, which is exactly what happened here: four tickets, no action, then silence that reads like resolution. Making the heal actually run, with a window wide enough to reach backwards, is the durable answer. A one-off widened invocation is the cheapest way to work off the historical backlog without committing the standing weekly job to a wide window on day one.

One point in favour of widening that 032's header does not make: the placeholder's `reps`, `lapses` and `first_seen` are aggregates over the look-back window, so a wider window makes them *more* accurate, not less. And 032's stated worry about resurrecting data "superseded by a later reset" is smaller than it reads, because `reset_all_progress` (migration 018, lines 38-40) deletes `card_reviews`, `grade_log` and `streak_days` together, so a reset removes the very rows that would drive a heal.

Rejected:

- **Widening the monitor's 4-day floor.** The `#1230` note in `check-grade-log-divergence.mjs` already ruled on this: the right shape is a periodic deeper sweep, not a permanently widened floor that pays the cost on every daily tick. The heal job already is that periodic sweep. It just is not live.
- **Opening a #1288-style investigation issue.** It would start with strictly less evidence than #1288 had and no live signal to chase. If Phase 0 shows a *pattern* of orphans across multiple users rather than one row, that changes and an investigation becomes the right call.
- **The replay-correct heal.** Migration 033 landed the `learning_step` and `step_started_at` columns #1416 asked for, so the prerequisite is done and no open issue tracks the job itself. It is the correct long-term answer to the placeholder's lossiness, but it means replaying grades through `lib/srs/scheduler.ts` in a route handler, which is far more than this alert justifies. Follow-up candidate.
- **Closing #1999 as benign.** #1213 and #1224 were closed that way; #1243 and #1288 then proved the shape was real. Three Option A hits do not get closed on a hunch.

## Risks and unknowns

- **I cannot see prod from this lane.** Every claim about pg_cron state is inferred from the repo: 032's dry-run schedule, no later migration touching it, and `CHANGELOG.md:391`. If the flip was done by hand in the dashboard it left no repo trace. Run the `cron.job` query before writing the migration. If it is already live, Phase 1 collapses to the look-back question alone.
- **No PITR (#298).** Every live INSERT is one-way, and a daily-backup restore is whole-database and loses up to 24h for every user. `ON CONFLICT DO NOTHING` guarantees no existing row is mutated and `LIMIT 50` per run caps the blast radius, but rows the job writes cannot be selectively rolled back. This is the substance of Q1.
- **The placeholder heal is visibly lossy.** It writes `stability = 1.0`, `difficulty = 5.0`, `scheduled_days = 1`, `due_date = CURRENT_DATE`. Mastery is `stability >= 21` (`MASTERY_STABILITY_DAYS`), so a card the user genuinely mastered comes back as due and un-mastered until the next real review re-derives state, and it drops out of the Pasture in the meantime. For one card this is trivial; for a wide backfill it is a user-visible regression on cards the user considers finished. Size it from Phase 0's unfiltered count before choosing a window.
- **Signature-overload grant trap.** Adding `p_lookback_days` creates a *new* function, it does not replace the old one. The existing `REVOKE` statements (032 line 300 for `public, anon`; 040 line 64 for `authenticated`) name the `(boolean)` signature only, and a freshly created function grants EXECUTE to PUBLIC by default. The migration must both `DROP FUNCTION public.reconcile_grade_log_orphans(boolean)` and re-issue all three revokes against `(boolean, integer)`, or an authenticated user can call a SECURITY DEFINER writer.
- **The #2003 dedupe is unverified in production.** #2010 warned that GitHub's search index strips HTML comments, so `--search "$MARKER in:body"` may never match; the landed fix uses exactly that form. #2031 carries the marker but never recurred, so the branch has not been exercised once. Out of scope for #1999, but worth knowing that the next recurrence may still open a fresh issue. This belongs on #2010.
- **`dff21628` may be unresolvable** if the account has since been deleted; `delete_account` (migration 027) cascades from `auth.users` and removes the grade_log rows too. An empty Phase 0 result is ambiguous between healed, never real, and account gone, which is why the plan checks `auth.users` for the prefix as well.

## Open questions for Fraser

**Q1. Flip `reconcile_grade_log_orphans` live, and how wide?** The standing safety net from #1360 has been in dry-run since 2026-05-30. This is a prod-write decision with no PITR behind it, so it is yours.

- **Option A (recommended).** Run Phase 0, then land migration 048: parameterise the look-back, flip the standing weekly job live at the existing 4-day window, and separately make one supervised one-off call with a wide window (30 days, or unbounded if Phase 0's count is small) to work off the historical backlog including `dff21628`. Trade-off: the net finally runs, the standing behaviour stays as narrow and conservative as #1360 designed it, and the one risky wide pass happens once with you watching rather than every Sunday unattended.
- **Option B.** Flip live *and* widen the standing schedule to 30 days. Trade-off: actually closes the "quiet orphan is invisible forever" class this alert exposes, with no follow-up needed, at the cost of the placeholder writing over older history every week. The `LIMIT 50` per run keeps the volume bounded.
- **Option C.** Leave it dry-run, hand-heal whatever Phase 0 finds with a single targeted INSERT, close the alert. Trade-off: zero standing prod-write risk and the smallest possible change, but the safety net stays dark into its fourth month and the next `dff21628` is another four unactioned tickets.

I would take A. It is the step #1360 explicitly deferred and nobody did, it repairs the actual row this issue is about, and it does not require settling the placeholder-lossiness argument before anything ships.

**Q2. The five open alert issues and #2010.** #2000, #2001 and #2002 are the same user and subject as #1999 on consecutive ticks. #2031 is a different user and plausibly self-resolved. #2010's defect is fixed in `9420abda` but the issue is still open. Closing or commenting on any of these is a shared-GitHub-state change.

- **Option A (recommended).** Close #2000, #2001 and #2002 as duplicates of #1999; close #2010 as fixed by #2003; leave #1999 open until the heal is confirmed, and leave #2031 open until Phase 0 confirms its row is present. Trade-off: keeps the two issues that still carry an open question, at the cost of a slightly untidy board for another day.
- **Option B.** Close all five alert issues now and rely on the dedupe to re-file if the shape returns. Trade-off: tidiest board, but if `dff21628`'s row is still an orphan the 4-day floor guarantees nothing re-files it, and the trail is gone.

I would take A.
