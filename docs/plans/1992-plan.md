# Plan: #1992 investigate-ci-failure skill is a flat .md and is never discovered (needs `<name>/SKILL.md`)

## What this is

`.claude/skills/investigate-ci-failure.md` is a flat markdown file. Claude Code discovers project
skills only at `.claude/skills/<skill-name>/SKILL.md`, so the file has never been loaded and
`/investigate-ci-failure` does not exist. Three places in the repo point at it as though it does.

The fix is a `git mv` into a directory, plus the two pointer updates that the move invalidates, plus
one dead cross-reference inside the skill body that I found while reading it.

**Confirmed, not assumed.** Beyond the docs the issue cites, this session's own available-skills
listing is direct evidence: `batch-issues` and `ship` both appear (with their exact frontmatter
`description:` text), and both are flat `.md` files under `.claude/commands/`. `investigate-ci-failure`
does not appear. So flat files under `.claude/commands/` load; a flat file under `.claude/skills/`
does not. That matches the issue exactly.

## Approach

Straight `git mv` into `.claude/skills/investigate-ci-failure/SKILL.md`, content otherwise verbatim
apart from the one dead cross-reference. The skill's substance was reviewed line by line and the rest
of it still holds against the current tree: the pinned image `mcr.microsoft.com/playwright:v1.60.0-noble`
matches `@playwright/test: ^1.60.0` in `package.json`; `.claude/commands/batch-issues.md` exists;
AGENTS.md still has a "Backlog / process" section; and all three cited memory records
(`feedback_investigate_after_sweep_fail`, `feedback_perf_budget_in_planner`,
`feedback_agent_fix_full_audit`) are live entries in `MEMORY.md`.

**Rejected: move it to `.claude/commands/investigate-ci-failure.md` instead.** Tempting, because
that is the shape the repo's two other orchestration documents already use and it demonstrably
works. Rejected because skills and commands are not equivalent: a skill can be model-invoked off its
`description`, a command only fires when someone types it. This protocol's whole purpose is to fire
at a moment the orchestrator would otherwise reach for the wrong reflex, so description-matched
invocation is the point, not an extra. The issue also prescribes the skills directory directly.

**Rejected: rewrite the skill content in the same PR.** The issue's own verification note is right
that the content is unproven, but rewriting unproven content before its first real exercise is
guesswork. Fix the dead pointer, land the discoverability bug, and let the first live run tell us
what actually needs changing.

## Testing

There is no automated assertion available for "the harness loaded this skill", which is precisely
why the bug survived three months. The verification is therefore layered:

1. **`npm run lint`** - must stay green. Confirms `lint:agents-size` (AGENTS.md line/byte budget) and
   the rest of the chain are unaffected. This is a regression check only, not proof of the fix.
2. **Fresh-session discovery check (the actual proof).** Start a new Claude Code session in the repo
   and confirm `investigate-ci-failure` appears in the available-skills listing with its
   `description:` text, and that `/investigate-ci-failure` is invocable. This is the same check that
   distinguishes `batch-issues`/`ship` (present) from `investigate-ci-failure` (absent) today, so it
   is a real before/after signal, not a tautology. A malformed-frontmatter drop looks identical to
   the current bug, so this step cannot be skipped.
3. **`npm run lint:claude-skills`** (only if open question 2 is "yes"): assert it exits non-zero
   against a deliberately reintroduced flat `.claude/skills/tmp.md`, and zero after removing it.
   Test the failure direction, not just the passing one.
4. **Live exercise against a real non-converging CI failure** - see open question 1. This cannot be
   manufactured on demand and is not a gate this PR can satisfy by itself.

`npm run pre-pr` is the standard gate, but note that for a `.claude/**`-only diff the diff-coverage
leg has no product lines to measure, so a clean run here proves less than usual. Step 2 is the
load-bearing check.

## Risks and unknowns

- **The fix is unverifiable in CI.** Nothing in `.github/workflows/` inspects `.claude/`, and the
  proposed lint can only check the directory shape, not whether the harness parsed the frontmatter.
  A skill that loads with broken frontmatter fails silently, exactly as this one has.
- **`allowed-tools` as a YAML array is proven for commands, not for skills.** `.claude/commands/ship.md`
  and `.claude/commands/batch-issues.md` both use the `[Bash, Read, ...]` array form and both load,
  so the harness tolerates it there. Some skill documentation shows a comma-separated string instead.
  If the skill fails to appear after the move, this is the first thing to try changing. The issue's
  claim that the frontmatter needs no change is right about the `Agent` rename but does not settle
  the array-versus-string question.
- **`TaskCreate` / `TaskUpdate` / `TaskList` in `allowed-tools` may be stale names.** They are not in
  this session's tool set. `batch-issues.md` lists the same three and still loads, so unknown names
  appear to be tolerated rather than fatal, but the skill may end up without working to-do tooling.
  Worth an eye during step 2, not worth blocking on.
- **The content has never run.** The issue says this and it stands. Treat the first invocation as a
  shakedown, not a trusted procedure.
- **Minor content drift already visible.** `docs/testing.md:62` still documents the e2e projects as
  `chromium` + `mobile-safari`, but `package.json`'s `test:e2e` now runs four (`chromium`,
  `mobile-safari`, `desktop-webkit`, `mobile-chrome`). The skill's example command hardcodes
  `--project=chromium`. Not wrong, but narrower than the suite. Out of scope here; it is a
  `docs/testing.md` accuracy issue and belongs in its own issue if you want it chased.

## Open questions for Fraser

**1. Does this PR block on a live exercise of the skill?**

- (a) Land the move now, verify discovery only, and file a follow-up to run the protocol against the
  next real non-converging CI failure.
- (b) Hold the PR open until a red CI turns up and drive the protocol through it before merging.

Recommendation: **(a)**. Trade-off: the content stays unproven, so the first real use may find gaps
in the procedure itself. But (b) blocks a correct, three-line fix on an unschedulable event, while
every CI investigation between now and then keeps falling back to the sweep-agent reflex the skill
exists to replace. Landing (a) at least makes the skill reachable when the moment arrives.

**2. Add a forcing-function lint for the skills directory shape?**

- (a) Add `scripts/lint-claude-skills.mjs` to the `lint` chain in this PR: fail if any `.md` sits
  directly under `.claude/skills/` rather than at `<name>/SKILL.md`.
- (b) Skip it; the move alone closes the issue.

Recommendation: **(a)**. It is roughly 30 lines and matches how this repo handles exactly this class
of silent-drift bug (`lint:i18n`, `lint:pseudo-locale`, `lint:agents-size`, the `no-restricted-syntax`
ban from #1327). Trade-off: it grows the lint chain for a directory containing one file today, and it
can only catch the shape, not a frontmatter parse failure, so it would not have caught every way this
skill could go invisible.

**3. Do `/batch-issues` and `/ship` converge on the skills layout too?**

They live in `.claude/commands/` but `AGENTS.md:201` calls them "skills", so the repo's vocabulary
and its layout disagree.

- (a) Leave them where they are; fix nothing.
- (b) Convert both to `.claude/skills/<name>/SKILL.md` for one location and one vocabulary.

Recommendation: **(a)**, and out of scope for this PR either way. Trade-off: the repo keeps two
locations and the loose AGENTS.md wording. But both files demonstrably load today, and converting
them is a behaviour change rather than a tidy-up: skills can be model-invoked off their description,
and `/batch-issues` auto-firing because a prompt smelled like a backlog drain would be considerably
worse than the current inconsistency.
