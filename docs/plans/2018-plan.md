# Plan: #2018 docs/persistence.md and AGENTS.md list 4 tables; the schema has 8

## What this is

Two prose inventories of the Supabase schema are four tables behind, and the invariant
stated alongside them ("all FK'd to `auth.users(id) ON DELETE CASCADE`") is no longer true.
The fix is a docs refresh in both files plus a forcing function so the list cannot silently
drift again.

Every claim in the issue was re-verified against this working copy:

- `grep -rniE "create table (if not exists )?(public\.)?[a-z_]+" db/migrations/` returns eight
  tables: `card_reviews`, `streak_days`, `user_settings` (001), `grade_log` (006),
  `push_subscriptions` (028:78), `feedback` (034:15), `usernames` (035:22),
  `rate_limit_buckets` (041:39).
- No `DROP TABLE` and no `ALTER TABLE ... RENAME` anywhere in `db/migrations/`, so the set is
  purely additive to date.
- `rate_limit_buckets` has no `user_id` (keyed on `ip_hash`, 041:39-44); RLS on, no client
  policies, all writes via the `SECURITY DEFINER` `check_rate_limit` RPC (041:49-52).
- `feedback.user_id` is nullable (034:17); RLS on, no client write policy, and migration
  040:61 later added an explicit deny-all `feedback_no_client_select`.
- `usernames` is PK'd on `username` with `user_id NOT NULL` FK cascade (035:22-37); its open
  SELECT policy was dropped in 044.
- `push_subscriptions` is a conventional per-user table: `user_id NOT NULL` FK cascade, plus
  SELECT / INSERT / DELETE policies (028:78-105).

Two further stale copies of the same inventory exist beyond the two the issue names. See
"Open questions for Fraser".

## Files to change

Existing files:

- `docs/persistence.md` - line 5: replace the four-name inventory with all eight, and split
  the one-sentence RLS/FK claim into an accurate form (per-user tables FK'd with cascade;
  `feedback.user_id` nullable; `rate_limit_buckets` has no `user_id` at all, by design). Line
  50 ("Reference shapes"): add the three precedents a planner currently cannot see -
  `rate_limit_buckets` (service-role-only internal table, RLS on with no client policies),
  `feedback` (write-once, append-only, service-role write path), `usernames` (uniqueness
  constraint table). This is the doc the AGENTS.md pointer routes persistence decisions to,
  so the precedents belong here rather than in a new file.
- `AGENTS.md` - line 112: same eight-name inventory. Keeps the list inline (it is loaded every
  session, so a sub-agent sees it without a file read); the guard below is what keeps the two
  copies honest. Byte budget: the file is 24397/26624 bytes and 206/240 lines against
  `scripts/lint-agents-size.mjs`, so ~200 extra bytes is comfortable but the byte ceiling is
  the tighter of the two.
- `package.json` - add `"lint:tables": "node scripts/check-table-inventory.mjs"` and chain it
  into the existing `lint` script alongside `lint:i18n` / `lint:agents-size`.

New files:

- `scripts/lib/table-inventory.mjs` (NEW) - pure helpers, no I/O: `tablesFromMigrationSql(sql)`
  (strip `--` comments, match `CREATE TABLE [IF NOT EXISTS] [public.]<name>`, ignore any
  schema-qualified name that is not `public.`, apply `DROP TABLE` removals in file order) and
  `tablesFromInventoryLine(markdown)` (find the single line containing `Tables today:`, return
  the backticked identifiers). Mirrors the `scripts/lib/changelog-fragment.mjs` split, which
  exists so the same parser can be unit-tested and reused.
- `scripts/lib/table-inventory.test.mjs` (NEW) - unit tests. `vitest.config.ts` already
  includes `scripts/**/*.test.mjs` in the `node` project, so no config change is needed.
- `scripts/check-table-inventory.mjs` (NEW) - reads `db/migrations/*.sql` in sorted order,
  derives the set, compares against the inventory line in `docs/persistence.md` and
  `AGENTS.md`, prints missing/extra per file, exits 1 on mismatch. Imports only Node built-ins,
  matching `check-node-version-drift.mjs`. Note `scripts/**` is in scope for
  `scripts/check-no-em-dash.mjs`, so comments and strings in these three files must avoid the
  em-dash glyph.

No `db/migrations/**` change, so the "run the integration suite before push" rule in AGENTS.md
does not apply here.

## Approach

**Derive the list from the migrations at check time; do not add a second source of truth.**
A `tables.json` manifest alongside `coverage-floor.json` was the obvious alternative and is
rejected: it is one more file that can go stale, and the schema already *is* the source of
truth. The script re-runs the issue's own grep in code.

**Anchor the guard on the existing `Tables today:` sentence rather than HTML markers.** Both
files already carry that literal string, so the guard costs zero new lines in AGENTS.md (where
the byte budget is 92% consumed). The `<!-- BEGIN:... -->` marker pair used for
`nextjs-agent-rules` in AGENTS.md was the alternative; it is more explicit but adds four lines
of comment noise across the two files for no extra safety, because the script already fails
loudly when the anchor is missing or matches more than once.

**Keep the inventory a flat alphabetical sentence; put the shape guidance on line 50.** A
richer per-table Markdown table in `docs/persistence.md` was considered and rejected: it
duplicates what `.claude/agents/supabase-expert.md` already does per table, and it would make
the guard parse a table rather than a sentence. The existing "Reference shapes" line is the
right home for "here is the precedent to extend", which is the actual complaint in the issue.

**Wire the check into the `lint` chain, not a standalone drift workflow.** The
`node-version-drift.yml` / `scope-lookup-drift.yml` model looks like the closer precedent, but
those workflows are not required checks on `qa` (required checks there are `test` and `e2e`),
so a red drift job would not stop auto-merge from landing exactly the drift we are guarding
against. `npm run lint` runs inside the `test` job (`ci.yml:89`) and inside `npm run pre-pr`,
which makes it blocking in both places.

Known gap, accepted deliberately: `ci.yml`'s `changes` filter marks docs-only PRs as
`code != true`, so the `test` job's inner steps (including lint) are skipped. A PR that adds a
migration always trips `code`, so the primary failure mode is covered; a docs-only PR that
deletes a name from the list is not caught until the next code PR. Closing that would mean
re-including `docs/persistence.md` and `AGENTS.md` in the `code` filter, which makes every
docs-only PR pay the full ~10 minute test job and touches `.github/workflows/**` (mandatory
workflow-expert review, no mechanical-change exception). Not worth it for this change.

**No `--fix` mode.** The correct new-table entry needs prose judgement about which precedent
group it belongs to; auto-inserting a name would encourage skipping that.

## Testing

- `scripts/lib/table-inventory.test.mjs` (new, `node` vitest project). Cases against inline SQL
  fixtures: bare `CREATE TABLE x`; `CREATE TABLE IF NOT EXISTS x`; `CREATE TABLE public.x`;
  a `-- CREATE TABLE commented_out` line is ignored; `CREATE TABLE auth.users` (the
  `lib/sync/integration/setup.ts:141` shape) is ignored as non-public; a later `DROP TABLE x`
  removes an earlier create; ordering across files is respected. For the inventory parser:
  extracts every backticked name from the `Tables today:` line; throws when the anchor is
  absent; throws when the anchor appears twice.
- Comparison behaviour: a fixture where the doc omits one table yields a non-empty "missing"
  list, and one where the doc names a table no migration creates yields a non-empty "extra"
  list. Assert on the returned diff, not on process exit, so the pure module stays testable.
- Real-repo positive check: `npm run lint:tables` exits 0 against the updated
  `docs/persistence.md` and `AGENTS.md`.
- Real-repo negative check (manual, recorded in the PR body): delete one name from the
  `docs/persistence.md` line, confirm exit 1 and that the message names the file and the
  missing table, then restore.
- `npm run lint` end to end, which also re-runs `lint:agents-size` against the grown AGENTS.md
  and `lint:em-dash` against the three new script files.
- `npm run pre-pr` as the gate. `vitest.config.ts` excludes `scripts/**` from the coverage
  `include` list (only `app/**`, `components/**`, `lib/**` are instrumented), so the new script
  should not move the coverage floor or the diff-coverage gate; confirm on the actual run
  rather than assuming.
- Not run: `VITEST_INTEGRATION=1 npm run test:integration`. No SQL changes, so the AGENTS.md
  trigger for it does not fire.

## Risks and unknowns

- **Regex fragility.** The parser handles the four `CREATE TABLE` spellings present today.
  It does not handle a table created inside a `DO $$ ... $$` block, a quoted identifier
  (`CREATE TABLE "Foo"`), or `ALTER TABLE ... RENAME TO`. None exist in `db/migrations/` today
  (verified by grep). A future migration using one of those forms would make the guard silently
  wrong rather than loudly wrong, which is the worse failure direction. Mitigation: state the
  supported forms in the script header, and keep the failure message pointing at the parser so
  the next maintainer knows where to look.
- **The guard hard-codes which files carry an inventory.** If a fifth file grows a "Tables
  today" list, it is unguarded until someone adds it to the script's file list. Cheap to
  extend, but it is a manual step.
- **Prose accuracy has no forcing function.** The guard checks the *set of names* only. The
  corrected FK/RLS sentence can still go stale (for example if a future migration adds another
  table with no `user_id`) and nothing will catch it. That is an accepted limit: the issue's
  measurable complaint is the name list.
- The two Supabase projects and `migration-check.yml` are untouched by this change.

## Open questions for Fraser

**1. Ship the forcing function in this change, or docs-only now?**

The issue frames the guard as "worth considering", which makes it a scope call rather than
mine.

- *Option A (recommended): docs fix plus the guard in one PR.* The list went stale across four
  migrations without anyone noticing, so a docs-only fix has a known half-life. Cost is roughly
  three small script files, one `package.json` line, and a unit-test file.
- *Option B: docs-only now, guard as a follow-up issue.* Smaller diff, faster to land, and
  keeps a doc correction from carrying tooling risk. The cost is that the follow-up may sit in
  the backlog while the next migration lands.

Trade-off: A is more work now and adds a permanent lint step (fast, no `npm ci` dependency);
B is minimal now and re-opens the same drift window.

**2. How wide should the refresh go? There are two more stale inventories the issue does not
name.**

- `.claude/agents/supabase-expert.md:46-48` - a "### Schema today" section opening "Four tables
  in `public`. All RLS-on. All FK'd to `auth.users(id) ON DELETE CASCADE`." This is the agent
  that *designs* schema, so it is arguably the highest-impact copy of the wrong list.
- `WORKFLOW.md:45` - the roster row for `supabase-expert` names the same four tables.

Options:

- *Option A (recommended): fix the inventory lines in all four files, and cover all four in the
  guard.* One pass, one guard, no known-stale copy left behind. Cost: the diff touches
  `.claude/agents/**`, where AGENTS.md routes non-trivial changes to workflow-expert review.
  An inventory-line edit is arguably trivial, but that is a judgement I should not make
  unilaterally.
- *Option B: stay inside the issue's two files and file a second issue for the other two.*
  Keeps this PR exactly as scoped and lets the Porter loop pick the rest up, at the cost of
  leaving the agent definition wrong for however long that takes.

Separately, and recommended either way: `.claude/agents/supabase-expert.md:50-52` describes
`card_reviews` as `UNIQUE (user_id, pokemon_id)` with "No `card_type` column", which migrations
010 (string keys) and 029 (locale in the PK) made wrong. That is a column-shape staleness, not
a table-inventory one, and it is a bigger correctness problem than #2018. It wants its own
issue rather than being folded in here.

Also noted, and recommended out of scope: `docs/dpia.md` says "all four tables" at lines 190,
221 and 254. Read narrowly those sentences are about the per-user data tables and are not
wrong, but the phrasing invites the same misreading. It is a compliance document under
privacy-expert review, so it should be a separate, privacy-reviewed change rather than a
drive-by edit here.
