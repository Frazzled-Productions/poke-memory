# Plan: #2076 next.config.ts assumes a webpack build, but Next 16 builds with Turbopack, so the Sentry debug-logging strip does nothing

## What this is

A build-config fix with one real change and one comment fix. The issue's diagnosis holds up against the code:

- `package.json:12` runs a plain `next build`, and Next 16 builds with Turbopack by default (`node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md:114-118`, `node_modules/next/dist/docs/01-app/03-api-reference/08-turbopack.md:39`). I took the CI log line (`▲ Next.js 16.3.1 (Turbopack)`) from the issue and did not re-check it.
- `@sentry/nextjs` reads `webpack.treeshake.removeDebugLogging` in one place only: `setupTreeshakingFromConfig` in `build/cjs/config/webpack.js:549-570`, which adds a `DefinePlugin` setting `__SENTRY_DEBUG__ = false`. That code runs only through `getWebpackPatch`, and `getWebpackPatch` returns `{}` unless the active bundler is webpack (`build/cjs/config/withSentryConfig/getFinalConfigObjectBundlerUtils.js:156`). The Turbopack path (`build/cjs/config/turbopack/constructTurbopackConfig.js`) sets no defines.
- `@sentry/core` controls its debug logging with `DEBUG_BUILD = (typeof __SENTRY_DEBUG__ === 'undefined' || __SENTRY_DEBUG__)` (`build/esm/debug-build.js:1`). Nothing defines that flag today, so the debug-logging code ships.
- None of the Sentry setup files (`instrumentation.ts`, `instrumentation-node.ts`, `instrumentation-client.ts`) passes `debug: true`. Runtime behaviour is therefore the same either way. The only effects of this bug are extra bytes in the client bundle and a comment that says the opposite of what the build does.
- Source-map upload does still work under Turbopack, so the note at `next.config.ts:137-139` is wrong about that too. Under Turbopack, `useRunAfterProductionCompileHook` defaults to true (`getFinalConfigObjectBundlerUtils.js:43-45`). That hook installs `compiler.runAfterProductionCompile` to do the upload (lines 46-76), and `maybeEnableTurbopackSourcemaps` switches on `productionBrowserSourceMaps` (lines 103-126).

**Where these readings come from.** The worktree has no `node_modules`, so I read the main checkout's copy. That copy has `@sentry/nextjs` 10.65.0, which matches the lockfile. Its `next` is 16.2.9, but the lockfile pins 16.3.1. The implementer should re-check the two Next files cited below (`define-env.js`, `config-shared.d.ts`) after `npm ci`.

## Files to change

- `next.config.ts`: four edits.
  - Add `compiler: { define: { __SENTRY_DEBUG__: false } }` to `nextConfig`, with a comment. This is the Turbopack-compatible replacement (see Approach).
  - Remove the `webpack: { treeshake: { removeDebugLogging: true } }` block from the `withSentryConfig` options. It does nothing under this build.
  - Rewrite the comments at lines 115-116 ("so it can instrument webpack fully"), 124-127 (the `webpack.treeshake.removeDebugLogging` entry) and 149-151 so they describe the Turbopack build.
  - Replace the NOTE at lines 137-139. It should say that the build uses Turbopack, that source maps upload through the `runAfterProductionCompile` hook, and that `webpack.*` options passed to `withSentryConfig` do nothing under this build and trigger no warning.
- `changelog.d/unreleased/2076-sentry-debug-strip-turbopack.md` (new): a `kind: fixed` fragment, only if the `compiler.define` change lands, e.g. "Sentry SDK debug-logging code is now stripped from the production bundle under Turbopack builds." If only the comment and option removal land, skip the fragment: nothing a user would notice changes.
- No test files change. The Testing section explains why.

## Approach

**Use Next's `compiler.define` to set `__SENTRY_DEBUG__` to `false`.** The evidence that this works under Turbopack:

- The Next compiler docs (`node_modules/next/dist/docs/03-architecture/nextjs-compiler.md:263-282`) describe `compiler.define` as applying to "all environments (server, edge, and client)".
- `node_modules/next/dist/build/define-env.js:51` builds the define map in `getDefineEnv({ isTurbopack, ... })` and merges `config.compiler.define` into it at lines 204-214. That is the same code for both bundlers, unlike the Sentry option.
- The type is `define?: Record<string, string | number | boolean>` (`node_modules/next/dist/server/config-shared.d.ts:1138`), so a boolean passes the type check.

Details the implementer must get right:

1. **The value must be the boolean `false`, not the string `'false'`.** `serializeDefineEnv` passes every value through `JSON.stringify` (`define-env.js:23-29`). The string `'false'` would therefore be inlined as the literal `"false"`, which is truthy, and the debug code would stay without any warning.
2. **Put it on `nextConfig` (the inner object), not in the Sentry options.** Sentry edits `compiler` in place and only adds `runAfterProductionCompile` when it is absent (`getFinalConfigObjectBundlerUtils.js:61-64`), so our `define` and Sentry's upload hook can sit side by side. Do not set `compiler.runAfterProductionCompile` ourselves.
3. **`define` also reaches server and edge bundles.** That matches the old webpack intent, since Sentry added the `DefinePlugin` to every webpack build. It does mean a future `debug: true` in any `Sentry.init` would print nothing, and the new comment must say so, so that nobody spends time debugging a silent debug flag.
4. **Name clash.** If a define key already exists as a Next built-in, Next throws error E688 (`define-env.js:206-212`). `__SENTRY_DEBUG__` is not a built-in, but the build will show it if that changes.

**Open technical point, settled by the build check below.** I could not confirm from the in-repo docs whether Turbopack's define step also rewrites `typeof __SENTRY_DEBUG__`. If it only rewrites the bare name, then `typeof __SENTRY_DEBUG__ === 'undefined'` stays true at runtime, and nothing is stripped even with the define in place. Webpack's `DefinePlugin` does rewrite `typeof`; for Turbopack I can't say. So:

- **If the debug marker disappears from the client chunks,** ship all of it: the define, the option removal, and the comment rewrite.
- **If the marker stays,** ship only the option removal and the comment rewrite, which is the issue's "drop it" option. The comment should then say that this SDK version has no Turbopack equivalent. File a follow-up issue to revisit when `@sentry/nextjs` adds a Turbopack-native option.

**Draft wording for the replacement NOTE** (the implementer can tighten it):

> The build uses Turbopack (the Next 16 default for a plain `next build`). `withSentryConfig` uploads source maps from its `compiler.runAfterProductionCompile` hook, which it installs by default under Turbopack and which needs no webpack plugin. Options under the `webpack` key of the Sentry options do nothing under this build, and nothing warns about them: put build-time behaviour in `nextConfig` (e.g. `compiler.define`) or in a Turbopack-aware Sentry option instead.

**Rejected alternatives:**

- **Build with `next build --webpack`.** This reverses the Next 16 default, slows builds, and other code already assumes Turbopack (`scripts/seed-pokemon.mjs:1316` sizes seed chunks around Turbopack's inlining; `AGENTS.md:165` notes the build needs Turbopack on Node 24). That is too much disruption for a bundle-size saving.
- **Keep `webpack.treeshake` in case someone builds with `--webpack`.** An option that does nothing but reads as if it works is exactly what the issue complains about (its point 3).
- **A `turbopack.rules` string-replace loader over `@sentry/core`.** It is fragile, needs a new dev dependency (`string-replace-loader`, which would need vendor screening), and depends on the SDK's internal code.
- **`compiler.removeConsole`.** It does a different job: it removes `console.*` calls from application code, not `node_modules`, and Sentry's debug logger is not a plain `console` call.

## Testing

There are no unit tests to add. `next.config.ts` is build config that no vitest project includes (`vitest.config.ts:82-100`), and a test of the config object's shape would not show that the bundler strips anything. Only the build output can prove it.

Run everything under Node 24 (`PATH=/opt/homebrew/opt/node@24/bin:...`), after `npm ci`.

1. **Baseline on `origin/qa`, before the change:**

   - Run `grep -rl "Integration installed:" .next/static/chunks`. The string comes from a debug-only log in `@sentry/core/build/esm/integration.js:86`. Expect at least one match, which confirms the issue.
   - Repeat the grep for `"Integration skipped because it was already installed"` (same file, line 58) as a second marker.
   - Record the size of `.next/static/chunks` (`du -sk .next/static/chunks`) and the output of `npm run check:bundle`.
2. **After the change:** repeat step 1.
   - Expect no matches for either marker in `.next/static/chunks`, and a smaller chunks total.
   - Put the before and after numbers in the PR body.
   - Also grep `.next/server`, for information only.
3. **Build log:** check that it still says Turbopack, that there is no E688 error, and that there are no new Sentry warnings.
4. **`npm run check:bundle` is necessary but not enough on its own.** It only guards against the Pokémon seed leaking into a chunk and prints the size of the largest chunk (`scripts/check-bundle-size.mjs`). It measures nothing about Sentry, so the grep in step 2 is the real proof.
5. **`npm run pre-pr`:** the full local gate (lint, typecheck, build, test, coverage, diff-coverage). Its lint step includes `lint:em-dash`, which covers the new comments.
6. **Smoke test:** run `npm run start`, load the home page and check for console errors. `e2e/error-boundary.spec.ts` (driven by `app/test-error/page.tsx`) exercises the Sentry-wrapped error path in CI's e2e job.
7. **Source-map upload** (the issue's "confirm once" item) needs a different check from the one the issue suggests: see Risks.

## Risks and unknowns

- **Turbopack may not rewrite `typeof`,** as described in Approach. The fallback is already defined, so this cannot block the PR, only shrink it.
- **The upload check the issue suggests won't work as written.** `silent: true` (`next.config.ts:145`) hides Sentry's build output, so a Vercel build log may show no upload step even when the upload succeeds. Better checks:
  - look for the preview deploy's release and artifact bundle in the Sentry project;
  - or run a one-off preview build with `silent: false` and don't merge it.

  Either check also depends on `SENTRY_AUTH_TOKEN` being set on Vercel. `CHANGELOG.md:150` says Sentry was "wired inert until the maintainer provisions the DSN and auth token", and I can't tell from the repo whether that has happened since.
- **Version drift** between what I read (Next 16.2.9) and what CI builds (16.3.1). This is low risk, but see "Where these readings come from" above.
- **Sentry's web docs were not checked**, because this lane has no web access; the plan relies on the installed SDK source. A later `@sentry/nextjs` release may add a Turbopack-native option for this. If so, the implementer should switch to it and drop `compiler.define`.
- **Review routing.** No `.github/workflows/**` or `.claude/agents/**` changes, so no workflow-expert review is needed. Because this touches Next config, a quick next16-expert check of the `compiler.define` usage before implementing fits the roster, then `code-reviewer` on the diff as usual.
