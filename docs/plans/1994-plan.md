# Plan: #1994 Migrate batch-issues.md to a skill for progressive disclosure

## What this is

Move `.claude/commands/batch-issues.md` (345 lines) and `.claude/commands/ship.md` (41 lines) to
the skills layout (`.claude/skills/<name>/SKILL.md`), deleting each command file in the same commit
so a skill and a command never share a name, and update the handful of files that cite the old
paths. Optionally split part of the batch-issues body into one-level-deep reference files.

**Read this first, because it changes the value case.** The issue quotes the docs line "a skill's
body loads only when it's used" and reads it as the win. That line contrasts skills with
`CLAUDE.md`, not with commands: a command body already loads only on invocation, so migrating buys
no lazy-loading that we do not already have. What migration actually adds is three things, all
modest:

1. `disable-model-invocation: true`, which drops the skill's `description` from every session's
   startup context. That is the only measurable context saving on the table, and it comes with a
   behaviour cost (see Open questions).
2. A directory to hold reference files, so a long body can be split by phase.
3. Model auto-invocation, which for these two commands we would be turning off, not on.

Everything else in the issue (the `allowed-tools` carry-over, `Agent` already being the current
tool name) is a no-op. The work is small and low-risk if scoped to the move; the risk lives entirely
in how aggressively we split the body. Nothing here is broken today, which the issue says outright.

## Approach

**Two commits, one PR into `qa`.** Commit one migrates `batch-issues` and updates its referrers;
commit two migrates `ship`. Migrating one at a time is the issue's own caution, and it keeps each
commit reviewable as what it is: a file move plus a link fix. Do the moves with `git mv` so the diff
renders as a rename and a reviewer can see at a glance that no prose changed.

**Reject `context: fork` plus `agent` for both files.** The issue lists it as a field worth picking
up. It is wrong for these two. `/batch-issues` is an orchestrator: it dispatches sub-agents, runs
ground-truth heartbeats against their worktrees, and takes over stalled ones by editing their
branches directly. Running it in a forked subagent context puts the orchestrator behind the same
opacity barrier that its own Implementation step 1 spends four paragraphs warning about ("a
sub-agent's intermediate output does not stream to the main chat, so a stall is indistinguishable
from normal quiet work"). `/ship` inherits the same review and gate machinery. Neither should fork.

**Keep `allowed-tools` semantically identical, but check two entries in passing.**
`batch-issues.md` line 3 lists `TaskCreate`, `TaskUpdate`, `TaskList`, which are not tools this
runtime exposes, and does not list `TodoWrite`, which `.claude/settings.json` wires a `PostToolUse`
hook to (`mirror-todos-to-comment.sh`). If `allowed-tools` is a genuine allow-list rather than a
prompt-suppression list, that combination means the todo-mirror hook can never fire during a
`/batch-issues` run. Verify the semantics before changing anything; if it is an allow-list, swapping
the three stale names for `TodoWrite` is a one-line fix in a file we are already rewriting.

**On splitting the body, the conservative read.** Of the four blocks the issue names as reference
candidates, only one is big: Pre-flight is 93 lines, the agent-liveness rules in Implementation step
1 are 21 lines, the coverage-ratchet mechanics are 22 lines, and the `gh pr checks --required`
guidance is 3 lines. Splitting a 3-line block into its own file costs more than it saves. The
authoring guidance the issue cites recommends splitting past a 500-line SKILL.md, and this file is
345. So the case for splitting rests on in-run ordering, not on the size ceiling, and it is bought
at the price the issue itself flags: a partially-read reference file on a command whose failure mode
is a skipped gate. Recommendation is in Open questions, because how much risk to take for how much
saving is a scope call, not a HOW call.

## Testing

There is no automated coverage of `.claude/**` anywhere in this repo. `check-no-em-dash.mjs` has
`.claude` in its `SKIP_DIRS` and only scans `changelog.d` and `CHANGELOG.md` for markdown;
`lint-agents-size.mjs` reads `AGENTS.md` alone; nothing else touches the directory. So the gate is
manual plus two greps, and that gap is itself worth deciding about (Open questions, Q3).

1. **`npm run pre-pr`.** Only the `AGENTS.md` and `WORKFLOW.md` edits are in its blast radius, and
   both are one-line path swaps, so this should be uneventful. It proves `lint:agents-size` still
   passes after the AGENTS.md edit.
2. **No stale command paths.** `git grep -n '\.claude/commands/'` must return nothing. This is the
   check that catches the half-migration case: a surviving command file silently wins or loses
   against a same-named skill depending on which way round precedence goes, and the tree gives no
   signal either way.
3. **Every relative link resolves from the new depth.** For each markdown link in
   `.claude/skills/**/*.md`, confirm the target exists. Three links change depth: SKILL.md line 28
   to `../../../WORKFLOW.md`, and ship's two to `../batch-issues/SKILL.md`. A broken link here is
   exactly the silent-gate-skip failure mode, so check it explicitly rather than by eye.
4. **Both slash commands still resolve, in a fresh session.** Start a new Claude Code session in the
   repo and confirm `/batch-issues` and `/ship` are invocable and load the new SKILL.md. If
   `disable-model-invocation: true` is applied, additionally confirm the skill is still reachable by
   typing the slash command while its description is absent from the startup listing. Do this before
   merging, not after: the whole change is a no-op if the files stop resolving.
5. **If Pre-flight is split out, prove the reference file actually loads.** Run `/batch-issues` far
   enough to observe it performing the Pre-flight work (the `gh issue list` backlog query and the
   `git rev-list --left-right --count origin/main...origin/qa` check), then stop. A run that skips
   straight to planning is the regression this issue's own Caution section warns about, and no grep
   will catch it.
6. **Manual read for em dashes** in the two new SKILL.md files, since `lint:em-dash` does not cover
   `.claude/**`. Four exist in the current batch-issues body and would otherwise travel unchanged.

## Risks and unknowns

- **`/investigate-ci-failure` appears to be dead already, and for this exact reason.**
  `.claude/skills/investigate-ci-failure.md` is a flat `.md` directly under `.claude/skills/`, not
  `.claude/skills/investigate-ci-failure/SKILL.md`. Skills on this machine (checked against the
  installed `apple-hig-skills` plugin) are directories containing `SKILL.md`, matching the docs the
  issue quotes. In this session's available-skills listing, `batch-issues` and `ship` both appear
  and `investigate-ci-failure` does not, and its frontmatter carries nothing that would hide it
  (just `name`, `description`, `allowed-tools`). So the command is very likely not registered at
  all, while `AGENTS.md` line 200 and `batch-issues.md` lines 207 and 230 all route work to it.
  Worth a ten-second confirmation (type `/investigate-ci-failure` in a fresh session) before acting
  on it. It is also a warning about this change: a layout mistake here fails silently and stays
  unnoticed for months.
- **Partial reads of reference files.** The issue's own Caution. `/batch-issues` exists to stop
  gates being skipped, so a reference file that gets partially read is a worse failure than a long
  inline body. This is the argument for splitting little or nothing.
- **The file carries dead instructions that a verbatim move would enshrine.** `auto-review.yml` was
  removed in #2003 and is absent from `.github/workflows/`, which AGENTS.md line 200 records. But
  `batch-issues.md` still devotes Pre-flight step 2, Wrap-up steps 1 and 8, a guardrail, and part of
  the Implementation step 3 note to disabling and re-enabling it, including the hard instruction
  "the run MUST NOT progress to dispatching any implementer until Auto Review is disabled" with an
  escalate-to-the-maintainer path when the command fails. `gh workflow disable "Auto Review"` now
  fails permanently, so a literal reading of the live command file stalls the run before it starts.
  `WORKFLOW.md` lines 100 and 102 repeat the same dead protocol. This is a real bug independent of
  #1994; see Q3.
- **Timing against other porter branches.** Several plan branches are in flight in this worktree
  set. If any of them edits `AGENTS.md` or `WORKFLOW.md`, expect a trivial conflict on the path
  lines. Branch off the latest `origin/qa` at implementation time.
- **Unknown: whether `disable-model-invocation` affects slash resolution.** The issue asserts the
  description stops occupying startup context while the command stays user-triggered. Plausible, but
  worth confirming empirically (test 4) rather than trusting, since getting it wrong makes
  `/batch-issues` unreachable.

## Open questions for Fraser

**Q1. How much of the batch-issues body should move into reference files?**

- (a) **No split.** Migrate the layout only: same body, new path, plus the frontmatter fields.
- (b) **Split Pre-flight only** (lines 30 to 122, about 93 lines), leaving SKILL.md at roughly 250
  lines and everything gate-critical inline.
- (c) **Split all four blocks the issue names**, giving a SKILL.md of about 205 lines and four
  reference files, one of which would be 3 lines long.

Recommendation: **(b)**. Pre-flight is the one block big enough to be worth a file, it is genuinely
phase-scoped (it runs once, before anything else, and is never revisited), and it is the block
whose steps are self-contained checks rather than rules the rest of the file depends on. (c) buys
about 45 more lines of deferral and spends it on three files, one of them absurdly small, on a
command whose documented failure mode is skipping a step. (a) is defensible if you would rather the
whole change be a pure `git mv`; say so and I will do that instead.

**Q2. Set `disable-model-invocation: true`, and on which file?**

The saving is real but small: two `description` lines out of every session's startup context. The
cost is specific. `batch-issues.md` line 17 documents its own trigger as "User says
`/batch-issues`, 'work through the backlog', 'implement all the open issues', or any variant" and
`ship.md` line 12 does the same for "ship this one issue", "do #N and open a PR". Those
natural-language triggers only work through model invocation. Turning it off means the skill fires
only on the literal slash command, and the "When to use" section becomes partly aspirational.

Recommendation: **set it on neither, for now**, and treat the reference-file directory as the
migration's whole benefit. If the startup context saving matters more than the natural-language
triggers, the next-best option is to set it on `ship` only (the narrower, always-deliberate one) and
delete the natural-language trigger wording from its "When to use" section in the same change, so
the file does not promise behaviour it no longer has. Please pick, since this is a change to how
you invoke your own tooling.

**Q3. Fold the three adjacent defects into this PR, or file them?**

House default is to file an issue rather than fix inline, but two of these are one-line structural
fixes inside files this change already rewrites.

- (i) `.claude/skills/investigate-ci-failure.md` to
  `.claude/skills/investigate-ci-failure/SKILL.md`. One `git mv`, in the directory we are already
  restructuring, and it plausibly resurrects a command that three other files route work to.
- (ii) The stale `allowed-tools` entries (`TaskCreate` / `TaskUpdate` / `TaskList` for `TodoWrite`),
  in the frontmatter we are already rewriting.
- (iii) The dead Auto Review protocol across `batch-issues.md` (five places) and `WORKFLOW.md`
  (lines 100 and 102).

Recommendation: **fold in (i) and (ii), file (iii) separately.** (i) and (ii) are structural and
keep the diff a move; (iii) is prose surgery across two files and would bury the rename under
content edits, which defeats the point of a reviewable move. (iii) is also the one with actual
operational bite: it stalls a `/batch-issues` run at Pre-flight step 2 today, so it wants its own
issue at a real priority rather than `priority:later`. Tell me if you would rather all three were
issues, and I will file three and keep this PR to the move alone.
