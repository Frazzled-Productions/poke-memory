# Plan: #2073 Streak nudge: 'reviewed today' compares UTC last_review with the user's local date, so nudges reach the wrong users

## What this is

A bug fix to the late-day streak nudge (#1950). Gate D ("already reviewed today") asks `get_push_reviewed_today` whether any `card_reviews.last_review` equals the user's **local** today. `last_review` is a **UTC** date (`lib/srs/scheduler.ts:290`, via the file-local `isoDate` at `:132`), and it is only set when a card graduates or lapses (`scheduler.ts:27`). The streak itself is stored in the user's local day (`components/review/ReviewSession.tsx:2599`, `:2909`). So Gate D gives the wrong answer for anyone not on UTC, and for anyone whose only practice today was on learning-step cards.

This is also a compliance regression, not just a targeting bug. `docs/childrens-code-assessment.md:104` (Standard 13, constraint 5, "No false urgency") and `docs/dpia.md:302` (R8) both record "never tell the user their streak is at risk when it is not" as a condition of the feature. Scenarios 2 and 3 in the issue break that condition today.

The fix: derive "reviewed today" from the same local-day `streak_days` rows the route already fetches for Gate E, and stop consulting `get_push_reviewed_today`. No migration.

## Approach

**Decision: route-only fix, with "reviewed today" derived inside the predicate.**

- `streak_days` is already written in the user's local day and already fetched by the route, so no new data source and no migration are needed.
- The derived signal means "streak secured today" (`recordReview`'s 5-card or empty-queue threshold, `lib/streak/persistence.ts:36`). That is exactly the question the nudge copy answers (`messages/en.json:1268`: "A few minutes today keeps it going").
- Deriving it inside `isEligibleForStreakNudge`, rather than passing a boolean in, is a forcing function. No caller can hand the predicate a "reviewed today" answer from a different day domain, which is how this bug happened. It also makes the predicate's Gate 2 assumption true by construction.

**Rejected:**

- **Keep the boolean parameter and compute it in the route** (the issue's literal suggestion): this works, but the predicate still accepts a value that can disagree with `streakDays`.
- **Repoint `get_push_reviewed_today` at `streak_days`**: this keeps a cheap pre-filter before the streak fetch. But it needs a migration applied to both Supabase projects before merge, plus a real-RPC integration test, and it duplicates a check the route can do on data it already holds.
- **Repoint it at `grade_log`**: this changes the meaning to "touched any card today" (see open question 1), and it also needs a migration.
- **OR the old RPC with the new check**: this keeps the west-of-UTC missed nudge, because the RPC's false positive still drops the user.

**Why pagination is part of this change.** Supabase's API layer (PostgREST) silently cuts any response off at 1000 rows by default (`lib/sync/paginatedFetch.ts:4-6`). `get_push_streak_days` returns each user's entire `streak_days` history, and the route reads it in one unpaged call today. That is a latent bug already, but the fix makes it worse in two ways:

- Users who reviewed today are no longer filtered out first, and they are the most active users with the longest histories.
- Results are ordered by date ascending, so a cut-off result loses a user's **most recent** dates. Losing today's date gives a false nudge; losing yesterday's gives a missed one.

Paging through the results with `fetchAllPages` closes that gap. `send-daily` already does it for the same kind of set-returning RPC.

## Risks and unknowns

- **Sync lag still produces an occasional false nudge.** `streak_days` reaches the cloud only through `AutoSyncOnChange.tsx:83`, which fires when `recordReview` adds a new date, and through the sign-in callback (`app/auth/callback-complete/page.tsx:334`). If today's push fails (offline, flaky network), nothing retries it until the next new streak day. `pullAndMerge` only re-pushes when the cloud pull changes local data. That user gets a false nudge at 20:00. This is much narrower than today's systematic offset, and the issue accepts it. A retry-on-reconnect for the streak push could be a follow-up issue.
- **Semantic shift.** Users who practised today but stayed below the streak threshold (fewer than 5 cards, due queue not empty) will now get the nudge. See open question 1.
- **Timezone agreement.** The route and `ReviewSession` both fall back to `"UTC"` when the timezone is missing (`route.ts:279`, `ReviewSession.tsx:1391`). The fix assumes the client's `settings.timezone` and the cloud `user_settings.timezone` column that `get_push_targets` returns agree. I have not traced that sync path. If they can drift, the route's "today" and the stored streak day can still disagree for that user, as before.
- **Unknown:** the configured PostgREST row limit on the prod and QA projects. The plan assumes Supabase's default of 1000, which the repo's own comments also assume. Paging is correct whatever the limit is.
- **Wider read per run.** Every user past gates A-C now has their full `streak_days` history fetched, not just users who have not reviewed. At current scale (opted-in users whose local clock reads 20:00 this hour) this is small. Paging bounds the size of each response.
- **Compliance:** the fix restores Standard 13 constraint 5. The `docs/dpia.md` R8 wording must change in the same PR, or the DPIA will describe a read the job no longer makes. Have privacy-expert confirm the new wording.

## Open questions for Fraser

1. **Should a user who practised today, but not enough to count the streak day, still get the nudge?**
   - **(a) Yes: "reviewed today" means "streak day recorded"** (`streak_days`, the plan as written). The copy "A few minutes today keeps it going" is literally true for them, and the nudge fires only when the streak will actually break. The cost: someone who did 3 cards gets a push that evening.
   - **(b) No: "reviewed today" means "graded any card today"** (`grade_log`, whose `date` is also the local day, `ReviewSession.tsx:2914`). Anyone who opened a session is left alone, even though their streak will lapse. The cost: a migration applied to both Supabase projects before merge, a real-RPC integration test, and an at-risk streak that goes un-nudged.
   - **Recommendation: (a).** It matches the feature's stated purpose (nudge when the streak is genuinely at risk) and the issue's acceptance criteria, and it needs no migration.
2. **What happens to `get_push_reviewed_today`, which nothing calls after this fix?**
   - **(a) Leave it for now and file a follow-up issue to drop it.** It is `SECURITY DEFINER` but callable only by `service_role` (`047:115-116`), so the exposure is nil, and this fix stays migration-free and quick to ship.
   - **(b) Drop it in this PR** with a new `048_drop_get_push_reviewed_today.sql`. That needs `apply_migration` on both prod and QA before merge, plus trimming the `get_push_reviewed_today` blocks from `push-streak-nudge-rpc.test.ts`.
   - **(c) Leave it permanently.** This keeps a misleading "reviewed today" contract in the schema for someone to reuse later.
   - **Recommendation: (a).** Filing the follow-up issue is a GitHub mutation, so it needs your go-ahead.
