# Plan: #2059 Four-locale test coverage is mandatory but unenforced

## What this is

`AGENTS.md:160` makes four-locale test coverage non-negotiable, and until 2026-08-16 the only thing
enforcing it was `auto-review.yml`, which was deleted in `9420abda` (#2003). This change builds the
missing forcing function: a static gate, `npm run lint:locale-coverage`, that fails when a component
rendering catalogue copy has no sibling test exercising all four supported locales.

Scope honesty up front, because it decides whether this is worth building:

- It catches the **#1947 / #1955 class** exactly: a component whose tests render `en` and `ja` but
  never `zh-Hans` / `zh-Hant`. Both incidents are reproducible as fixtures.
- It does **not** catch the **#1935 class**: a locale suite that exercises only one of three new
  share-text variants per locale. That is a state-by-locale product gap, not a syntactic property of
  the test file, and no static gate reaches it. The state-coverage half of `AGENTS.md:160` stays
  enforced by human review.

So this closes two of the three cited cases, and the third is called out as out of reach rather than
papered over.

## Approach

**The unit is the component, not the test file.** Eight components already split their locale
assertions into a dedicated sibling: `EvolutionWall`, `MilestoneShareButton`, `PokedexGrid`,
`ScopeControl`, `RandomEvolutionNote`, `HigherOrLowerGame`, `StrugglingCards`, `StrugglingCardRow`
all have a `*.locale.test.tsx` (all eight cover `zh-Hant`). A per-test-file rule would report four of
those as failures while the coverage plainly exists. So the gate groups every test file in a
directory by its basename before the first dot (`Foo.test.tsx`, `Foo.locale.test.tsx`,
`Foo.i18n-leak.test.tsx` all belong to `Foo.tsx`) and unions their locale coverage.

**Detection is a token scan, not an AST walk.** A component counts as covered when the union of its
sibling test sources contains a marker for each locale: `renderJa` or `"ja"`, `renderZhHans` or
`"zh-Hans"`, `renderZhHant` or `"zh-Hant"`, and an `en` render (`renderWithIntl(` or `"en"`). Crude,
but it survives the two patterns actually in use: literal-per-locale calls, and the
`Record<AppLocale, ...>` map keyed by literals that `ScopeControl.locale.test.tsx:37` uses. Known
limitation: a future test that loops over `SUPPORTED_LOCALES` imported from `i18n/locales.ts:8` has
no literals in the file and would false-positive. No test does that today (checked), and the
exemption file is the escape hatch.

**Exemptions are a ratchet, not a graveyard.** A listed path that no longer exists, or that now
passes, is itself a lint error. This mirrors `lint-i18n.mjs`'s extra-key check: drift in either
direction fails, so the list shrinks under its own pressure instead of accumulating.

**Wiring into the `lint` chain rather than a new workflow** is deliberate. It buys the required-check
enforcement and the `pre-pr` visibility the issue's third suggestion asks for, with zero
`.github/workflows/**` surface. The one behavioural nuance: `ci.yml:88-90` gates `npm run lint` on
`changes.outputs.code`, and the `code` filter (`ci.yml:38-44`) excludes only `**/*.md`,
`changelog.d/**`, `docs/**` and `.claude/agents/**`. Any `components/**` or `messages/**` change sets
`code=true`, so the gate runs on every PR that could possibly violate it.

**Rejected: runtime instrumentation.** Recording locales inside `renderWithIntl` and asserting in a
vitest global teardown would be precise, and it was my first instinct. It does not work here:
`ci.yml:98-106` runs `npm test -- --changed origin/<base>` on pull requests, so the teardown only
ever observes the changed test files and cannot distinguish "this component is uncovered" from "this
component's test did not run in this job". It would be a gate that passes for the wrong reason on
exactly the PRs it exists to police.

**Rejected: a custom ESLint rule.** The repo has no custom-rule infrastructure (`eslint.config.mjs`
uses built-in `no-restricted-syntax` selectors only), and ESLint is per-file, so it cannot see the
sibling `*.locale.test.tsx` that makes the component-granularity rule correct.

**Rejected: extending `test:i18n-leak` from its three-file opt-in to an opt-out default**, which is
the issue's first suggested fix. It is a different axis. The pseudo-locale harness proves that
rendered text came from the catalogue; it says nothing about whether a real non-English catalogue was
ever rendered. Because `lint:i18n` already enforces key parity across all four catalogues, the copy
in #1947 and #1955 was in every catalogue and the leak gate would have passed. Broadening it is
worthwhile (it catches a different failure, hard-coded English), but as its own issue, not as this
gate.

**Backlog size.** These are grep approximations at file granularity, not the gate's own output. The
implementer should run the script first and use its report as the authoritative seed list.

- 95 non-test `components/**` / `app/**` sources call `useTranslations(` / `getTranslations(`.
- About 59 test files that import the intl helpers never mention `zh-Hant`.
- About 30 test files render `ja` but never `zh-Hant`; four of those have a `.locale.test.tsx`
  sibling that does, leaving roughly 26 genuine gaps under the narrow scope.
- `components/review/ReviewSession.test.tsx` (one of the two #1955 files) has zero `zh-Hant`
  references today. Whether it is grandfathered is precisely what Q2 decides.

## Testing

- `scripts/lint-locale-coverage.test.mjs`, node project, against temp-directory fixtures. Test the
  exported helpers (`groupTestsByComponent`, `localesCovered`, `findGaps`, `findStaleExemptions`),
  not the process exit: covered component, `en`+`ja`-only component, component covered only via its
  `.locale.test.tsx` sibling, component with no sibling test at all, exempted component, and a stale
  exemption entry.
- **The acceptance test that matters**: a fixture reconstructing the #1947 and #1955 shapes (a
  component test block asserting copy in `en` and `ja` and nothing else) must be reported by the
  gate. If it is not, the change has not done its job, whatever else passes.
- `npm run lint` green end to end on `qa` after seeding or burn-down, since a half-seeded exemption
  file turns every subsequent PR red for unrelated reasons.
- `npm run pre-pr` before opening the PR, per `AGENTS.md`.
- No e2e work, and no product-code change. `test:diff-coverage` instruments `app/**`,
  `components/**`, `lib/**` only (`vitest.config.ts:44`), so a scripts-only diff reports as skipped
  and passes, which is expected rather than a failure to chase. If Q2 option (c) is chosen, the
  touched test files change that.

## Risks and unknowns

- **The exemption list becomes a rubber stamp.** A seeded list of roughly 26 to 55 entries that
  nobody burns down leaves the rule enforced for new components and dead for existing ones. The
  staleness check pushes in the right direction but does not force progress; a `priority:next`
  burn-down issue should be filed alongside, and Q2 option (b) is the structural answer.
- **Child components covered only through a parent's suite** produce false positives (for example
  `GradeButtons` rendered inside `ReviewSession`). The `reason` field on the exemption entry is the
  intended outlet, but every such entry is a small honesty tax on the list.
- **Token matching can be fooled** by a locale tag appearing in a comment. Accepted: this is a nudge
  gate for a rule people forget, not an adversarial check.
- **The wider hole stays open.** The issue's real finding is that the reviewer which caught all three
  cases no longer exists. This gate covers one class of what it caught. Whether to restore some form
  of automated PR review after #2003 is a separate decision and is not in this issue's scope.
- **Unverified**: I did not execute a component-granularity count (the probe script run was refused
  by the sandbox), so every backlog figure above is grep-derived at file granularity and will shift
  once the script reports for real. It will shift down, not up, because sibling coverage only helps.

## Open questions for Fraser

**Q1. How wide should the gate's scope be?**

- **(a) Narrow**: only components whose sibling tests already render some non-`en` locale must render
  all four. Backlog roughly 26 components. Loophole: a component tested in `en` only is never in
  scope, so the laziest path stays silent, and deleting a `ja` test silences the gate.
- **(b) Wide**: every component or page calling `useTranslations()` must have sibling coverage in all
  four locales. Backlog roughly 55. Closes the loophole, at the cost of a much longer seeded
  exemption list on day one.

Recommendation: **(b)**. The failure mode the issue documents is an implementer stopping early, and
under (a) stopping earliest of all (English only) is rewarded with silence. The cost is a bigger
exemption list, which Q2 then determines the honesty of.

**Q2. What happens to the existing gaps?**

- **(a) Plain exemption list.** Cheapest. `ReviewSession.test.tsx` and friends are grandfathered
  permanently, which means the gate would not have caught #1955 on the file where it happened.
- **(b) Exemption void on touch.** Add a `--diff` mode (base `origin/qa`, overridable like
  `DIFF_COVERAGE_BASE`, skipping cleanly when the base is unresolvable) that ignores the exemption
  for any component or test file changed in the diff. About 20 extra lines in the script, one extra
  `pre-pr` step, and one extra `ci.yml` step, which triggers mandatory `workflow-expert` review.
- **(c) No exemptions, burn down all gaps in this PR.** Strongest, and a genuinely large diff: 26 to
  55 test files gaining `zh-Hans` / `zh-Hant` assertions written by someone who does not read those
  languages, which is how low-value assertions get written.

Recommendation: **(b)**. It is the only option under which a future #1955 fails, because the moment
someone edits the copy in an exempted component the exemption stops applying. It also makes the
seeded list self-limiting: entries only survive while nobody touches them. If the `ci.yml` step is
unwelcome, (b) still works locally through `pre-pr` alone, with weaker enforcement.
