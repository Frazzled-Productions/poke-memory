# Plan: #2015 next/image `priority` is deprecated in Next 16, still used at 9 call sites, and the docs point at tracking that does not exist

## What this is

`next/image`'s `priority` prop was deprecated in Next 16 in favour of `preload`. Nine call sites still
use it, and `AGENTS.md` plus `docs/sprites.md` teach it as the canonical rule, so new sprite surfaces
keep adding more. The deprecation is silent (no `warnOnce`, no type error, only a `@deprecated` JSDoc
tag), so nothing surfaces it until the prop is removed in a future major.

The mechanical part is a rename. The part that needs a decision is whether the five **review flip-card**
sites should become `preload` (identical behaviour) or `loading="eager"` (what the installed doc
actually recommends for them). That is the single open question below.

**Verified against the source, not from memory** (installed `next` 16.2.9 under the parent checkout):

- `node_modules/next/dist/shared/lib/get-img-props.js:584` - `preload: preload || priority`. A
  like-for-like rename is byte-identical in the emitted HTML.
- Same file `:404` - setting both props throws `E802`. It must be a replacement, never an addition.
- Same file `:397` - `preload` truthy plus `loading="lazy"` throws `E803`. `preload={false}` plus
  `loading="lazy"` is fine (the guard tests truthiness), which matters for two of the call sites.
- Same file `:269` / `:550` - `priority` and `preload` are equivalent inputs to `isLazy`; neither sets
  `fetchPriority`, which is passed straight through from props (`:569`).
- `node_modules/next/dist/shared/lib/get-img-props.d.ts:23-28` - `preload?: boolean` exists;
  `priority?: boolean` carries `@deprecated`. TypeScript does **not** error on it.
- `node_modules/next/dist/client/image-component.js:209-227` - a truthy `preload` renders
  `ReactDOM.preload(src)`, i.e. a `<link rel="preload" as="image">`.

## Approach

**The decision: rename, plus a lint ban, plus the docs in the same change.**

The rename itself is not interesting - `preload: preload || priority` makes it a no-op. What makes this
worth doing properly is that the issue is really about the *guidance*, not the call sites: nine usages
exist because `AGENTS.md:139` and the `docs/sprites.md` table tell every future implementer to write
them. Migrating the code without rewriting the guidance leaves the generator running. Hence docs and
`AGENTS.md` land in the same commit, and hence the ESLint rule: this repo's stated pattern for a
single-source rule is a forcing function, not a reviewer's memory (#1327, #1389, #1456, #1559 all did
exactly this in `eslint.config.mjs`).

**Explicit `preload={false}` rather than deleting the three false sites.** `priority={false}` is already
the default, so deleting the prop is behaviour-identical and a smaller diff. Rejected: `docs/sprites.md`
states the convention three separate times (`:58` "Prefer the explicit `priority={false}` for clarity",
`:60`, `:125` "Decorative chrome gets `priority={false}`"). Deleting the props would silently reverse a
maintainer-documented convention under cover of a mechanical migration. Renaming preserves it, and if
Fraser would rather drop them the follow-up is three one-line deletions.

**Rejected: a type-aware `@typescript-eslint/no-deprecated` rule.** It would catch this and every future
deprecated Next API generically, which is genuinely more valuable. But it requires type-aware linting,
which this config does not currently enable (`eslint.config.mjs` extends only `eslint-config-next`
core-web-vitals + typescript), and turning that on repo-wide is a lint-performance and
baseline-burn-down change of its own. Out of scope here; worth its own issue if Fraser wants it.

**Rejected: adding `fetchPriority="high"` anywhere.** The installed doc offers it as an alternative, but
no current site sets it, `priority` never implied it in Next 16 (`get-img-props.js:569` passes it
through untouched), so adding it would be a new behaviour smuggled into a deprecation cleanup.

**Rejected: touching `components/pokedex/PokedexGrid.tsx`.** It is a plain `<img>` under the documented
grid exemption and has no `priority` prop. Its `:29` comment mentions "blanket preload", which is about
`SpritePreloader`, not this prop.

## Testing

Nothing here changes rendered output under Option A, so the tests are a regression net plus a proof that
the new lint rule actually fires.

1. **`npm run pre-pr`** (lint -> typecheck -> build -> test -> coverage -> diff-coverage). The worktree
   has no `node_modules`; run `npm ci` there first with the pinned Node major from `.nvmrc` on `PATH`.
2. **Prove the lint rule fires.** A negative-space rule that matches nothing proves nothing. Temporarily
   add `priority` back to one `<Image>`, confirm `npm run lint` errors with the new message, then revert.
   Then confirm a clean `npm run lint` over the migrated tree - that is what proves zero sites remain.
3. **`npm run build` is the only automated catch for the double-prop throw.** E802 fires at render, and
   every component test mocks `next/image` as `<img {...props} />` (see `components/review/SpritePicker.test.tsx:10`,
   `components/theme/ThemeWatermark.test.tsx`, and seven others), so a site left with both props would
   spread them onto a DOM node and pass. The build prerenders `/pokedex/[id]` through the real
   component, so only that one site is covered by the build. Everything else relies on lint plus a
   final `grep -rn "priority" components app` sweep. Do the sweep; do not skip it.
4. **Existing tests that must stay green** (all touched components except `PokemonCard.tsx`, which has
   no dedicated spec and is exercised through `ReviewSession.test.tsx`):
   `components/review/EvolutionCardLayout.test.tsx`, `components/review/TypedEntryNameCard.test.tsx`,
   `components/review/MultipleChoiceNameCard.test.tsx`, `components/theme/ThemeWatermark.test.tsx`,
   `components/pasture/NextArrivalsStrip.test.tsx`, `components/onboarding/KnownPokemonQuiz.test.tsx`,
   `components/pokedex/PokemonDetailDisclosure.test.tsx`, `components/review/ReviewSession.test.tsx`.
   De-flake against the full jsdom project (`npx vitest run --project jsdom`), not file-alone (#1464).
5. **No new unit tests.** There is no new behaviour to assert, and asserting a prop name through a
   mocked `next/image` would test the mock. The ESLint rule is the regression test; that is the point of
   step 2.
6. **Diff coverage.** All changed product lines sit inside render paths the specs above already execute,
   so the 90% patch bar should hold with no new tests. Confirm with `npm run test:diff-coverage` rather
   than assuming.
7. **`visual-regression.yml` will run** (its path filter matches `components/**`). The Stats and Journey
   baselines contain no sprite using these props, so expect a clean compare. If it fails, that is a real
   signal, not a baseline refresh - investigate before regenerating.
8. **Option B only:** a QA-preview pass on the practice route watching sprite pop-in across several card
   advances, on `chromium` and `mobile-safari`. Option A needs no manual QA.

## Risks and unknowns

- **Version drift, and this plan was verified against the resolved tree, not the pin.** `package.json:53`
  pins `next` to `16.3.1`; the resolved `node_modules` in the parent checkout is `16.2.9`; `AGENTS.md`
  still claims 16.2.6; the issue says 16.2.10. Everything above was read from the installed 16.2.9
  source. `preload` landed in 16.0.0 so it certainly exists in 16.3.1, but re-read
  `node_modules/next/dist/shared/lib/get-img-props.js` after `npm ci` in the worktree before editing, in
  case 16.3.x tightened the E802/E803 guards. The AGENTS.md stack-version staleness is a separate
  problem; do not fix it in this change.
- **This buys no immediate signal.** `priority` is `@deprecated` in the `.d.ts` only, so typecheck stays
  green either way and nothing breaks until the removal major. The payoff is that the docs stop teaching
  a deprecated prop, not a fixed failure.
- **The unit-test net has a real hole**, as described in testing step 3. Called out here because it is
  the failure mode most likely to reach a preview: the review-card sites are client-only, so neither
  `npm run build` nor `npm test` would catch a half-applied edit there.
- **`lint:agents-size`** gates `AGENTS.md` on line and byte ceilings, so the `:139` rewrite must stay one
  line and roughly its current length. Do not expand it into a paragraph about the deprecation; that
  detail belongs in `docs/sprites.md`.
- **Unknown, and deliberately not resolved here:** how much a post-hydration `ReactDOM.preload` call
  actually buys on the review route. My reading is "little to nothing" (the `<link>` is injected in the
  same tick the `<img>` mounts, and `SpritePreloader` plus `decodeSpriteUrls` already cover the network
  and decode gaps for the *next* card), but I have not measured it. That is exactly why the review-card
  treatment is a question rather than a decision.

## Open questions for Fraser

**Q1. For the five review flip-card sites, do you want a like-for-like rename, or the treatment the
Next docs actually recommend for them?**

Context: the installed doc (`node_modules/next/dist/docs/01-app/03-api-reference/02-components/image.md:289`)
says "In most cases, you should use `loading="eager"` or `fetchPriority="high"` instead of `preload`",
and lists preload's purpose as getting the fetch started *in the `<head>`, before the body is parsed*.
The review cards do not have that shape: `ReviewSession.tsx:787` marks its state as "null = SSR /
not-yet-hydrated", so the card sprite renders client-side only, and the preload `<link>` is injected at
the same moment the `<img>` mounts - and re-injected on every card advance. The Pokédex detail sprite is
different: it genuinely is a server-rendered route hero, and stays `preload` under either option.

- **Option A (recommended): rename all six truthy sites to `preload`.** Zero behaviour change (byte-identical
  HTML), smallest diff, clears the deprecation now. Leaves a mild inaccuracy in place: five images
  emitting preload links that probably do not earn them.
- **Option B: `preload` for the Pokédex detail hero, `loading="eager"` for the five review-card sites.**
  More faithful to what the prop means, removes the per-card head churn, and stops the review cards
  triple-covering the same gap that `SpritePreloader` and `decodeSpriteUrls` already handle. Costs a
  behaviour change on the app's core surface, a preview-QA pass on sprite pop-in, and a wider rewrite of
  the `docs/sprites.md` surface-class table (the rows change meaning, not just prop names).

**Trade-off:** A is a clean deprecation clearance with nothing to QA. B is more correct but couples a
perf judgement I cannot verify without measurement to a change that otherwise needs none.

**Recommendation: A now, and if you want B, file it as a separate perf issue.** Keeping them separate
means the deprecation clearance and the lint ban land unblocked, and the perf question gets judged on
measured pop-in behaviour rather than on my reading of the docs. Say the word and I will do B in one
pass instead.
