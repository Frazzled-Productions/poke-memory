# Plan: #2014 Supabase `Database` type is still the `unknown` stub from migration 001

## What this is

`lib/supabase/types.ts` is a four-line stub (`export type Database = unknown`) threaded into
`createBrowserClient<Database>` (`lib/supabase/client.ts:8`) and `createServerClient<Database>`
(`lib/supabase/server.ts:9`). Because `keyof unknown` is `never`, every typed call collapses,
which is exactly why `app/api/sync/route.ts:35-38` says "the typed upsert to expect never[]".
The fix is to generate real schema types, remove the casts that become redundant, and add a
forcing function so the file cannot fall 47 migrations behind again.

Two corrections to the issue body, because they change the shape of the work:

1. **Only 11 of the 14 `no-explicit-any` disables in product code are Supabase-related.**
   `app/api/push/send-daily/route.ts:106`, `app/api/push/send-streak-nudge/route.ts:89` and
   `lib/pwa/downloadController.ts:130` are message-catalogue and Proxy types, untouched by this
   change. The Supabase ones are `lib/auth/actions.ts:76/144/199`, `app/api/feedback/route.ts:102`
   and seven in `scripts/qa-seed-cloud.ts`.

2. **"Fold `rpc-types.ts` into the generated function types" is not reachable by generating
   types alone.** Its two consumers (`lib/sync/settings.ts:36`, `app/api/srs/optimize/route.ts:129`
   and `:236`) receive a bare `SupabaseClient` parameter, not the typed client. Generated types do
   nothing for a call site whose client is already widened to the untyped default. The same is true
   of the four `as unknown as SupabaseClient` widening casts in `app/api/sync/route.ts:38`,
   `app/api/export/route.ts:100`, `app/api/push/resubscribe/route.ts:36` and
   `app/api/srs/optimize/route.ts:173`. Those only disappear once `SupabaseClient<Database>` is
   threaded through the ~25 modules in `lib/sync/**`, `lib/push/**` and `lib/auth/**` that
   currently take the untyped alias. That is a separate, sync-layer-touching change, and it is the
   subject of the first open question below.

## Approach

**Generate from the live project via the Management API, not from a local Postgres container.**

The tempting alternative is generating from the throwaway Postgres instance the integration suite
already builds from `db/migrations/**` (`lib/sync/integration/applyMigrations.ts` +
`setup.ts`). That would make the types a pure function of the committed migrations, checkable in CI
with no secrets. I rejected it for now because it needs the `supabase` CLI as a new dev dependency
(it is installed on this machine at v2.109.1 but is not in `package.json`), it needs the
pre-migration fixture (`auth` schema, `auth.uid()` polyfill, the three roles) to be reproduced
outside the vitest harness, and it would generate types from a schema that is one fixture away from
the real one. The live-project route needs zero new dependencies and reuses secrets and a workflow
that already exist. If the local route is wanted later, it is a clean follow-up.

**Reuse `check-migrations.mjs` wholesale rather than inventing a new mechanism.** The Management
API exposes `GET /v1/projects/{ref}/types/typescript`, which is the same endpoint
`supabase gen types --project-id` calls, so a committed file and a CI fetch are byte-comparable.
Putting the new step inside `migration-check.yml` means the types check inherits the env-to-branch
routing (#1806) for free: QA parity on `qa`-based PRs, prod parity on push to `main`. A separate
workflow would have to duplicate that routing and the fork/dependabot guards, and drift between the
two copies is precisely the failure mode #1806 was about.

**Do not derive `CloudRow` from the generated `card_reviews` Row type,** even though the issue
suggests it. `CloudRow` (`lib/sync/cloud.ts:111-142`) types `subject_key` as `string | null` and
`locale` as optional, but migration 012 made `subject_key` NOT NULL and migration 029 made `locale`
NOT NULL DEFAULT 'en'. Those are not stale types: they are deliberate tolerances for rows written
before those migrations, and pull paths branch on them ("Null for unmigrated edge rows (skipped on
pull)", "all pull paths default to `en` via `row.locale ?? "en"`"). Deriving the wire type from the
schema would delete two defensive branches on the highest-consequence path in the codebase.
`CloudRow` should stay a distinct wire type; if anything it wants a comment saying why it is looser
than the schema.

**Rejected: doing everything in one PR.** The remaining prize (threading
`SupabaseClient<Database>` through `lib/sync/**` so `card_reviews` upserts are schema-checked)
touches the sync layer, which AGENTS.md flags as the one place a mistake is catastrophic and
partially unrecoverable (#293 wiped 2497 of 2513 cloud rows; backups are daily-only with PITR
deferred, #298). It is also where the type checker will actually find things, and therefore where
the diff will grow unpredictably. Mixing it with the mechanical generate-and-delete-casts work
makes the whole thing unreviewable. See open question 1.

**Rejected: deleting `lib/supabase/rpc-types.ts` in this change.** As set out above, its call sites
hold untyped clients. Deleting it now would mean re-adding the `as any` casts it exists to avoid.

## Testing

`npm run pre-pr` is the gate (fail-fast lint, typecheck, build, test, coverage, diff-coverage), and
for this change `tsc --noEmit` is the actual proof: it is the step that tells us the generated
`Database` matches every `.from(...)`, `.select("...")` and `.rpc(...)` string in the repo. Expect
it to surface real mismatches on the first run; each one is a finding, not a nuisance, and should be
fixed rather than cast away.

Specific tests:

- `npm run typecheck` - must pass with the casts removed. The seven tables the code touches
  (`push_subscriptions`, `card_reviews`, `grade_log`, `user_settings`, `feedback`, `streak_days`,
  `usernames`) and the RPCs it calls (`check_rate_limit`, `merge_user_settings`,
  `reset_all_progress`, `delete_account`, `get_push_targets`, `get_push_due_cards`,
  `get_push_streak_nudge_targets`) all have to resolve.
- `scripts/lib/supabase-types-compare.test.mjs` (new) - identical input passes; a one-line schema
  difference fails; a differing generator version banner alone does not fail. Runs under the `node`
  vitest project.
- `node scripts/check-supabase-types.mjs` run locally against the prod ref, twice: once on the
  committed file (expect exit 0) and once with a hand-edited column removed (expect exit 1 and a
  message naming the regen command). Same manual verification `check-migrations.mjs` gets.
- The existing suites are the regression net for the cast removals:
  `lib/sync/settings.test.ts`, `lib/sync/streak.test.ts`, `lib/sync/gradeLog.test.ts`,
  `lib/sync/pushSubscriptions.test.ts`, `lib/auth/requireAuth.test.ts` and
  `components/pwa/subscribe.test.tsx` all build fake clients with
  `{ ... } as unknown as SupabaseClient`. That cast widens to the untyped default, so they should
  keep compiling unchanged. If any stops compiling, the change has reached further into the sync
  layer than intended and should be trimmed back.
- De-flake against the full suite per AGENTS.md: `npx vitest run --project node`,
  `--project jsdom`, and `--changed origin/qa`. Not file-alone (#1464 / #1470).
- No `db/migrations/**` change here, so the integration suite is not mandatory, but running
  `VITEST_INTEGRATION=1 npm run test:integration` once is cheap insurance that `qa-seed-cloud.ts`
  still matches the schema it seeds.
- No user-facing surface changes, so no new e2e specs, no locale coverage, no screenshot regen.

## Risks and unknowns

- **QA and prod may not generate byte-identical types.** The plan wires the check into
  `migration-check.yml`, which points at QA for `qa`-based PRs and prod on push to `main`. That only
  works if both projects produce the same file. Migration parity was reconciled on 2026-06-08
  (001-041, per `docs/persistence.md:60`), so they should match, but this is unverified: the
  planning lane has no Supabase credentials. **First implementation step is to generate from both
  refs and diff them.** If they differ, either fix the drift (a real finding) or run the types check
  against prod only and say so in the workflow comment.
- **The generated file bakes in whatever the live project actually has**, including any object
  created through the dashboard that no migration records. If the diff between the generated types
  and what the migrations imply looks surprising, that surprise is the finding, not noise.
- **Typecheck fallout is unbounded until it is run.** `.select("settings, updated_at, last_reset_at")`
  strings are parsed by the generated types, so hand-written result shapes such as
  `UserSettingsRow` (`lib/sync/settings.ts:184-192`) may not agree with the schema. Some of those
  disagreements will be deliberate tolerances, like `CloudRow`'s. Each needs a judgement call, and
  the change should not silently tighten a defensive branch.
- **Regenerating on every migration is a manual step until the CI check lands**, and manual steps
  are what produced this issue. If the byte-comparison gate turns out not to be viable (see the
  first bullet), say so explicitly rather than shipping the doc line alone; a checklist entry with
  no forcing function is what "TODO: remove cast once `supabase gen types` is run" already was.
- **`no-explicit-any` is not currently configured as an error in `eslint.config.mjs`.** It comes
  from `eslint-config-next/typescript`. Removing disable comments is safe, but do not assume a new
  `as any` would fail CI without checking the effective rule severity first.
- Low risk, worth a glance: the generated file passes through `npm run lint:em-dash`, which scans
  comments and string literals under `lib/`. Supabase's generator does not emit em dashes today,
  but a future banner change would fail the lint chain rather than the type check, which would be
  a confusing failure to debug cold.

## Open questions for Fraser

**1. How far should the cast cleanup go?**

- **Option A (recommended): generate the types, take the ten casts that fall out for free, add the
  drift gate, and file a follow-up issue for the sync layer.** Removes eleven `eslint-disable` lines
  and all ten `(x as any)` Supabase cast sites a repo-wide grep finds (the issue says eleven; I
  count three in `lib/auth/actions.ts`, one in `app/api/feedback/route.ts`, six in
  `scripts/qa-seed-cloud.ts`), all in code paths with existing test coverage.
  Leaves `rpc-types.ts`, the four widening casts, and the untyped `SupabaseClient` parameters in
  `lib/sync/**` for a second change.
- **Option B: do it all in one PR**, threading `SupabaseClient<Database>` through `lib/sync/**`,
  `lib/push/subscribe.ts`, `lib/auth/{requireAuth,mockAuth,AuthContext}` and the four API routes,
  and deleting `rpc-types.ts`.
- Trade-off: Option B is where the actual schema safety lives, since `card_reviews` upserts are the
  thing worth type-checking. It is also a large diff across the one subsystem where a mistake is
  partially unrecoverable (daily-only backups, PITR deferred, #298), and it drags in
  `lib/auth/mockAuth.ts` and roughly twenty-five test files that fake clients. Option A is a change
  a reviewer can hold in their head; Option B is not. Splitting also means the type file lands
  regardless of how long the second half takes. The risk of Option A is the obvious one: the
  follow-up sits in the backlog and the interesting half never happens. Mitigation is to file the
  follow-up issue in the same session as the PR, not "later".

**2. Should the follow-up in option A be filed as a `priority:next` issue, or is this a
"do it now or never" case?**

- **Option A (recommended): file it at `priority:next`.** It is real type safety on the sync layer
  and deserves its own review pass, but nothing is broken today (the issue says so itself), and
  there is no forcing deadline.
- **Option B: skip the follow-up entirely and accept the untyped sync layer permanently,** recording
  that decision in `docs/sync.md` so the next drift survey does not refile it.
- Trade-off: this is the "if regenerating is a deliberate deferral, the file should say so" point
  from the issue applied one level up. The thing that made #2014 expensive was not the missing
  types, it was a comment that pointed at a precondition met dozens of migrations earlier. Whichever
  option is chosen, the residual state should be written down as a decision rather than left as an
  implied TODO.
