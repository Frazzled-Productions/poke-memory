# Plan: #2045 Em-dash gate parses only JS/TS, so tracked YAML, SQL, CSS, shell and docs carry violations it cannot see

## What this is

(`ops/standards/conventions.md` lines 89 to 93) but only over seven hardcoded directories
(`SOURCE_ROOTS`, line 53) and five source extensions (`SOURCE_EXT`, line 56), plus a special-cased
markdown pass over `changelog.d/**` and `CHANGELOG.md`. Everything else in the repo is invisible to
it, and the invisible part is where the violations actually live.

## Approach

**Discover files with `git ls-files`, not a directory walk.** `execFileSync("git", ["ls-files",
"-z"])` from the repo root, filtered by an explicit extension allowlist. This is the whole design
decision, and it is chosen for the failure mode it closes rather than for tidiness: the current walk
misses files in two independent ways (wrong root, wrong extension), and `next.config.ts`,
`app/globals.css` and `.github/scripts/cut-release.mjs` were each missed by only one of the two. A
root list is a list of places the rule applies, which means the next new top-level file or file type
silently opts out. Tracked-files-minus-an-allowlist inverts that: a new file type is *in* scope
until someone writes down why it is not. It also drops `SKIP_DIRS` entirely, because
`node_modules`, `.next` and `coverage` are not tracked. koinori's `check-house-style.sh` already
sweeps `git ls-files '*.md'`, so this also converges the two repos' discovery model even if we never
merge the scripts.

**Two scanners, keyed by extension.**

- `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.mjs`, `.cjs` keep today's TypeScript-AST pass
  (`scanText`, line 297): comments, JSX text, and every string or template literal, with the
  standalone no-value-glyph allowance intact. That allowance is load-bearing and must not be lost:
  `components/stats/RecordsCard.tsx:11,64` render a bare U+2014 as the no-value placeholder, and five
  assertions in `app/api/push/send-daily/route.test.tsx` and
  `app/api/push/send-streak-nudge/route.test.tsx` match on the bare glyph.
- `.md`, `.yml`, `.yaml`, `.sql`, `.css`, `.sh`, plus the extensionless `LICENSE`, get a generalised
  version of today's `checkMarkdownFile` (line 333): flag any line containing the glyph. Keep the
  leading-`---` front-matter skip for `.md` only; changelog fragments and the `docs/` files use it
  for structural metadata. A line scan is right for these types because there is no construct in a
  YAML comment, a `--` SQL comment or a shell heredoc where an em dash is anything but prose.

**Exclusions, as an explicit named list rather than an emergent property of the walk.** Generated and
external data only: `lib/pokemon/generated*.json`, `public/pokemon-data/**`, the detector itself
(`DETECTOR_SELF_PATH`, already present at line 44). Binaries never match the extension allowlist, so
they need no rule.

**The one line that legitimately prints the glyph.** `.claude/agents/ui-coder.md:47` states the rule
and shows the character. Rewrite it to name the codepoint (`U+2014`) instead of printing it. There is
already an in-repo precedent: `lib/changelog/parse.ts:30-31` writes the codepoint as a backslash-u
escape inside a character class specifically so the gate does not flag the file, and says so in its
comment. This keeps the
allowlist at zero entries, which matters because every allowlist entry is a place a real violation
can hide later. koinori hit the same problem from the other direction and solved it by *not*
sweeping the surface (see the note at `check-house-style.sh:98-103`); naming the codepoint is
strictly better where it is available.

**Sequencing: sweep first, then widen.** Two PRs into `qa`.

1. PR 1, sweep only, gate untouched. Nothing goes red because the gate has not moved yet, and the
   diff is mechanical enough to review by skim.
2. PR 2, the gate plus its tests. Small, genuinely reviewable, and green on arrival because PR 1
   cleared the ground.

The issue assumes one PR ("the 41 files above need clearing in the same change, or the widened gate
lands red"). That is true of the ordering gate-then-sweep, not of sweep-then-gate. Splitting matters
here because an 81-file sweep across every workflow file conflicts with every concurrent PR, and
this repo has been burned by exactly that: `.claude/commands/batch-issues.md:70` records the #1648
em-dash sweep amplifying a `qa` to `main` promotion into roughly 30 conflicts on 2026-06-05. A
one-PR version is still acceptable if Fraser prefers it; it is just a longer window of conflict
exposure.

**Rejected**

- *A blanket repo-wide regex sweep with no per-type parsing.* Loses the no-value-glyph allowance
  (seven live call sites) and flags generated PokéAPI text and sprite binaries.
- *Keeping the directory walk and just adding roots and extensions.* Fixes today's 81 files and
  leaves the mechanism that produced them. This is the "two half-implementations" failure the issue
  itself objects to, reproduced one level down.
- *Lifting a shared checker into `frazzled-claude` or the org `.github` repo as the first move.* See
  the open question; the short version is that it is a real option but a much larger one, and it
  should not gate clearing a violation in a published compliance document.
- *Adding an inline `em-dash-ok` escape-hatch marker.* Exactly one authored line needs to print the
  glyph, and the `U+2014` rewrite handles it. Build the escape hatch when there is a second case.

## Testing

`lib/tooling/check-no-em-dash.test.ts` already imports the script's pure helpers directly (no
subprocess, no fixtures). Extend the same pattern. Export a `scanFileText(fileName, text)` dispatcher
and an `isScannablePath(relPath)` classifier so every new case stays a pure-function assertion.

New cases, in the existing `describe` style:

- `no-em-dash gate: line-scanned file types` - build each fixture string by interpolating the
  exported `EM_DASH` constant, exactly as the existing cases do, so the test file itself never holds
  the literal glyph. Flags a YAML comment; flags a YAML `run: echo "..."` string; flags an SQL `--`
  comment; flags a CSS block comment; flags a shell `#` comment; does not flag a plain hyphen in any
  of the five.
- `no-em-dash gate: markdown front-matter` - a `---` block at line 1 containing the glyph is skipped;
  the same glyph one line below the closing `---` is flagged. This pins existing behaviour that the
  rewrite could silently drop.
- `no-em-dash gate: path classification` - `isScannablePath` returns false for
  `lib/pokemon/generated.json`, `public/pokemon-data/generated-core.json`,
  `public/sprites/pokemon/37.png` and `scripts/check-no-em-dash.mjs`; true for
  `.github/workflows/ci.yml`, `db/migrations/028_web_push_subscriptions.sql`, `next.config.ts`,
  `app/globals.css`, `.claude/hooks/prune-worktrees.sh` and `LICENSE`.
- `no-em-dash gate: source files keep AST semantics` - the existing standalone-glyph cases must still
  pass unchanged. If they do not, the `RecordsCard` placeholder and the push-notification assertions
  break.

The end-to-end proof is the test that already exists: `expect(run()).toEqual([])` at line 103. After
PR 2 that single assertion covers all 81 swept files, and it fails loudly if any of them is missed.

Also run, in this order:

- `npm run lint:em-dash` directly, for the human-readable violation list during the sweep.
- A negative control before opening PR 2: reintroduce one glyph into a `.yml` and one into a `.sql`,
  confirm `npm run lint:em-dash` exits 1 and names both, then revert. Green-on-clean proves nothing
  about a gate whose job is to go red.
- `npm run pre-pr` on both PRs (`lint:em-dash` is inside the `lint` chain, `package.json:15-16`).
- `VITEST_INTEGRATION=1 npm run test:integration` locally against the `postgres:15` container, on
  whichever PR carries the `db/migrations/*.sql` edits. AGENTS.md makes this non-negotiable for any
  migration-file change and `npm test` does not execute SQL (#1653).

Coverage is not a concern: `scripts/**` is excluded from the coverage `include`
(`vitest.config.ts:44,54`), so the gate rewrite carries no diff-coverage obligation. The test file
itself is excluded as `**/*.test.ts`.

Review routing: 25 workflow files change, and AGENTS.md requires `workflow-expert` review on
**every** `.github/workflows/**` change with no mechanical-change exception (#1859 / #1815 / #1806).
That applies to the sweep PR even though the edits are comment-only.

## Risks and unknowns

- **Applied migrations become editable history.** `db/migrations/*.sql` are the as-applied record;
  rewriting comments in a file Supabase has already run means the repo copy is no longer byte-identical
  to the statement text stored in the project. CI does not care:
  `scripts/check-migrations.mjs:28,76` compares derived *names* only, never content, so
  `migration-check.yml` stays green. The risk is documentary, not operational, and it is the reason
  this is a question below rather than a decision.
- **Issue-form option values change.** `app<U+2014>Pokédex` becoming `app - Pokédex` changes the
  string recorded in future issue bodies. I grepped `.github/scripts`, `.github/workflows`,
  `.claude`, `lib` and `scripts` for the `app` option prefix and found no consumer, so nothing in
  the repo parses these. A saved
  GitHub search or board filter outside the repo would still drift, and I cannot check those from here.
- **Sweep-versus-concurrent-work conflicts.** Documented precedent above (#1648, 2026-06-05). Land
  the sweep PR quickly and do not stack other work on top of it.
- **The plan file you are reading comes into scope.** `docs/plans/*.md` is tracked markdown, so after
  PR 2 it is swept like everything else. It is written glyph-free for that reason.
- **`git ls-files` as a subprocess inside vitest.** `run()` is called from the node-project test, so
  the test process shells out to `git`. Fine in CI (`actions/checkout`) and locally, and it works
  from a worktree, but it is a new dependency for a previously filesystem-only script. A fallback to
  the recursive walk when `git` is absent is possible; I would not add one unless a run actually fails.
- **`.env.local.example` is unreadable from this session.** One line, content unknown, and it may be
  a comment or an example value. Inspect before editing.
- **`LICENSE` is a legal-ish file.** The affected line is our own Pokémon trademark carve-out, not
  the MIT text, so a punctuation change is safe, but read the surrounding sentence before rewriting.

## Open questions for Fraser

**1. One shared checker across repos, or one checker per repo that we simply make complete?**

- **Option A (recommended): extend `scripts/check-no-em-dash.mjs` in this repo now, and file a
  separate issue for cross-repo consolidation.** Fastest route to the rule actually being enforced,
  keeps this change reviewable, and does not couple a published-compliance-doc fix to a multi-repo
  refactor.
- **Option B: lift a single checker into `frazzled-claude` (it exists, private, and
  `ops/standards/conventions.md:79` already treats it as the home for shared process tooling) or the
  org `.github` repo, and have both repos call it.** Genuinely one definition of the rule, which is
  what the single-source-of-truth standard asks for.
- **Trade-off.** The two existing implementations are not two versions of one thing. poke-memory's is
  a Node script with a TypeScript AST pass and a no-value-glyph allowance that koinori has no need
  for; koinori's is a bash script in which the markdown em-dash sweep is one of six fused gates
  (AI-attribution trailer, merge-conflict markers, a pbxproj Release setting, a Swift `#expect`
  rule, a localisation ratchet). Only the markdown sweep is generic, and it is about ten lines. A
  real consolidation means a new published artefact plus a cross-repo release dependency for a
  ten-line rule. My honest read is that B is worth doing eventually for the *policy* (one definition,
  one exemption list) and is poor value if it is only about the ten lines. Either way, do A first:
  under B the widened scanner still has to exist, so no work is thrown away.

**2. How wide does the sweep go, and does anything get a documented permanent exemption?**

`ops/standards/agents-md.md` lets a repo extend a standard for a documented local reason but not
silently weaken it, so any carve-out needs to be written into the script header as a decision.

- **Option A (recommended): sweep everything in the table, no exemptions beyond generated and
  external data.** 81 files, ~327 lines, all mechanical. Includes the 27 SQL files, both issue-form
  files, `LICENSE`, and the four tracked `.claude/**` files.
- **Option B: sweep everything except `db/migrations/**`, exempted permanently on the grounds that an
  applied migration is a historical record and should not be retouched.** Removes 27 files and 65
  lines, and removes the local integration-suite run from the critical path. Cost: the largest single
  category stays permanently un-enforced, and the exemption is hard to scope to "already applied"
  without also exempting new migrations, which is where enforcement would actually matter.
- **Option C: gate and sweep only `.yml` plus `.md` plus `.sh` now (the issue's stated scope, 43
  files), and file follow-ups for SQL, CSS and root config.** Smallest change. Cost: we would be
  choosing, deliberately, to leave four known-broken categories behind while closing an issue whose
  whole complaint is half-implemented enforcement.
- **Trade-off and recommendation.** A, on the grounds that the sweep is genuinely mechanical and
  every path left out is a place the rule quietly does not apply. The real cost of A over B is one
  local integration-suite run and a slightly bigger diff. If the as-applied-record argument lands
  with you, B is defensible and I would implement it as an explicit `EXEMPT_PREFIXES` entry in the
  script with the reason in a comment, not as an accident of the file walk.
- **Sub-question inside this one, if you pick A or B:** the issue-form dropdown values
  (`app<U+2014>Pokédex`, `now<U+2014>blocks normal use`). Nothing in the repo parses them, so I recommend
  changing them, but they are the one part of the sweep with a visible effect outside the codebase.
