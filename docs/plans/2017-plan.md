# Plan: #2017 Vercel ignore-build step skips deploys for messages/, i18n/ and instrumentation*.ts changes

## What this is

`scripts/vercel-ignored-build.sh` is wired in as `ignoreCommand` (`vercel.json:3`) and decides whether a
commit landing on `main` reaches production (`vercel.json:4-9` restricts auto-deploy to `main`). Its
`WATCH_PATHS` list (lines 17-30) omits three real build inputs, all of which exist in the tree today:
`messages/` (five catalogues: `en`, `ja`, `zh-Hans`, `zh-Hant`, `xx-pseudo`), `i18n/` (`locales.ts`,
`request.ts`, whose `getRequestConfig` dynamically imports `../messages/${locale}.json` at line 53), and
the four root `instrumentation*.ts` files holding the Sentry init and sampling config. A change confined
to any of those exits 0 at line 54-59, prints "No app/site files changed", and Vercel keeps the previous
deployment aliased. The skip is a green Vercel run, so nothing goes red.

The code fix is a few lines in one file. The part worth thinking about is stopping the list drifting a
third time.

## Files to change

- `scripts/vercel-ignored-build.sh` (exists) - add `messages/`, `i18n/` and `instrumentation*.ts` to the
  `WATCH_PATHS` array (lines 17-30), with a rationale comment in the style of the existing `scripts/` and
  `package.json` notes (lines 14-16, 31-34), because all three ship into the deployed build.
- `scripts/vercel-ignored-build.test.mjs` (**NEW**) - exit-code regression tests for the three missing
  inputs, a control case proving the guard still skips, and a drift guard over the repo's top-level
  entries. `vitest.config.ts:87` already includes `scripts/**/*.test.mjs` in the `node` project, so no
  config change is needed.
- `changelog.d/unreleased/*.md` - **no fragment.** `changelog-gate.yml` (lines 48-53) only requires one
  when the diff touches `app/**`, `components/**` or `lib/**`; this change touches `scripts/` only, and
  the fix is CI plumbing with no user-visible behaviour.
- `WORKFLOW.md:808` - **no change.** Its claim (release commits touch `package.json`, which is watched,
  so the version banner updates) stays true. Only revisit if Q1 below lands on watching `CHANGELOG.md`.

## Approach

Add the three paths, then make the list self-policing.

**Pathspec mechanics, which is where this is easy to get silently wrong.**

- `messages/` and `i18n/` go in as directory pathspecs, matching the existing entries.
- The instrumentation files go in as the single glob `instrumentation*.ts`, not as four literals.
  Verified: `git ls-files -- 'instrumentation*.ts'` returns exactly the four root files. Also verified
  that `*` in a git pathspec crosses `/` (`git ls-files -- 'app*.tsx'` returns 51 nested files), so the
  glob would additionally match a hypothetical `instrumentation-foo/bar.ts`. That over-match costs one
  unnecessary build and never a skipped one, and unlike four literals it picks up a fifth instrumentation
  file the day someone adds it.
- **Rejected: a bare `instrumentation` entry**, as the issue's "add `instrumentation` (the four root
  files)" wording could be read. A pathspec with no wildcard matches only a file or directory of exactly
  that name, so it would watch nothing at all and read as if it did. This is the one way to "fix" the
  issue and leave it broken.

**Rejected: removing `ignoreCommand` altogether.** That fixes the whole class of bug, but it is a wider
call than the issue asks for. It is offered as Q2 instead.

**Add a drift guard, do not just trust the list.** AGENTS.md's single-source-of-truth section asks for a
forcing function (a lint rule, or a fitness/contract test) whenever one concept is restated in two
places. This list has now drifted twice: `messages/` and `i18n/` arrived on 2026-05-29 (`8cf55f38`) and
were still missed by the 2026-06-07 edit (`b28f3b11`) that added `scripts/`. The guard test parses the
`WATCH_PATHS` block out of the shell script, enumerates the repo's top-level entries, and asserts each is
either matched by a watch path or named in an explicit `NOT_A_BUILD_INPUT` list inside the test. A future
root-level addition then fails CI until someone classifies it, which is exactly the step that was skipped
in June.

**Do not add `set -euo pipefail` while you are in the file.** `git diff --quiet` exits 1 by design (line
54) and both `git cat-file -e` guards are expected to fail on the shallow-clone path (lines 41, 48).
`set -e` would turn each into an early exit and break the deliberate fail-open at lines 48-51.

**Optional, cheap: `.npmrc` and `.nvmrc`.** Both shape how the deployment installs and which Node major
runs, and `.npmrc` carries the `engine-strict` setting. Whether Vercel honours `.nvmrc` (as opposed to
project settings or `package.json` `engines`) is not verified here, and I have not checked it against
Vercel's docs, so treat these as cheap insurance rather than a known input: adding them can only ever
cause an extra build. Include them and say so in the comment, or leave them out and list them in the
guard's `NOT_A_BUILD_INPUT` instead. Either is defensible; I lean towards including them.

## Testing

The script only executes inside Vercel's build container, so the proof is a local subprocess test, not a
deployment. Precedent for shelling out from vitest is `lib/i18n/lint-i18n.test.ts:14-21`, which runs
`scripts/lint-i18n.mjs` as a CLI smoke test. `scripts/**` is excluded from coverage
(`vitest.config.ts:54`), so no coverage floor or diff-coverage obligation follows from the new file.

New file `scripts/vercel-ignored-build.test.mjs`. Each case builds a throwaway git repo in a temp dir
(`git init`, with committer identity and `commit.gpgsign=false` passed via `git -c` so a local signing
config cannot break it), commits a baseline, commits a second change, then runs
`execFileSync("bash", [SCRIPT], { cwd: tmp, env: { ...process.env, VERCEL_GIT_PREVIOUS_SHA: baseSha } })`.
Exit 1 means "build", so the assertions read `err.status` off the thrown error rather than the return
value.

- `messages/en.json`-only change exits 1 (builds). Red before the fix.
- `i18n/request.ts`-only change exits 1. Red before the fix.
- `instrumentation-client.ts`-only change exits 1. Red before the fix.
- **Control:** `docs/x.md`-only change exits 0 (skips). Green before and after, and it is what proves the
  fix tightened the list rather than neutering the guard.
- Fail-open regression cover: unset `VERCEL_GIT_PREVIOUS_SHA` exits 1 (lines 8-11); an unreachable SHA in
  a repo with no remote exits 1 (lines 48-51). Neither is touched by this change, and both are the paths
  most likely to be broken by a careless tidy-up.
- Drift guard: every top-level entry from `git ls-files` is either watched or explicitly listed as not a
  build input, with a failure message that names the offending entry and says what to do.

Then `npx vitest run --project node` (full project, per the de-flake rule in AGENTS.md, not the file
alone), then `npm run pre-pr`. No e2e, no migration, no screenshot regeneration: nothing user-facing
changes.

Post-merge, the only real-world check is observational: the first `main` deploy after this lands should
log "App/site files changed - proceeding with build". It cannot be proven on `qa`, because the qa preview
is fired through a deploy hook (`.github/workflows/qa-preview-deploy.yml`) and I have not verified
whether a hook-triggered deployment sets `VERCEL_GIT_PREVIOUS_SHA` at all.

## Risks and unknowns

- **Latent, so there is no symptom to confirm against.** As the issue says, no deploy has been wrongly
  skipped yet; every recent `messages/` commit also touched `app/` or `components/`. The test is the only
  evidence the fix works, which is why the control case matters as much as the three new ones.
- **Failure polarity is one-directional.** An over-broad pattern costs one build; an under-broad one
  costs a silently stale production site. Prefer over-broad on every judgement call in this file.
- **Slightly more builds on `main`.** Catalogue changes are frequent. That is the intended trade, not a
  regression.
- **Unverified: whether the ignore step runs for deploy-hook deployments of `qa`.** The fix targets
  `main`, which is where `vercel.json:4-9` permits auto-deploy, so this does not block the change.
- **Guard-test friction.** Every new top-level file or directory will fail CI until someone classifies
  it. That is the point, but the failure message has to be actionable or it becomes a nuisance that gets
  rubber-stamped.
- **Em dashes.** `scripts/check-no-em-dash.mjs` scans `.tsx?/.mjs/.cjs/.js` (`SOURCE_EXT`, line 56) but
  not `.sh`, which is why the existing shell comments still contain them. The new `.mjs` test file is in
  scope, so keep its comments em-dash-free. Do not tidy the `.sh` comments in this PR: unrelated churn on
  a file whose diff should stay readable.

## Open questions for Fraser

**Q1. Should `CHANGELOG.md` be watched too?** (The issue raises this explicitly.)

- **A: add it to `WATCH_PATHS`.** It is a genuine build input: `next.config.ts:47-49` traces it into the
  `/whats-new` deployment and the page reads it via `fs` at render time.
- **B: leave it unwatched**, on the grounds that release commits bump `package.json` and rebuild anyway.
- **Recommendation: A.** The only commits whose behaviour changes are hand-made changelog corrections,
  which are rare, so the extra-build cost is near zero, while the cost of being wrong is a permanently
  stale `/whats-new`. One line.

**Q2. Keep the allowlist, or invert it to a denylist?**

- **A (what this plan assumes):** keep `WATCH_PATHS`, add the three missing entries, add the drift-guard
  test.
- **B:** invert the script. Build by default; skip only when the diff is confined to a known-inert list
  (`docs/`, `e2e/`, `.github/`, `.claude/`, `changelog.d/`, `tools/`, root `*.md`). Structurally
  fail-safe: a new build input is covered the day it lands, with no list to keep fresh.
- **Trade-off:** A is the smaller diff and the fewer builds, but keeps a list that has already drifted
  twice and relies on a test to notice the third time. B ends the drift class outright, at the price of a
  build on every docs-only commit that reaches `main`. In practice that is few, since `main` only
  receives `qa -> main` promotion merges and release commits, and both nearly always touch watched paths
  already.
- **Recommendation: A.** The guard test buys most of B's protection for a fraction of the change, and B
  is a behaviour change wider than the issue asked for. If you would rather have the structural fix, say
  so: the same file gets rewritten around a `SKIP_PATHS` list, and the test file carries over almost
  unchanged (the drift guard becomes "every top-level entry is either inert-listed or triggers a build").
