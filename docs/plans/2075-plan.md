# Plan: #2075 Dependabot keeps offering TypeScript 7 in the tooling group, which CI rejects, so @types/node updates are stuck behind it

## What this is

A config-only fix. `.github/dependabot.yml` has no `ignore` rule, and its `tooling` group (lines 25-26) bundles `typescript` with `@types/node`. So every tooling PR carries typescript 6 to 7, which cannot pass while #1921 is open, and the harmless `@types/node` bump is stuck behind it (#1916 closed, #1988 had to be edited by hand before merge, #2037 is red now).

The core change needs no decision: add a semver-major `ignore` rule for `typescript`. The issue's second point, whether `@types/node` should follow the Node 24 runtime instead of ^26, is a scope call for Fraser (Q1 below). The plan covers both outcomes.

Checked against the code on `qa` (6a6b2104):

- `package.json:90` has `"typescript": "^6"`, locked at 6.0.3 (`package-lock.json:13107`).
- `package.json:75` has `"@types/node": "^26"`, locked at 26.2.0 (`package-lock.json:5319`; the issue says 5340).
- `package-lock.json:13120-13142`: typescript-eslint is locked at **8.59.2** on qa, and its declared peer range is `typescript: ">=4.8.4 <6.1.0"`. The issue's "8.69.0" comes from the install on #2037's branch, not from qa. Either way, the conclusion holds: typescript-eslint rejects TS 7.
- `.nvmrc` = `24`, `package.json:6` `engines.node` = `24.x`, and every workflow uses `node-version-file: .nvmrc` (enforced by `scripts/check-node-version-drift.mjs`).

## Approach

Exact block to insert after `open-pull-requests-limit: 5` in the npm entry, before `groups:`:

```yaml
    # TypeScript 7 is blocked until Next.js supports the native compiler (#1921):
    # `next build` crashes without the removed JS compiler API,
    # scripts/check-no-em-dash.mjs uses that API, and typescript-eslint refuses
    # TS 7 outright. Without this rule every `tooling` group PR carries the major
    # and strands the @types/node bump riding with it (#1916, #1988, #2037).
    # Remove it as part of the #1921 upgrade.
    ignore:
      - dependency-name: "typescript"
        update-types: ["version-update:semver-major"]
```

With Q1 option A, append to the same list:

```yaml
      # @types/node follows the runtime major in .nvmrc (Node 24), not the
      # newest Node. Bump it by hand in the same change that bumps .nvmrc.
      - dependency-name: "@types/node"
        update-types: ["version-update:semver-major"]
```

The block goes above `groups:`, not inside it: `ignore` belongs to the update entry, and the existing comment requires `npm-security-other` to stay last within `groups`. Dependabot drops ignored versions before it builds a group, so the tooling group PR should then contain only `@types/node`.

Rejected alternatives:

- **Remove `typescript` from the `tooling` group.** This frees `@types/node`, but Dependabot would then open a standalone TS 7 PR every week, and each one would fail and need closing. It moves the noise without removing it.
- **`@dependabot ignore typescript major version` comment on #2037.** It works, but the ignore lives in Dependabot's hidden per-repo state, not in the repo: nobody can review it, nobody will find it when #1921 fires, and it breaks the single-source-of-truth rule. It is also a GitHub mutation.
- **`versions: [">=7"]` instead of `update-types`.** It works the same today. `update-types` is what the issue proposed, and it matches the optional `@types/node` rule, where "any major above the current one" is the right idea. Minor and patch updates to 6.x keep flowing either way.
- **Put `@types/node` in its own group.** This does nothing about the TS 7 offers, which are the actual failure.

1. **Local syntax check (before PR).** Parse the file and assert the structure, e.g. `node -e` with `js-yaml` after `npm ci` under Node 24 (it arrives transitively via ESLint; check it resolves first), or `npx --yes js-yaml .github/dependabot.yml`. Confirm `updates[0].ignore[0]` is `{dependency-name: "typescript", update-types: ["version-update:semver-major"]}` and that `groups` is unchanged.
2. **Gate.** Run `npm run pre-pr` under Node 24. With config alone this is a formality. Under Q1 option A it is the real test: `npm run typecheck` against `@types/node` 24 is what shows no code uses a Node 25+ API. The issue found no such call site, but `tsc` is the authority, and `@types/node` 24 also brings a different `undici-types` line, so `fetch`/`Response` typings may shift.

   - `gh pr checks <n>` then `gh pr view <n> --json statusCheckRollup`: `test` and the Coverage check are green. (Don't trust the `--watch` exit code alone.)
   - No open PR offers `typescript` 7.x.
   - Check the npm update job on GitHub's Dependabot page for this repo for config errors. Confirm where that page lives in the UI before quoting a click path.

## Risks and unknowns

- **Activation is delayed until promotion.** Until this reaches `main`, Dependabot keeps offering 7.0.2 and #2037 stays red. That is harmless but visible. See Q3.
- **What Dependabot does with #2037 once the config changes is unverified.** It may rewrite the group PR in place or close it and open a new one. Either outcome is fine; step 3 of Testing covers both.
- **Unverified: whether `ignore` also suppresses a Dependabot security update for `typescript`.** This only matters if an advisory is fixed only in 7.x, which is unlikely for a devDependency compiler.
- **A future TypeScript 6.1 minor would still be offered through the group**, and qa's typescript-eslint declares `typescript <6.1.0` as its peer range. That could produce a new lint failure the same way. This is out of scope here, but worth knowing if the tooling PR goes red again.
- **Remember to remove the rule.** The rule is relative to the installed version, so once #1921's manual bump to 7 lands, a leftover rule would silently block 8. The comment and the proposed #1921 note (Q4) are the only prompts to remove it.
- **Review routing.** AGENTS.md's mandatory workflow-expert review covers `.github/workflows/**` only, and `.github/dependabot.yml` is outside it. It becomes mandatory only if Q2 (a) touches `node-version-drift.yml`. `code-reviewer` runs regardless.
- **Q1 option A downgrade.** It could surface type errors not visible today (see Testing, step 2). If it does, that is evidence the gap was real, and the fix belongs in this PR only if it is small. Otherwise stop and report.

## Open questions for Fraser

**Q1. Should `@types/node` follow the Node 24 runtime?**
Today `tsc` type-checks against Node 26 APIs while the code runs on Node 24 (`.nvmrc`, `engines`, Vercel, CI).

- **A. Pin to `^24` and add a semver-major ignore rule for it. (Recommended.)** The types then match the runtime, so a Node 25+ only API becomes a compile error instead of a production crash. Cost: a lockfile churn PR, possible typecheck fallout, and a manual `@types/node` bump every time `.nvmrc` moves.
- **B. Keep `^26` deliberately** and add a one-line comment in `dependabot.yml` saying so. No work and no churn, but the latent risk the issue describes stays, and nothing flags it.
- **C. Leave it for now** and handle it whenever `.nvmrc` next moves. This keeps this PR minimal, but #1921-style drift tends to be forgotten.

**Q2. (Only if Q1 = A.) Add a forcing function so the pin cannot drift?**

- **(a) Extend `scripts/check-node-version-drift.mjs`** so the `@types/node` major must equal the `.nvmrc` major, and add `package.json` to that workflow's trigger paths. (Recommended.) This follows the repo's single-source-of-truth rule: without it, the next `.nvmrc` bump silently leaves the types behind, the same class of bug #1575 fixed for workflows. Cost: about 20 lines plus a new test, and a mandatory workflow-expert review.
- **(b) Rely on the `dependabot.yml` comment**, or file it as a separate follow-up issue. This keeps #2075 a pure config PR, but the protection is only as good as someone reading the comment.

**Q3. How should this land?**

- **qa, the normal route. (Recommended.)** Nothing in production is broken. The only cost is that #2037 stays red until the next `qa -> main` promotion.
- **Hotfix PR straight into `main`.** It takes effect on the next Dependabot run, but it needs your `hotfix` label and a backmerge into `qa` afterwards, which is a lot of ceremony for a devDependency.

**Q4. GitHub housekeeping (these mutate shared state, so they need your OK).**

- **#2037: leave it open** for Dependabot to rewrite after promotion, and close it only if it still carries TS 7 after the first run. (Recommended.) The alternative, **closing it now**, gives a cleaner queue, but Dependabot will reopen the same TS 7 PR on Monday until the config reaches `main`.
- **#1921: post a comment (recommended) or edit the body.** Either way, add typescript-eslint as blocker 3, and add "remove the `typescript` ignore rule in `.github/dependabot.yml`" to its revisit steps. A comment keeps your original text intact; editing the body keeps the checklist in one place.
