# Plan: #2011 QA-seed cards use a non-canonical subject_key format that no production code path can parse

## What this is

The three QA-seed card builders in `lib/qa-seed/scenarios.ts` hand-roll `subjectKey`
strings (`species:25`, `edge:1:2`) instead of calling the canonical codec in
`lib/cards/subjectKey.ts` (`"25"`, `"1>>>2"`). The fix is to call the codec, and to
replace the fitness test that currently pins the wrong format with one that pins the
codec round-trip.

I verified every claim in the issue against the code before writing this. Two
corrections to the issue's own analysis, both of which change how the fix should be
justified but not what the fix is:

**1. Hydration does normalise, on most paths.** The issue says the bad key survives
load because `migrateReviewCard` (`lib/review/persistence.ts:208`) only backfills when
`subjectKey` is `undefined`. That part is true, but `hydrateSession`
(`lib/review/session.ts:257-345`) unconditionally rewrites `subjectKey` through
`Subject.forSpecies` / `Subject.forEdge` for every saved card whose seed entry resolves.
QA-seed cards are built from real `SEED_POKEMON` / `SEED_EVOLUTION_CARDS` entries, so on
any surface that hydrates (`components/review/ReviewSession.tsx:1264`,
`app/journey/page.tsx:430`, `app/stats/page.tsx:265`, both Pasture pages) the bad key is
silently replaced before it reaches the eligibility gate.

**2. There is nevertheless a real consumer that sees the raw key.** The badge hooks read
`loadSession()` and pass `session.cards` straight into the eligibility chokepoint with no
hydration step:

- `components/pwa/usePwaBadge.ts:47` → `computeQueueCount` (`lib/stats/dashboard-snapshot.ts:216`)
  → `computeEligibleCardIds` (`lib/review/scope.ts:401`) → `isCardEligible` (`lib/eligibility/index.ts:143`).
- `components/pwa/useDocumentTitleBadge.ts:56` → the same chain.

`app/pokedex/page.tsx:33` also calls `hydrateSession` with an empty `evoSeed`, so seeded
evolution cards hit the `if (!fresh) return card` branch and keep `edge:1:2`.

So the honest statement is narrower than "no production code path can parse it", and
narrower still than the issue's headline, but the defect is real: the QA harness produces
card identities that two live consumers cannot parse, and the divergence between the
hydrating and non-hydrating paths is itself the thing that makes it invisible. Everything
in the issue's "Honest scoping of the impact" section still holds: seeded ids are all
below `ALT_FORM_ID_THRESHOLD` (10000), so nothing user-visible is wrong today.

## Approach

**The fix.** Call the codec at the three builder sites. There is no design latitude here:
`Subject.forSpecies` / `Subject.forEdge` are the single source of truth, both builders
already have the raw ids in hand, and both throw on non-positive-integer input, so a
future bad id fails loudly at seed time instead of producing an unparseable key.

**The forcing function.** The point of the issue is not the three lines, it is that the
harness drifted from production identity for months with a test asserting the drift was
correct. The mechanism I would add is a round-trip fitness test over every scenario in
`SCENARIOS`, in the existing "AC2: Card identity from real hydrate path" describe block:

- For every seeded `name` card: `Subject.parseSpecies(card.subjectKey) === card.id`.
- For every seeded `reverse` card: `Subject.parseSpecies(card.subjectKey) === card.pokemonId`.
- For every seeded `evolution` card: `Subject.parseEdge(card.subjectKey)` equals
  `{ fromId: card.preEvoId, toId: card.postEvoId }`.
- For every seeded card, mapped through `appTypeToDbType`:
  `resolveAnchorId(dbType, card.subjectKey) !== null`.

That last assertion is the sharp one. `resolveAnchorId`
(`lib/eligibility/scopePredicate.ts:125`) returns `null` for both current QA-seed shapes
and non-null for both canonical shapes, so it fails today and passes after the fix
without encoding any string literal in the test. Round-tripping through the parser rather
than string-comparing against the encoder means the test cannot be satisfied by a second
hand-rolled format, which is exactly how the current test failed.

**What I rejected.**

- *An ESLint `no-restricted-syntax` rule* banning template literals shaped like
  `` `species:${x}` ``. The repo does use this lever (`eslint.config.mjs:74` for
  `.displayName`), but a selector can only ban the shapes we already know about, and the
  three existing bad shapes in this repo are `species:`, `edge:a:b`, `a:b` and `a-b`. A
  rule would not have caught the fourth. The round-trip test catches every shape.
- *Normalising in `migrateReviewCard`* (`lib/review/persistence.ts:205-233`), i.e.
  re-deriving `subjectKey` whenever it fails to parse rather than only when `undefined`.
  It would work and it is only a few lines, but it makes the load boundary silently
  repair producer bugs, which is the opposite of a forcing function: the next divergent
  producer would then be invisible on *every* path, not just the hydrating ones. I would
  not do this.
- *Validating `subjectKey` format in `isReviewCardShaped` / `parseSession`.* Actively
  dangerous: `parseSession` (`lib/review/persistence.ts:239, 267`) returns `null` for the
  whole session if any single card fails validation, so one malformed key would discard a
  user's entire local card set. Not worth it for a QA-only defect.
- *Deriving `subjectKey` inside a shared card-factory* so the QA seed cannot set it at
  all. Structurally the best answer, but `SeededCard` is a deliberately minimal
  serialised shape distinct from `ReviewableCard`, and unifying them is a much larger
  change than this issue warrants.

**Order of work.** Change the builders first, run `npx vitest run --project node
lib/qa-seed`, confirm the existing `:526` assertion fails (proving it was pinning the
divergence), then update it and add the round-trip test.

## Testing

What proves it works, in order of strength:

1. **New round-trip fitness test** in `lib/qa-seed/scenarios.test.ts`, as specified above.
   Confirm it fails on the pre-fix builders before landing it, otherwise it is decoration.
2. **Updated assertion** at `lib/qa-seed/scenarios.test.ts:526`, now comparing against
   `Subject.forSpecies(rc.pokemonId)`.
3. **Existing suites that must stay green unchanged**, since they cover the paths the
   seeded keys flow through:
   - `lib/qa-seed/scenarios.test.ts` in full, in particular the practice-load smoke block
     at `:614-686` (`hydrate` → `buildSessionQueues`) and the `(id, locale)` uniqueness
     tests at `:210` and `:661`. Changing the key format must not collapse or split any
     card identity: name and reverse cards for one species share a `subjectKey` today and
     must still share it after, because the composite key everywhere is
     `cardType:subjectKey:locale` (`lib/sync/cloud.ts:510`, `lib/sync/pullAndMerge.ts:107`).
   - `lib/eligibility/index.test.ts` and `lib/review/scope.test.ts`, untouched, as
     regression cover on the gate.
4. **Full-suite de-flake, not file-alone** (AGENTS.md, #1464 / #1470):
   `npx vitest run --project node` and `npx vitest run --changed origin/qa`.
5. **`npm run pre-pr`** for the lint → typecheck → build → test → coverage → diff-coverage
   chain. Diff coverage should be trivially satisfied: three changed product lines, all
   executed by every scenario builder test.
6. **No e2e change required** for the core fix. Nothing user-facing changes, and no
   screenshot surface is affected. If the open question below is answered "yes", the
   `e2e/practice-scope.spec.ts` fixture edit needs a `chromium` run of that spec.

Manual QA is optional here and I would skip it: turn on `qaSeedMode`, apply
`pasture-progression`, and confirm Practice / Pasture / Stats behave identically to
before. The change is a no-op on those surfaces by construction, because `hydrateSession`
was already rewriting the key to exactly the value we now seed.

## Risks and unknowns

- **Low blast radius, and it is genuinely low.** The seeded value now equals what
  `hydrateSession` was already substituting, so every hydrating surface sees byte-identical
  input before and after. The only behavioural delta is on the two badge hooks and the
  Pokédex page, where cards stop being unparseable.
- **A latent QA-mode sync interaction, worth knowing about but not fixing here.**
  `pullAndMerge` keys local cards by `${cardType}:${subjectKey}:${locale}`
  (`lib/sync/pullAndMerge.ts:107, 113`). Background pulls stay enabled while superuser
  flags are on (only writes are suppressed), so today a signed-in tester with a QA seed
  applied has local cards that cannot key-match their cloud rows, and a pulled cloud card
  looks like a new insertion. This fix removes that mismatch as a side effect. I have not
  traced whether it currently causes visible duplicate cards in QA, and I would not expand
  this PR to find out.
- **Unknown: whether any QA scenario was authored around the broken behaviour.** I found
  no evidence of one. Every seeded id is a real seed id below 10000, so the skipped
  alt-forms exclusion is inert, and no scenario description references form cards. If a
  scenario turns out to depend on a card slipping the gate, the round-trip test will
  surface it as a failure rather than a silent change.
- **The `lint:agents-size` and pseudo-locale gates are not engaged** by this change: no
  `AGENTS.md` edit, no message-catalogue key.

## Open questions for Fraser

**Do the three non-QA-seed test fixtures with the same defect come along in this PR?**

The same class of hand-rolled key exists in three test files the issue does not mention.
I found these while checking whether the QA seed was the only offender:

- `e2e/practice-scope.spec.ts:568` - `subjectKey: "1:2"` on the Bulbasaur evolution
  fixture, should be `"1>>>2"`.
- `lib/review/scope.test.ts:109` and `:129` - `` `${preEvoId}-${postEvoId}` `` on the
  evolution and reverse-evolution card factories.
- `lib/evolution/chains.test.ts:46, :58, :67` - `` `${seed.preEvoId}:${seed.postEvoId}` ``.

None of these look deliberate; they read as placeholder values written before the codec
was the established convention. `lib/review/scope.test.ts` is the one that matters: those
fixtures feed `cardIsEligible` → `isCardEligible`, where an unparseable edge key hits the
`catch` at `lib/eligibility/index.ts:157` and is treated as eligible. So those tests are
currently exercising the malformed-key fallback rather than the real alt-forms path, and
would not catch a regression in it.

- **Option A - fix them in this PR.** Six extra lines, all in test files, and it makes the
  new round-trip rule true repo-wide rather than true only for the QA seed. Consistent
  with the "cover every producer path" principle. Risk: `lib/review/scope.test.ts` and
  `lib/evolution/chains.test.ts` assertions may quietly depend on the current fallback
  behaviour, so a couple of them could need adjusting, which widens the diff into
  test-semantics territory.
- **Option B - QA seed only, file the rest as a follow-up issue.** Keeps this PR to the
  literal issue scope and keeps the review surface tiny.

**Recommendation: Option A**, with the caveat that if either non-e2e file's assertions
shift meaningfully once the keys are canonical, I stop and split that file out rather
than reinterpreting what the test was for. The QA-seed fix alone leaves the alt-forms gate
untested through its real parsing path, which is a thinner result than the issue is
actually asking for.
