# Plan: #2081 Monitor workflows keep misfiring when they look up their tracking issue: qa-drift-check overwrote and closed an unrelated issue (#1997)

## What this is

Four scheduled workflows find their tracking issue again by an HTML-comment marker. Each workflow has its own copy of that lookup. Three copies use an unanchored jq `contains`, so any open issue that quotes the marker can be taken over, as #1997 was. The fourth (`monitor-grade-log-divergence.yml`) uses `gh issue list --search "... in:body"`, the search form that #1919 found silently matches nothing.

This change adds one shared lookup, points all four monitors at it, and adds a lint check so the next workflow cannot bring either form back. The human tidy-up the issue lists (#1997's lost text, #2000 to #2002, #2010) is out of scope, as the issue says.

This plan deliberately names markers ("the drift marker") rather than quoting them in full. Until the fix reaches `main`, any issue body that quotes a full marker can be taken over.

**Live state, checked read-only with `gh` on 2026-09-17:**

- There are 44 open issues. Every current lookup caps at 100.
- Only two open issues contain a full monitor marker: #2044 (drift) and #2031 (grade-log). Both have the marker alone on line 1, and both were authored by `app/github-actions`.
- I checked every issue, open or closed, whose body starts with one of the four markers. All were authored by `app/github-actions` except one: #1997, authored by `app/poke-memory-bot`. #1997 is the takeover victim, and its overwritten body now **starts** with the drift marker. So matching on line 1 alone would still match an issue that has already been taken over.
- The repo is public, so any GitHub account can open an issue whose first line is a marker.
- All four writers post with `GITHUB_TOKEN`: `auto-release.yml:248`, `cron-health-monitor.yml:52`, `pokeapi-species-monitor.yml:49` and `monitor-grade-log-divergence.yml:97`.

## Approach

### 1. The shared lookup

How a workflow calls it:

```sh
EXISTING=$(node .github/scripts/find-marker-issue.mjs \
  --repo "$REPO" --marker "$MARKER" --author app/github-actions)
```

It prints the issue number, or nothing if no issue matches. It exits non-zero if `gh` fails, if `gh` returns something that is not JSON, or if the list may have been cut short. Under the callers' `set -euo pipefail`, a failing command substitution in an assignment aborts the step. So a failure can never look like "no existing issue".

How it works:

1. **Fetch.** It runs `gh issue list --repo R --state open --limit 1000 --json number,author,body` through `execFileSync`, with no shell, so the marker text is never shell-interpreted.
2. **Match.** An issue matches only if both hold:
   - `author.login` equals `--author`;
   - the first line of the body, split on `\r?\n` and with trailing whitespace trimmed, is **exactly** the marker.

   This is a slightly stricter form of the issue's suggested `startswith`, and it matches what every writer already does: the marker sits alone on line 1 (`auto-release.yml:298`, `cron-health-monitor.yml:263`, `pokeapi-species-monitor.yml:117`, `monitor-grade-log-divergence.yml:127`). It also stops a marker from matching a longer marker that starts with it. A null or empty body does not match and does not throw. A body with CRLF line endings (from a web-UI edit) still matches.
3. **Duplicates.** If more than one issue matches, it prints the newest, which is what today's `.[0]` over gh's newest-first order does. It also writes a `::warning::` listing the others, so duplicates show up in the run log instead of passing silently.
4. **Truncation guard.** If `gh` returns exactly `--limit` issues, the helper exits non-zero. A silent cap is how a real tracking issue could fall off the list and a duplicate get filed.
5. **Structure.** The pure `findMarkerIssue` is exported. The CLI only runs when the file is executed directly, using the same guard as `scripts/check-no-em-dash.mjs:433-438`. The function that calls `gh` can be swapped out in tests.
6. **Node built-ins only.** The qa-drift-check job, `cron-health-monitor.yml` and `pokeapi-species-monitor.yml` have no `setup-node` step, so they use the runner's preinstalled Node. `pokeapi-species-monitor.yml:67` already relies on that for `node -e`.

**Why Node rather than bash.** The existing helpers in `.github/scripts/` are bash, each with a `.test.sh` sibling, but nothing in CI runs those `.test.sh` files: the only reference outside the scripts themselves is a comment in `qa-issue-label.yml`. CI runs `npm test -- --changed origin/<base>` (`ci.yml:98-106`). A `.mjs` helper imported by a vitest file is in that import graph, so a later edit to the helper reruns its tests.

Rejected alternatives:
- A bash helper with a `.test.sh`: the tests would never run in CI.
- A bash helper spawned from vitest with a stubbed `gh` on `PATH`: this works, but an edit to the `.sh` file alone is not in the import graph, so `--changed` would skip the test.

**Why an author filter, which the issue did not ask for (see Q2).** Anchoring the match to line 1 fixes what triggered #1997: a marker quoted mid-body. It does not fix two closely related cases:
- **Planted marker:** because the repo is public, anyone can open an issue whose first line is the drift marker. The drift job would then rewrite that issue's body daily and close it.
- **Already overwritten:** an issue that has already been taken over keeps the marker on line 1, as #1997's body does today, so it stays matchable.

Every legitimate tracking issue was written by `app/github-actions` (checked above). WORKFLOW.md's trust rule (line 184, #1859) already says a body marker alone is attacker-postable. The author is a required argument at each call site, so it sits in the same step as the token that decides it.

**Other rejected alternatives:**
- **Keeping `--search` with the marker quoted:** GitHub's search index strips HTML comments (WORKFLOW.md:93).
- **Keeping the grade-log `--label monitoring` filter:** once author and anchor both have to match, the label adds nothing. It also adds a way to fail: if someone removes the label, the lookup misses the issue and a duplicate gets filed.
- **Keeping the single fetch in `cron-health-monitor.yml` by letting the helper read pre-fetched JSON:** that saves three API calls a week. The cost is a second input path that would need its own tests. The plan calls the helper four times a week instead.

### 2. The forcing function

`scripts/lint-marker-lookups.mjs` scans `.github/workflows/*.yml` line by line. No YAML parser is a dependency (`scripts/dependabot-config.test.mjs:15` says the same).

- It skips any line whose trimmed text starts with `#`. The existing warning comments mention the banned form on purpose, for example `auto-close-umbrella.yml:33`.
- It flags any line containing `in:body`.
- It flags any line containing both `contains(` and `body`. That catches the jq form `select(.body | contains(...))` and the Actions-expression form `contains(github.event.comment.body, ...)`.

On the current tree these rules flag exactly ten lines, and nothing else. I checked with grep: the label checks, such as `changelog-gate.yml:59` and `vercel-preview-on-ready.yml:59`, have no `body` on the line.

| Line | Kind | Handled by |
|---|---|---|
| `auto-release.yml:274` | issue lookup | the helper |
| `cron-health-monitor.yml:245` | issue lookup | the helper |
| `pokeapi-species-monitor.yml:107` | issue lookup | the helper |
| `monitor-grade-log-divergence.yml:119` | issue lookup (`in:body`) | the helper |
| `coverage.yml:152` | comment lookup, writer puts marker on line 1 (`:132`) | Q1 |
| `ci-failure-autofix.yml:68` | comment lookup, marker on line 1 (`:125`) | Q1 |
| `pr-check-monitor.yml:94` | comment lookup, marker on line 1 (`:109`) | Q1 |
| `vercel-preview-on-ready.yml:130` | comment lookup, marker on line 1 (`:246`) | Q1 |
| `vercel-preview-on-ready.yml:56` | `if:` trigger filter on the auto-review marker | allowlist |
| `vercel-preview-on-ready.yml:202` | the auto-review SHA marker, which sits on **line 2** (`workflow-expert.md:29`), so `startswith` cannot work | allowlist |

**Escape hatch.** Allowed exceptions live in an array inside the script, as `{ file, needle, reason }` entries, not as an inline YAML comment. A `#` comment cannot go inside the `if: |` block scalar at `vercel-preview-on-ready.yml:56`. The test fails on any allowlist entry that no longer matches a line, so entries cannot go stale.

**Failure message.** It points issue lookups at `.github/scripts/find-marker-issue.mjs` and comment lookups at `startswith`.

**Why the lint chain rather than a vitest test.** CI's vitest run uses `--changed`, which follows imports. A PR that only edits a workflow would therefore skip a test that reads YAML. `npm run lint` runs in full on every PR that touches `.github/**`, because `ci.yml:37-44` counts `.github/**` as code.

## Testing

**`scripts/find-marker-issue.test.mjs`**

Matching cases:

- **The #1997 case.** A newer issue by the same author quotes the drift marker mid-body, and an older issue has it on line 1. The lookup returns the older issue even though the newer one comes first in gh's order. This is exactly what went wrong on 2026-08-04.
- **Already overwritten.** Marker on line 1, author `app/poke-memory-bot`: no match.
- **Planted by an outsider.** Marker on line 1, author an ordinary user: no match.
- **Colon markers.** The cron-health marker for `auto-release.yml` and the grade-log marker both match. This is the #1919 regression.
- **Markers stay separate.** The cron-health marker for `auto-release.yml` does not match an issue carrying the marker for `refresh-user-count.yml`.
- **Marker plus more text on line 1:** no match. This pins the exact-first-line rule.
- **Tolerated formatting.** A CRLF body matches. Trailing whitespace after the marker matches.
- **Empty bodies.** An empty-string body and a null body: no match, and no throw.
- **Duplicates.** Two matches: the newest is returned and the other is reported as a duplicate.

CLI cases, using an injected `gh` runner:

- A runner that throws: non-zero exit, nothing on stdout.
- A runner that returns non-JSON: non-zero exit.
- A runner that returns exactly `limit` items: non-zero exit with a truncation message.
- No match: exit 0, empty stdout.
- The `gh` arguments include `--state open` and `--json number,author,body`, and never `--search`.

## Risks and unknowns

- **The lookup is tied to the posting identity.** If a monitor later switches to the App token, its issues are authored by `app/poke-memory-bot`. Its lookup would then stop matching, and it would open a new issue on every run. What limits the damage:
  - the `--author` value sits in the same step as the token;
  - the helper's header comment will say so;
  - the duplicate warning makes the result visible.

  A lint rule tying `--author` to the step's token is possible but not worth the complexity yet.
- **Existing tracking issues must still match.** #2044 and #2031 do (line 1, `app/github-actions`, checked 2026-09-17). Re-check just before merging.
- **A human edit can hide a tracking issue.** If someone edits one so line 1 is no longer the marker, the monitor stops finding it and opens a new one. That is noisy but does no damage, unlike the current failure.
- **Runner Node version is not pinned** in the three jobs without `setup-node`. Using only built-ins keeps that safe. If workflow-expert prefers, add `actions/setup-node` with `node-version-file: .nvmrc` to those jobs; it costs a few seconds per run.
- **The lint check is textual.** A lookup that puts `contains(` and `.body` on different lines would slip through. Every current site keeps them on one line, and the tests pin the forms it catches.
- **The old lookups stay live until promotion.** Until this reaches `main`, the old drift, cron-health and pokeapi lookups still run. No open issue other than the real tracking issues quotes a full marker (checked). Any new issue filed from this work (follow-ups, retros) must not quote a full marker until then. PR bodies and comments are safe, because the lookups list issue bodies only.
- **Not in scope: auto-close for the grade-log monitor.** It never closes its alert when the check returns OK, so #2031 stays open until someone closes it.
- **Follow-up candidate: a dead gate.** `auto-review.yml` was removed on 2026-08-16 (AGENTS.md), so nothing posts auto-review markers any more. The review gate in `vercel-preview-on-ready.yml` (lines 56 and 181-210) therefore looks like it can never pass, which would leave `/preview` as the only way to get a preview deploy. That is a separate problem and worth its own issue. It is also why this plan allowlists those two lines rather than converting them.
- **Stale marker table.** The table in `workflow-expert.md` still lists markers from removed workflows. This plan only adds a paragraph there and does not clean up the table.

## Open questions for Fraser

**Q1. How far should the lint rule, and therefore this PR, reach?**

- **A. All marker `contains` lookups, on issues and PR comments (recommended).** Change the four comment lookups whose writers put the marker on line 1 (`coverage.yml:152`, `ci-failure-autofix.yml:68`, `pr-check-monitor.yml:94`, `vercel-preview-on-ready.yml:130`) from `contains(` to `startswith(`, one word each. Allowlist only the two auto-review lines in `vercel-preview-on-ready.yml`, pointing at the dead-gate follow-up.
  *Trade-off:* four more workflow files in the diff, each needing workflow-expert review. In return, the same bug is fixed for PR comments. For example, `coverage.yml` would try to overwrite the first comment that quotes its marker.
- **B. Issue-body lookups only.** The lint check ships with all six comment and expression lines allowlisted under one reason, and a follow-up issue covers them.
  *Trade-off:* the smallest diff, and it matches the issue's four-monitor scope. But the allowlist starts with six entries, which weakens the check, and the comment lookups stay unanchored.
- **C. Check only `in:body` plus the four monitor files by name.**
  *Trade-off:* the least work, but a new monitor file would not be covered, which is how #2003 happened. Not recommended.

**Q2. Keep the author filter, which goes beyond the issue's suggested fix?**

- **A. Keep it (recommended).** It closes the two cases a line-1 match alone leaves open: an outsider planting a marker in a new issue on this public repo, and an issue that was already overwritten (#1997).
  *Trade-off:* the lookup depends on the identity that posts the issue (see Risks). A tracking issue someone recreates by hand is not picked up unless it is posted as `app/github-actions`.
- **B. Match on line 1 only, as the issue suggests.**
  *Trade-off:* simpler, with no dependency on the posting identity. But anyone who can open an issue can still get the drift job to rewrite and close it.
