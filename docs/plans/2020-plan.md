# Plan: #2020 Preview deploys can never fire: the gate still waits for an auto-review verdict nothing posts

## What this is

The defect the issue describes is real and every line reference in it matches the working copy. `.github/workflows/vercel-preview-on-ready.yml:212-218` requires `steps.review.outputs.pass == 'true'`, that output comes from the step at lines 181-210 which looks for a `<!-- auto-review-sha:$SHA -->` marker, and `auto-review.yml` (the sole writer of that marker) no longer exists in `.github/workflows/`. The automatic gate is permanently closed.

One fact changes what to do about it, and the issue flagged it as an unconfirmed observation:

**`WORKFLOW.md:740` documents this workflow as deliberately disabled.** The Status row reads "**Disabled** (`disabled_manually`). Under the qa staging flow, QA happens on the bundled `qa` branch via `qa-preview-deploy.yml`, so per-PR previews are redundant and were retired to stay within Vercel's deploy rate limit (#814)." That line was added by commit `147ba962` ("feat(workflow): extend qa staging flow to the auto pipeline (#814)"), long before the 2026-08-16 automation removal, and it explains the "no runs since 2026-05-17" observation the issue could not resolve.

Two consequences:

- The blast radius section overstates the live impact. Per-PR previews were retired by decision, not broken by the auto-review removal. Nothing regressed on 2026-08-16 except the correctness of a file that was already dormant.
- The "still working" list is wrong on one row. A workflow disabled at GitHub level does not run on *any* trigger, so `/preview` is dead too, not just the automatic gate. (`qa` previews and `main` production deploys are unaffected, as stated: `qa-preview-deploy.yml` and Vercel's own `main` deploy are separate paths.)

So this is not "restore a broken preview pipeline". It is "decide what to do with a dormant, unreferenced workflow whose gate is now provably dead", and that end-state call is Fraser's. The mechanical repair is fully specified below and is the same work under every option that keeps the file.

Verified in the working copy (`porter-author/2020-plan`, based on `qa` at `d7181d15`):

- `.github/workflows/auto-review.yml` is absent; the only surviving `auto-review-sha` references are inside `vercel-preview-on-ready.yml` itself and in `.claude/agents/workflow-expert.md:28-29`.
- `vercel.json:4-9` sets `git.deploymentEnabled` to `{"**": false, "main": true}`, as the issue says.
- `qa-preview-deploy.yml` is `workflow_dispatch`-only and hardcodes `?ref=qa`; `.claude/commands/batch-issues.md:240-255` drives the batch preview-QA step through it. The batch flow does not depend on `vercel-preview-on-ready.yml` at all.
- `.claude/commands/ship.md` never mentions previews.
- No other workflow, command, skill or doc references `vercel-preview-on-ready.yml` apart from the `WORKFLOW.md` catalogue entry. `cron-health-monitor.yml` does not watch it (it is not cron-driven).
- Nothing in the repo describes a marker the Mac-local loop posts, so the issue's "replace the review gate with whatever the Mac-local loop posts" suggestion has nothing to point at today.

## Approach

The design decision is not how to remove the dead condition (that is mechanical), it is what the workflow should be *for* now that per-PR previews were retired but no on-demand preview path for a feature branch exists. That is the open question below.

What I rejected, and why:

- **Fire on the CI `test` check alone and re-enable** (the issue's first suggested fix, option D). Correct as a code change, but it silently reverses the #814 decision: every green CI run on every non-`qa` PR would fire a Vercel deploy, which is the exact volume #814 retired to stay inside the rate limit. It also restarts `e2e.yml` on every resulting preview (that workflow triggers on `deployment_status` for non-Production `vercel[bot]` deployments). Re-enabling is a Fraser call, not a bug fix.
- **Substitute a Mac-local-loop verdict for the auto-review verdict** (the issue's second suggestion). Not actionable: nothing in the repo defines a marker the loop posts into poke-memory PRs, so this would mean inventing a contract with `Frazzled-Productions/frazzled-loop` from this side. If that contract is wanted it should be designed once, in the loop repo, and consumed here afterwards.
- **Fix the condition and stop** without touching `WORKFLOW.md`. Rejected: `WORKFLOW.md:31` mandates the doc update in the same commit, and line 740's Status row is precisely the fact that would have saved this issue a round trip.
- **Bundle the `.claude/agents/workflow-expert.md` cleanup.** Rejected as above: partial correction of a broadly historical file reads as "this file is now accurate", which is worse than a file everyone knows is dated.

Process note for whoever implements: `.github/workflows/**` requires a `workflow-expert` review on every change with no mechanical-change exception (AGENTS.md file-ownership table, WORKFLOW.md line 93), and because this workflow uses marker-based dedup (`<!-- vercel-preview-fired:<sha> -->`) the same rule says consult `workflow-expert` *before* writing the edit, not only as a reviewer afterwards.

## Testing

There is no unit-test surface for this and no `actionlint` in the repo, so the proof is layered:

1. **`workflow-expert` review** of the diff, dispatched before and after the edit per the rule above. This is the primary gate, not a formality: the specific things to have it check are that the fire step's `if:` no longer references a deleted step id (a dangling `steps.review.outputs.pass` evaluates to empty, not an error, so YAML will not tell you), and that the fork guard and the `author_association` check on `/preview` both survive intact (#1859).
2. **YAML parse check** before push: `python3 -c "import yaml,sys; yaml.safe_load(open('.github/workflows/vercel-preview-on-ready.yml'))"` if PyYAML is present locally. Otherwise the first push surfaces a parse failure in the Actions tab. `npm run pre-pr` does not lint YAML.
3. **`npm run pre-pr`** as the standard pre-PR gate. It should pass untouched: the diff is `.yml` plus `.md`, so there are no product lines for `scripts/diff-coverage.mjs` to score and no changelog fragment is required.
4. **Live verification, only possible under options C and D** (a disabled workflow cannot be exercised, which is the main weakness of option B): on an open non-`qa` PR, comment `/preview`, then assert all four of
   - `gh run list --workflow=vercel-preview-on-ready.yml --limit 1` shows a run for that comment,
   - the "Fire Vercel Deploy Hook" step actually ran **and logged a hook response**, not the "preview deploys paused" branch (an empty `VERCEL_DEPLOY_HOOK_URL` exits 0 by design since #618, so a green run is not evidence of a fire),
   - exactly one `<!-- vercel-preview-fired:<sha> -->` comment appears on the PR, and a second `/preview` at the same SHA is a no-op (the idempotency step at lines 115-136 skips the fire),
   - a Vercel preview deployment exists **for that branch**, confirming both that the deploy hook overrides `git.deploymentEnabled: {"**": false}` and that `?ref=<branch>` still selects the branch.
5. **Negative check, option D only**: push a commit that fails CI to the same PR and confirm the resulting `workflow_run` evaluation leaves the fire step skipped.

## Risks and unknowns

- **The disabled state is documented, not directly verified.** `gh` is not available to this lane, so `WORKFLOW.md:740` plus the run-history gap is the whole evidence base. Run `gh workflow list --all --repo Frazzled-Productions/poke-memory` before acting. The entire framing above depends on it: if the workflow is in fact enabled, the issue's blast-radius section is right, feature branches genuinely have had no preview since 2026-08-16, and options C and D become considerably more urgent.
- **Secrets may have decayed during dormancy.** `VERCEL_DEPLOY_HOOK_URL`, `secrets.BOT_APP_PRIVATE_KEY` and `vars.BOT_APP_ID` have not been exercised on this path since 2026-05-17. The paused-not-failed branch (#618) means a missing hook URL produces a green run that did nothing, so check the step log rather than the run conclusion. A missing App private key fails louder, at the token-minting step.
- **The deploy hook may have been recreated.** If the stored hook URL now points at a differently-configured hook, `?ref=<branch>` may not select the branch and the fire could deploy the wrong ref. Test 4's last assertion is specifically for this.
- **Re-enabling has second-order cost** beyond Vercel deploys: `e2e.yml` runs the Playwright smoke suite against every non-Production preview, so option D multiplies both deploy count and Actions minutes by PR volume.
- **Editing YAML here is silent-failure-prone**, which is why the mandatory review exists. Three incidents (#1859, #1815, #1806) came from treating a workflow edit as mechanical.

## Open questions for Fraser

**What should `vercel-preview-on-ready.yml` be now?** The gate cannot be repaired into its original design (nothing posts a review verdict), and per-PR previews were deliberately retired by #814, so this needs a direction, not just a fix.

- **A. Delete the workflow.** Remove the file and its `WORKFLOW.md` section. Honest about the current position: it is disabled, unreferenced, and its gate is dead. Cost: `/preview` goes with it, and there is then no way at all to preview a feature branch, since `qa-preview-deploy.yml` only deploys `qa` and `vercel.json` blocks branch auto-deploy.
- **B. Repair, leave disabled.** Drop the review gate so the file is correct if ever re-enabled, and leave the Status row as-is. Cost: nothing can be verified live (test 4 is unavailable), so it lands as untested-by-construction, and the same "what is this file for?" question resurfaces at the next audit.
- **C. Repair, enable, `/preview` only.** Drop the review gate *and* the automatic `workflow_run` arm, leaving a workflow that fires only when an OWNER/MEMBER/COLLABORATOR comments `/preview`. Background deploy volume stays at zero, so #814's rate-limit reason is respected, while on-demand feature-branch previews come back and become testable.
- **D. Repair, enable, CI-only automatic gate.** The issue's first suggestion. Restores automatic per-PR previews on green CI, and reverses #814.

**Recommendation: C.** It is the only option that both fixes the defect and leaves something demonstrably working: `/preview` is currently dead in two independent ways, it is the one preview capability with no substitute, and gating it on an explicit human comment costs nothing until someone asks for it. A is defensible if you would rather carry no per-PR preview path at all than carry a rarely-used one; D is the right answer only if per-PR previews are wanted back as a habit, which is a Vercel-budget and Actions-minutes decision rather than a bug fix. B is the weakest: it pays the review and edit cost while leaving the file as unverifiable as it is today.

The mechanical work is small under every option (one workflow file plus one `WORKFLOW.md` section), so the answer to this question is the only thing blocking implementation.
