# Plan: #2021 /batch-issues pre-flight hard-blocks on disabling the removed Auto Review workflow

## What this is

`.claude/commands/batch-issues.md` still tells a batch drain to `gh workflow disable "Auto Review"` before dispatching any implementer, and makes that a non-negotiable stop-the-run gate. `auto-review.yml` and `auto-pr.yml` were deleted on 2026-08-16 (#2003 / #2004). Verified in this worktree: neither file exists under `.github/workflows/`.

So the gate is at best a wasted round-trip each drain, and at worst the skill's own escalation rule ("do NOT fall back to proceeding ... STOP and get it suspended first") halts pre-flight and escalates a blocker about a workflow that was deliberately removed. AGENTS.md was corrected in #2004; the skill was not, and `/ship` defers to it (`.claude/commands/ship.md:8`), so both orchestration paths inherit the stale step.

The change is prose-only inside one command file: delete the dead instructions, keep the one true statement (the in-session `code-reviewer` is now the sole review gate), and renumber cleanly.

## Approach

**Delete the instructions rather than annotate them as historical.** This file is imperative: an orchestrator executes it top to bottom. A dated "this used to happen" note in an imperative file still costs the reader a decision on every run, which is the cost the issue is complaining about. AGENTS.md set the precedent in #2004 by replacing the instruction with a positive statement of what happens now, and `:211` gets exactly that treatment here.

Rejected alternatives:

1. **Keep the disable but make it best-effort** (drop the blocking language, ignore errors). Rejected: it removes the hard stop but keeps a per-drain round-trip on a workflow that cannot come back, and leaves a false claim ("`auto-review.yml` runs on PRs into `qa`") in a file agents read as ground truth.
2. **Apply WORKFLOW.md's dated-banner treatment in place.** Rejected for the imperative-file reason above, and because the file is already 58KB with #1994 open to convert it to a progressively-disclosed skill; adding tombstones works against both.
3. **Fold this into #1994's skill conversion.** Rejected: the issue's point is that the stale step blocks a drain today, and every deletion here is independent of whichever shape the file lands in.

**The load-bearing detail is the renumbering, not the deletions.** Six numbered cross-references point at steps that shift. All verified:

## Risks and unknowns

- **Whether the command errors today is unverified.** This lane has no network (`gh workflow list --all` was not approved), so I could not confirm whether GitHub still holds a workflow record named "Auto Review" for the deleted file. GitHub does retain records for deleted workflow files, so `gh workflow disable "Auto Review"` may still resolve the name and return success, making today's cost a wasted round-trip rather than the hard stop the issue describes. **The fix is identical either way**; only the severity claim depends on it. Whoever implements should settle it with one `gh workflow list --all | grep -i "auto review"` and state the real answer in the PR body rather than repeating the issue's assumption.
- **Line numbers are anchored to this worktree** (base `qa`, merge `d7181d15`). They matched the issue's cited numbers exactly, so nothing has moved since it was filed, but `qa` moves. Anchor the edits on quoted strings, not line numbers.
- **A maintainer directive is being deleted.** Wrap-up `:238` carries an explicit 2026-06-07 directive from Fraser ("Keep Auto Review OFF ... the mistake the maintainer caught"). Removing it is correct only because its subject no longer exists, not because the directive was wrong. Flagged so it can be vetoed rather than discovered later.
- **Adjacent live breakage, not fixed here.** `.github/workflows/vercel-preview-on-ready.yml:181-218` still gates its Vercel deploy hook on a `poke-memory-bot[bot]` comment containing `<!-- auto-review-sha:$SHA -->`. Nothing writes that marker any more, so `steps.review.outputs.pass` is permanently `false` and the automatic per-PR preview deploy can only fire via the manual `/preview` override. The manual `qa` preview (`qa-preview-deploy.yml`, dispatched in Wrap-up) is unaffected. This is a real workflow defect, separate from this issue: different file, different area label, and `.github/workflows/**` needs a `workflow-expert` review per AGENTS.md. See the open question below.
- **Doc debt deliberately left alone.** `.claude/agents/workflow-expert.md:28-80` and much of WORKFLOW.md still describe the removed workflows. WORKFLOW.md carries a deliberate 2026-08-16 banner saying the maintainer chose to date it rather than rewrite, so that is a decision, not an oversight. `workflow-expert.md` has no such banner and is stale, but it is reference material for an advisory agent, not an instruction that blocks a run.

## Open questions for Fraser

**1. Does this change extend to WORKFLOW.md's drain protocol, or stay strictly inside the command file?**

`WORKFLOW.md:100` and `:102` restate the same instruction operatively: "**suspend Auto Review before dispatching the first implementer** ... Do not dispatch any implementer until the disable succeeds", and "then **re-enable Auto Review** ... as the last action".

- **Option A (recommended): also fix `WORKFLOW.md:100` and `:102`.** These two lines are operative instruction, not catalogue description, and leaving them re-seeds exactly the divergence this issue traces (#2004 fixed one half of an instruction pair, the other half kept executing). Two lines, no structural change.
- **Option B: strictly the file the issue names.** Cleanest match to the issue as filed, and it avoids touching a document where you deliberately chose "honestly dated over confidently wrong".

Trade-off: Option A slightly reopens the banner decision, since the banner already declares everything auto-\* below it historical, and a reader who trusts the banner is not misled. Option B is defensible, but a drain following the WORKFLOW.md protocol summary would still be told the disable is a gate. I would take A and leave every descriptive auto-\* section under the banner untouched.

**2. The `vercel-preview-on-ready.yml` dead gate: separate issue, or fold in?**

- **Option A (recommended): file it as its own bug** (`area:workflow`), and keep #2021 prose-only. It needs a `workflow-expert` review, a decision about what the gate should key on now that nothing posts a verdict, and it carries deploy-behaviour risk that a docs change does not.
- **Option B: fix both in one PR.** One less round-trip, but it mixes a zero-risk text deletion with a workflow change that can break preview deploys, and puts them behind one review.

The decision needed from you is really "what should that gate key on instead" (CI-green alone? require the manual `/preview`? drop the workflow?), which is a direction call, so it wants its own issue either way. I have not filed it, since this lane does not mutate GitHub state.
