## Context

Poké Memory runs on Vercel (Next.js 16, Cache Components on, a Node function for the FSRS optimiser)
and Supabase (Postgres with 17 row-level security policies, 9 `SECURITY DEFINER` functions, 6 `pg_cron`
jobs, 5 `pg_net` calls, 3 Vault secrets, Supabase Auth with GitHub, Google and username accounts).
Company decision 0018 (ops, 19 November 2026) moves every app to Cloudflare Workers with D1. This is
stage 4 of that programme (ops #610). A local trial on 19 November 2026 proved the parts: with
`cacheComponents: false` all 21 routes render on Workers and match `next start`; the schema, Better Auth
and the settings path ran on D1; `web-push` and Sentry ran under `nodejs_compat`; the optimiser cannot
run in a Worker (it needs threads) but its wasm build runs in the browser on a cross-origin-isolated page.

About 20 people have accounts and the database is 25 MB (grade_log about 19,000 rows). Guests keep
everything in the browser and are not affected beyond the hosting change.

## Goals / Non-Goals

**Goals:** the whole app runs as one Cloudflare Worker with one D1 database (EU jurisdiction), with the
same behaviour for players except one more sign-in; every per-user query is pinned to the session user
by one helper, with a CI rule and cross-user tests; scheduled work runs from the Worker; nightly backups
to R2; per-PR preview versions; a rehearsable data copy.

**Non-Goals:** the cutover itself (DNS, the write freeze, the live copy), any change at Supabase, Vercel,
GitHub or Google, Cache Components (off until the adapter bug is fixed and tested), new features.

## Decisions

### D1. Runtime: OpenNext on one Worker, Cache Components off

`@opennextjs/cloudflare` builds `.open-next/worker.js`; `cacheComponents: false` in `next.config.ts`
(OpenNext PR #1318 unmerged, every Cache Components page hangs). Incremental cache: the static-assets
cache with cache interception off, as in the trial: nothing revalidates at runtime (no `cacheTag`,
`updateTag` or `revalidateTag` call exists in the app), so no R2 or KV cache is needed. Pages that were
partially prerendered now render per request (25 to 60 ms in the trial). `app/test-error` gets
`dynamic = "force-dynamic"` because without Cache Components its deliberate throw would fail the build.
`CHANGELOG.md` is read from the filesystem today, which a Worker has not got: a build step
(`scripts/generate-changelog-module.mjs`) writes it into a generated module.

Alternatives: a VPS (rejected in decision 0018); keeping Cache Components with PR #1318 (still logs a
render mismatch, not shippable).

### D2. Worker entry and scheduled work

`worker/index.ts` wraps the OpenNext handler and adds `scheduled`. Two Cron Triggers replace the six
`pg_cron` jobs: `0 * * * *` and `*/30 * * * *`. A pure function `cronRoutesFor(cron, now)`
(`lib/cron/schedule.ts`) maps each firing to the app's own routes, which keep their constant-time bearer
check (`CRON_SHARED_SECRET`, now a Worker secret instead of a Vault secret):

| Was (`pg_cron`) | Now (UTC) | Route |
|---|---|---|
| hourly daily reminders (031) | every hour | `POST /api/push/send-daily` |
| hourly streak nudge (047) | every hour | `POST /api/push/send-streak-nudge` |
| weekly digest, Monday 09:00 (042) | Monday 09:00 | `POST /api/discord/digest` |
| feedback retention, 03:00 (034) | 03:00 | `POST /api/cron/feedback-retention` |
| grade_log orphan reconcile, Sunday 04:00 (032) | Sunday 04:00 | `POST /api/cron/reconcile-grade-log` |
| rate-limit bucket clean-up, every 30 minutes (041) | every 30 minutes | `POST /api/cron/rate-limit-cleanup` |
| (new) nightly backup | 02:00 | `POST /api/cron/backup` |

The scheduled handler calls each route through the Worker's own fetch handler (no network hop), awaits
it with `ctx.waitUntil`, and logs the status. A failing route does not stop the others.

Outbound sends (Web Push, Discord) happen only when `DEPLOY_ENV` is `cloudflare-production`
(`lib/outbound.ts`); anywhere else the routes do their reads and log what they would have sent. The
preview Worker has no Cron Triggers and no VAPID private key or Discord webhook, so a preview loaded
with rehearsal data can never message a real person.

### D3. Data: one D1 database, schema translated from Postgres

`db/d1/migrations/0001_schema.sql` is the final state of Postgres migrations 001 to 051 in SQLite
(rules in the file header: uuid and timestamptz as TEXT, jsonb as TEXT with `json_valid`, booleans as
0/1, CHECKs that need `current_date` as triggers, `RAISE(ABORT, ...)` for the regression guards).
`0002_auth.sql` holds Better Auth's tables (generated by its CLI with the username plugin). `0003_events.sql`
is the events table (D9). The Postgres migrations in `db/migrations/` stay as history until the 14-day
fallback ends (then removed, task in the after-cutover issue).

Guards that move from the database to the Worker (D1 cannot run them as triggers, or the trial chose
JS for fidelity):

- `merge_user_settings` (deep merge): JavaScript, because SQLite's `json_patch` drops keys whose patch
  value is null and Postgres `jsonb_deep_merge` keeps them as null. Read, merge, compare-and-swap on
  `updated_at`, up to 5 retries.
- The `user_settings` regression guard (migration 038): JavaScript in the same merge, same rules and the
  same `23514` code.
- The Discord notify trigger on feedback insert and delete (042, 051): the feedback route and the
  retention job call the notify logic directly with `ctx.waitUntil`, instead of `pg_net` from a trigger.
  The bug embed's Supabase dashboard link becomes the feedback row id; the rest of the message is the
  same.
- `reset_all_progress` (018, 026 cooldown, 022 tombstone) and `delete_account` (027): JavaScript in
  `lib/db/rpc/`, each one D1 `batch()` (atomic), user id from the session only.

Guards that stay in the database as SQLite triggers: the `card_reviews` regression trigger (002, 015,
016, 017, 020), the `updated_at` stamp (043), the `last_reset_at` tombstone checks on `card_reviews`,
`streak_days` and `grade_log` (022), `streak_days` no future date (021), the push subscription limits
(049), username format CHECKs.

### D4. Authorisation: the scope helper replaces row-level security

`lib/db/scope.ts` exports `forUser(db, userId)`. Every read gets `user_id = ?` bound to the session user;
every written row has its `user_id` set to the session user, and a row naming anyone else is refused
with 403 before SQL runs. Table and column names are checked against an allowlist (`lib/db/tables.ts`)
that also converts types (0/1 to booleans, JSON text to objects), so callers see the same shapes as
supabase-js returned. Errors carry Postgres-style codes (`23514` for a guard, `23505` unique, `42703`
unknown column) so the client's existing rejection and structural-error handling keeps working.

Cross-user work (the cron routes, the feedback notify, the backup) uses `lib/db/system.ts`, whose
functions are named for their one job and are only importable from `app/api/cron/**`,
`app/api/push/send-*`, `app/api/discord/**` and `app/api/feedback/**` (ESLint `no-restricted-imports`).

**CI rule:** `scripts/check-scoped-queries.mjs` (in `npm run lint`) fails when a file outside `lib/db/`
calls `.prepare(`, `.exec(` or `.batch(` on a D1 binding, or holds SQL naming a per-user table
(`card_reviews`, `user_settings`, `streak_days`, `grade_log`, `push_subscriptions`, `feedback`,
`feedback_discord_posts`, `rate_limit_buckets`, `user`, `session`, `account`). Better Auth's own queries
run inside the library and are outside the rule.

**Cross-user tests:** every route and gateway operation has a test with two users proving that user B
can neither read nor change user A's rows (`lib/db/crossUser.test.ts` and each route's test).

### D5. The browser data client and the gateway

Today 52 call sites in the browser call supabase-js directly under RLS. Rewriting each into its own
route would touch every sync module and its tests. Instead `lib/db/client.ts` gives the browser a small
client with the same query-builder subset the app uses (`from().select().eq().in().gte().not().order()
.range().limit().maybeSingle().single()`, `upsert`, `insert`, `update`, `delete`, `rpc`, and
`count: "exact", head: true`). It serialises each query to JSON and posts it to `POST /api/db`, which
runs it through the scope helper. The wire format is fixed and validated (zod-free, hand-written checks):
unknown tables, columns, operators and RPC names are refused. Results come back as `{ data, error,
count }` like supabase-js. Upserts run as one D1 `batch()` (atomic, like one Postgres statement).

The RPCs the browser may call: `reset_all_progress`, `delete_account`, `merge_user_settings`. Other
tables the browser never touched directly (`feedback`, `feedback_discord_posts`, `rate_limit_buckets`)
are not on the gateway.

Alternatives: one route per operation (more churn and more test rewrites for the same security); a
PostgREST-compatible endpoint behind supabase-js itself (keeps a Supabase dependency named for a
service we left, and its auth module).

### D6. Auth: Better Auth on D1

`lib/auth/server.ts` builds Better Auth per request from the D1 binding: username plus password (the
username plugin; usernames keep the `^[a-z0-9_-]{3,30}$` rule and the synthetic email), GitHub and Google,
account linking across the three (`trustedProviders: ["github", "google"]`, `allowDifferentEmails: true`).
Handler at `app/api/auth/[...all]/route.ts`. New user ids are UUIDs (`generateId`), the same shape as
the copied Supabase ids. `lib/auth/client.ts` is Better Auth's React client; `AuthContext` keeps its
`{ user, loading }` interface on top of `useSession`. `requireAuth` reads the session from the request
headers. The OAuth callback becomes Better Auth's `/api/auth/callback/<provider>`; the old
`/api/auth/callback` route and `exchangeCodeForSession` go. `callback-complete` keeps its job (sorting
the first arrival by what data exists), reached as the OAuth `callbackURL`.

**Passwords:** Supabase stores bcrypt hashes; the copy moves them into Better Auth's `account.password`.
`password.verify` checks a `$2a$`/`$2b$` hash with `bcryptjs`, otherwise Better Auth's own scrypt. After a
successful bcrypt sign-in the hash is replaced with scrypt (an after-hook on the username sign-in), so
bcrypt hashes fade out.

**Sessions:** none are copied, so every signed-in player signs in once more, with no notice (decision
0018). Their local data stays on the device and the account guard (`guardAccountSwitch`) sees the same
user id, so nothing is archived or merged differently.

**Per-IP throttle:** username sign-up and sign-in keep the existing per-IP buckets
(`rate_limit_buckets`, now in D1), applied in a Better Auth `before` hook. The IP comes from
`CF-Connecting-IP` (set by Cloudflare), never the first `X-Forwarded-For` value, which a client can set;
the feedback limit uses the same header.

**Usernames:** the `usernames` table goes; the username lives on Better Auth's `user` row (`username`
column, format checked by triggers in `0002_auth.sql`).

**Privacy defaults:** sessions store no IP address or user agent; OAuth tokens are not kept in plain
text. Sign-out revokes all of the player's sessions, as Supabase's did. OAuth failures land on
`/?error=<code>`, and the home page shows its sign-in error for any code.

**Re-sign-in after the move:** a player whose device already holds progress for the same user id is
not asked to pick local or cloud; it behaves like an ordinary sign-in on their own device (pull and
merge).

### D7. The optimiser in the browser

The native `@open-spaced-repetition/binding` route goes. Its wasm32-wasi build runs in a Web Worker on a
dedicated page, `/settings/optimiser`, served with `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp` (only that path, so cross-origin images elsewhere keep
working). The Settings section links there; the page reads the grade log through the data client, builds
items (one item per review prefix, see #2392), runs `computeParameters`, and saves the weights with the
existing settings push. The weekly limit (`OPTIMIZER_COOLDOWN_MS`) and the minimum review count stay
in the shared `lib/srs/optimizer.ts` and are now checked in the browser and again in the settings merge
(`fsrsWeightsOptimizedAt` may not move forward less than a week after the stored one). The old route's
five-minute in-progress lock goes: the run happens on the player's own device. The page reads the
last-run date from the cloud settings row, as the route did, and the player's locale.. A browser without
cross-origin isolation or wasm threads sees a plain "not supported in this browser" message.

### D8. Push, Discord and Sentry on Workers

`web-push` and `@sentry/nextjs` run under `nodejs_compat` (trial). VAPID keys become Worker secrets: a new key pair, because Vercel never returns its stored secrets
(owner ruling, 19 November 2026, 21:30). Existing browser subscriptions belong to the old public key, so
on app start a signed-in player with notification permission whose subscription carries a different key is
re-subscribed with the current key automatically (no prompt on the same origin). The private key is
required only in production (elsewhere the send
routes compute targets and log counts without failing).
Sentry environment names change from `vercel-production`/`vercel-preview` to `cloudflare-production`/
`cloudflare-preview` from a `DEPLOY_ENV` var; the privacy scrubbing (`lib/observability/sentryPrivacy.ts`)
is unchanged. `maxDuration` exports are dropped (Workers ignore them; Cron Triggers allow 15 minutes).

### D9. Analytics

`@vercel/analytics` and `@vercel/speed-insights` go. The one custom event (`app_open` with two bucketed
properties) goes to `POST /api/event`, counted per UTC day in a D1 table holding only the day, the event
name, the two buckets and a count (no IP address, user agent, user id or page address), rate-limited per
event name. Page views come from Cloudflare Web Analytics when a beacon token is set at build time
(`NEXT_PUBLIC_CF_BEACON_TOKEN`; absent in previews).

### D10. Backups

`POST /api/cron/backup` (02:00 UTC) writes every table as SQL `INSERT` statements to R2
(`poke-memory-backups`, EU jurisdiction) at `d1/YYYY-MM-DD.sql`, then deletes objects older than 90 days.
D1 Time Travel covers 30 days on top. A monthly GitHub Actions job restores the latest file into a local
D1 and checks row counts (it needs an R2 read token, an owner step). The preview Worker has its own
bucket.

### D11. Previews and deploys

`.github/workflows/deploy.yml`, modelled on the company site's (stage 1): a push to `main` builds, applies
D1 migrations and deploys the Worker `poke-memory`; a pull request uploads a version of the separate
Worker `poke-memory-preview` (own D1 database and bucket, seeded with test data by
`scripts/cloudflare/seed-preview.mjs`), aliased `pr-<number>`, and comments its URL. With no
`CLOUDFLARE_API_TOKEN` secret the jobs skip with a notice. Until cutover the Worker is only reachable
at `poke-memory.frasers-account.workers.dev`. The Vercel-specific workflows (`qa-preview-deploy`,
`vercel-preview-on-ready`, `vercel-failure-autofix`, `stale-preview-check`) and `vercel.json` go;
`e2e.yml` runs the auth specs against the preview version URL instead of a `vercel[bot]` deployment.
`migration-check.yml` checks D1 migrations apply cleanly to a fresh local D1 instead of Supabase parity;
`integration-tests.yml` runs the D1 suite instead of Postgres.

### D12. The data copy (rehearsable, not run live here)

`scripts/cloudflare/copy-from-supabase.mjs` reads a Postgres connection (`DATABASE_URL`, read-only) and
writes one SQL file for `wrangler d1 execute --file`: app tables row for row, `auth.users` to `user`
(same id, email, `username` from `usernames`), `auth.identities` to `account` (GitHub and Google, keyed
by the provider's user id), bcrypt hashes to `credential` accounts, no sessions. Timestamps are kept as
they are (the push subscription triggers must not rewrite `last_seen_at` or trim rows on import), and
push rows on an unknown host are skipped and counted, since the D1 CHECK applies to copied rows. It then prints row
counts per table for the check. Rehearsed in CI against the local Postgres container loaded with the
migrations and fixtures, then imported into a local D1 and compared.

## Risks / Trade-offs

- [The gateway is a generic query endpoint] -> it can do no more than the anon key could under RLS: the
  session user's own rows, allowlisted tables and columns, fixed operators; cross-user tests for every
  table and operation.
- [Lost database backstop: RLS] -> the scope helper, CI rule and cross-user tests (decision 0018).
- [D1 has no interactive transactions] -> atomic `batch()` for multi-statement work, compare-and-swap for
  the settings merge.
- [D1 limits: 100 bound parameters per statement] -> one statement per row inside a batch.
- [Partial prerendering lost] -> pages render per request; measured 25 to 60 ms in the trial.
- [Optimiser needs cross-origin isolation] -> only on its own page; unsupported browsers see a message.
- [Workers paid-plan CPU time] -> cron sends are I/O bound; the push helper's time budget stays.
- [Lock-in to Cloudflare] -> accepted in decision 0018.

## Migration Plan

Built and tested on `poke-memory-preview` and `poke-memory.frasers-account.workers.dev` before any
cutover. Cutover (a separate, owner-run step in #2393): two copy rehearsals, a short write
freeze, copy, row-count check, DNS switch, smoke test; Vercel and Supabase read-only for 14 days, then a
final dump to R2 and deletion. Rollback inside the window: point DNS back to Vercel; writes made on
Cloudflare in between are lost unless copied back (accepted: the window is short and the user count small).
